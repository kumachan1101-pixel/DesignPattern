## 著者指摘の採否を検証する

著者指摘を文言どおり全章へ貼り付けない。各指摘について、解決したい読者の困りごと、現行仕様との整合、前後フェーズへの影響、全章共通か章固有かを確認する。既存原則と衝突する場合は、採用、限定採用、不採用と理由を`review-tasks.md`の章別監査へ残す。

例えば「最初に`main()`と実行結果を見せる」は、コードより前に現状仕様をすべて定義する原則を撤回しない。次の順に統合する。

```text
代表的な実行結果を最初に提示
→ その結果を生む入力・操作と結果の読み方を文章で説明
→ 現状仕様をコードなしで確定
→ 同じケースの代表main・利用例
→ 入力・コード・結果の対応を確認
→ 全体構造・クラス図
→ クラス別コードと説明
```

この順序により、最初に動作イメージを与えながら、未定義の役職・状態・操作を`main()`で初出させるネタバレも防ぐ。実行結果には現状仕様だけを載せ、変更後要素や将来機能を混ぜない。

目的は実行結果の見出しを前へ移すことではない。初見読者が、コードを読む前に「誰が何を指定し、どの公開操作を行い、主要処理と状態変化がどの順に起き、何が返るか」を説明できる状態にする。中心動作を表さないデバッグ行や最終メッセージ一行だけを代表結果にしない。現行システムの価値が伝わるエンドツーエンドケースを時系列で示し、同じケースを後続の`main()`と対応させる。

```text

→ フェーズ4で確定した構造上の原因
→ フェーズ5-1の課題候補と、その候補を導いた理由
```

## フェーズ3の仮実装を変更IDへ明示的に紐づける

フェーズ3へ渡す入力は、1-5で確定した変更IDである。フェーズ3のどこかに変更IDが一度書かれているだけでは不十分であり、各仮実装コードと観測結果について、どの変更IDを適用したものか追えるようにする。

### フェーズ3の冒頭で変更試行表を置く

1-5と同じ変更ID・同じ変更文を使い、コードより前に次を示す。

| 変更ID・1-5と同じ変更文 | 現状コードへ加える変更 | 仮実装するクラス・メソッド | 同時に確認する維持範囲 | 実行・観測ケース |
|---|---|---|---|---|
| 変更ID1：【変更文】 | 【追加する分岐・状態・呼出し・データ】 | 【型名・メソッド名】 | 【既存要求・既存処理】 | 【ケース名】 |

次を必須とする。

- 1-5の全変更IDを欠落なく載せる。
- フェーズ3に、1-5にない変更ID、リスクID、未確定の将来機能を追加しない。
- 一つの変更IDが複数箇所を変える場合、修正箇所をすべて列挙する。
- 複数の変更IDを同じメソッドへ適用する場合、どの行・判断がどの変更IDかを区別する。
- 変更しない既存処理と再テスト範囲も示し、仮実装の都合で現行要求を落とさない。

### 仮実装コードの直前に適用IDを示す

コードブロックまたは連続する一組のコードブロックの直前に、次を明記する。

```text
適用する変更ID：変更ID1、変更ID2
変更する場所：BatchExecutor::execute()
変更ID1のコード：C社クライアントの生成・送信分岐
変更ID2のコード：各送信結果からSlack通知を呼ぶ処理
維持する処理：入力検証、データ取得、結果保存
```

複数変更が混在するコード内では、`// 変更ID1: C社連携の分岐`のように対応する行を示す。コメントだけで済ませず、本文または変更試行表で変更内容と観測目的を説明する。

### すべての変更IDを実際に試す

- 確定変更が条件分岐、状態、登録、生成、通知、履歴、順序、エラー処理を変えるなら、対応する仮実装コードを示す。
- コード全体の再掲は不要だが、変更IDを実装した事実を文章だけで済ませない。
- 順序や失敗後続行など複数要素の組合せが要求される場合、`main()`側の手動呼び分けではなく、現状システムへ書き足した仮実装の制御フローを示す。
- 設定・登録データだけの変更でも、登録コードまたは設定差分と、それを利用する既存コードへの接続を示す。
- 同じ仮実装で複数変更IDの相互影響を見る場合、一つの代表ケースへまとめてよい。ただし、各IDの入力、変更行、観測結果を分けて説明する。

### フェーズ3内で同じ変更IDを追う

```text
1-5の変更ID・変更文
→ 3-1の変更試行表
→ 3-1の仮実装コード
→ 3-1の実行・観測結果
→ 3-2の変更影響グラフ
→ 3-3の痛み
```

上記の変更ID集合は一致させる。3-3の痛みは、実際に仮実装したコードと再テスト範囲から導き、文章だけで想像した変更を根拠にしない。

変更IDと課題IDは一対一に紐づけない。変更IDは「何を現状構造へ適用したか」を追い、課題IDは観測した複数の痛みと原因を検討した後で「どの構造上の接続を直すか」を追う。

## 継承関係を採用する場合の必須説明

継承矢印をクラス図へ追加するだけでは不十分である。次を順番に説明する。

1. 何が全具体クラスで共通なのか。
2. 何が具体クラスごとに変わるのか。
3. 基底クラスまたはインターフェースが守る契約は何か。
4. 基底クラスへ置く処理・データは何か。
5. 具体クラスが実装または上書きする処理は何か。
6. 共通側が変更されない理由は何か。
7. 誰が具体クラスを選択・生成するのか。
8. 生成したオブジェクトを、どの基底型・インターフェース型として受け渡すのか。
9. 実行側が具体クラスの型判定をせず、共通契約だけを呼ぶこと。
10. 具体クラスを追加した場合に、変更する場所と変更しない場所はどこか。

共通性がない、具体クラスが一つしかない、実行側が引き続き具体型を`if`や`dynamic_cast`で判定する場合は、継承を採用した理由を再検討する。

## 「具体を生成して、契約として渡し、具体を意識せず実行する」を示す

各章で、次の知識配置が成立するかを説明する。

```text
生成する場所だけが具体クラスを知る
                 ↓
生成した具体オブジェクトを共通契約として渡す
                 ↓
安定した実行側は具体クラスを判定せず共通操作を呼ぶ
```

最低限、コードで次の二つを対応づける。

```cpp
// 具体クラスを知る生成・選択側
IContract* component = new ConcreteComponent(...);

// 具体クラスを意識しない実行側
component->execute();
```

上記は説明用の抽象例である。本文へそのまま貼らず、各章の実際のクラス名、入力、契約、実行メソッドに置き換える。

## 分離・生成・注入・所有・再結合を混同しない

各用語を次の意味で使う。

| 用語 | 本書で示す内容 |
|---|---|
| 分離 | 別の理由で変わる判断を別の責任へ移す |
| 選択 | 入力や設定から、利用する具体クラスを決める |
| 生成 | 具体クラスのインスタンスを作る |
| 注入 | 生成済みの依存インスタンスを、必要とするクラスへ外から渡す |
| 受け渡し | Factory等が生成結果を契約型で返し、利用側が受け取る。すべてを依存注入と呼ばない |
| 所有 | インスタンスの生存期間と、最後に破棄する責任を持つ |
| 組み立て | 複数のインスタンスを実行可能なオブジェクト構造へ接続する |
| 再結合 | 分離した責任を、要求を最後まで実行できる一つのシステムへ戻す |
| 実行 | 安定側が具体型を判定せず、契約の操作を呼ぶ |

「接続する」「注入する」「再結合する」だけで済ませず、実際のクラス名とコードで説明する。

## 生成時点と生存期間を分ける

各章で、少なくとも次を区別する。

- アプリケーション起動時に一度だけ生成する長寿命の部品。
- 一つの要求や操作ごとに生成する部品。
- 一回のメソッド実行中だけ存在する一時オブジェクト。
- 登録先や履歴が継続して所有するオブジェクト。
- 外側の部品が内側の部品を所有する合成構造。

生成・注入表には、生成場所だけでなく、生成時点、渡し先、契約型、所有者、破棄者を記載する。

## 掲載コードの必須条件

一メソッドだけの浮いた断片を出さない。設計判断を理解するために、最低限次が分かる範囲を掲載する。

- 変更前か、変更途中か、採用後か。
- 所属クラス。
- 必要なメンバー変数。
- コンストラクタと受け取る依存。
- 対象メソッド。
- 呼び出し元または生成元。
- 入力と戻り値。
- 所有・破棄の責任。

フェーズ6で全完成コードを再掲する必要はない。課題に関係するコードを、読者が途中を推測せず読めるまとまりで示す。全完成コードはフェーズ7へ置く。

各コードブロックの前に「変更前コード」「採用後コード」「採用後コードの関連部分」など、段階を明記する。

## 抜粋コードには、全体構造と抜粋位置を添える

フェーズ6で毎回すべてのコードを載せる必要はない。問題はコードを短くすることではなく、全体のどこを読んでいるか分からないことである。

抜粋コードの前に、最低限次を示す。

| 示す情報 | 内容 |
|---|---|
| 全体構造 | その処理が通る主要クラスの経路 |
| 今回の位置 | どのクラス・メソッドの、どの判断を抜粋するか |
| 変更段階 | 変更前、変更途中、採用後のどれか |
| 前後との接続 | 誰から呼ばれ、何を呼ぶか、何を返すか |
| 省略範囲 | 今回省略する安定処理と、全コードを確認できる節 |
| 確認目的 | この抜粋から、どの設計判断を確認するか |

例えば次のように、コードより先に位置を固定する。

```text
全体経路:
ReportApplication
→ ReportActionHistory
→ GenerateReportAction
→ ReportGenerationService
→ ReportAssembler
→ IReport

今回の抜粋:
採用後のReportAssembler::assemble()。
本文の具体クラスを選び、装飾列をIReportの入れ子へ変換する部分を示す。
検証と出力処理は安定側なので省略し、全コードはフェーズ7に掲載する。
```

コードを抜粋するときは、説明対象に応じて次を一緒に示す。

- メンバー変数を使うなら、そのメンバーの宣言とコンストラクタでどこから受け取るか。
- 仮想関数を呼ぶなら、基底契約と具体実装の対応。
- 具体クラスを`new`するなら、生成するコード、受け取る契約型、所有者。
- 別クラスへ委譲するなら、呼び出し側と呼ばれる側の両方。
- 登録や選択を説明するなら、登録コード、選択条件、返却型。
- 状態変化を説明するなら、変更前の値、変更処理、変更後の値、次に自動実行される処理。

一つの設計判断が複数クラスにまたがる場合は、一つの巨大コードブロックへ戻さず、番号付きで次のように接続する。

```text
1. 生成側のコード
2. 注入・受け渡し側のコード
3. 契約だけを使う実行側のコード
4. 所有・破棄するコード
```

各ブロックの間に「1で生成した`IReport*`を2でServiceが受け取る」のような接続文を書く。同じ変数名・型名を使い、読者に対応を推測させない。

抜粋の直後には、少なくとも次を説明する。

```text
変更前のどの判断が消えたか
→ 採用後のどのクラスへ移ったか
→ 安定側が具体を知らずに何を呼べるようになったか
→ 課題IDの完了条件へどう効いたか
```

短いコードブロック、`...`による省略、一つのメソッドだけの掲載を一律に禁止しない。ただし、上記の位置情報と接続がなければ掲載不十分と判定する。

## クラス図とコードの型を完全に対応させる

「浮いているクラス」を次の二種類に分け、どちらも残さない。

1. コードには定義されているが、登場型表または採用全体クラス図に載っていない型。
2. クラス図には載っているが、関係線がなく孤立している型、または完成コードに存在しない型。

部分クラス図と採用全体クラス図では基準が異なる。

### 部分クラス図

- その設計判断に関係する型だけへ絞ってよい。
- 抽象型と具体型だけを浮かせず、可能な限り、それを生成・登録・選択・注入・実行する側も含める。
- 図に載せたすべての型へ、継承、実装、保持、生成、登録、選択、引数、戻り値、呼び出しのいずれかの関係線を付ける。
- 部分図の型と関係は、後続の採用全体図の部分集合にする。

### 採用全体クラス図とフェーズ7の完成クラス図

- 完成コードで定義するすべての`class`と`struct`を、登場型表とクラス図へ載せる。
- データ型も、要求・設定・結果を受け渡す責任として省略しない。
- 完成コードに存在しない型を図へ載せない。
- 図中のすべての型に、コード上の根拠を持つ関係線を一つ以上付ける。
- 継承、実装、所有、参照、生成、注入、呼び出しを同じ線種・同じラベルで混同しない。
- 具体クラスの継承関係だけで終わらせず、具体クラスを作る側と、契約型で実行する側まで接続する。
- フェーズ6の採用全体図とフェーズ7の完成クラス図は、同じ構造定義にする。見た目を変えるために型や関係を増減させない。

変更影響グラフやシーケンス図についても、意味のない孤立ノードを残さない。変更対象外の安定クラスを示す場合は、実行・利用・所有など実際の関係へ接続し、「変更線が伸びない」ことと「システムから孤立している」ことを区別する。図の直前または直後に、線と色の読み方を説明する。

## 継承を使わない章の扱い

全章を無理に継承の説明へ統一しない。章で採用した構造に合わせて、次を説明する。

- 委譲：どの処理を、どの契約へ任せるか。
- 合成：外側と内側がどのように接続され、誰が所有するか。
- 登録：誰が具体実装を登録し、誰が契約型で検索するか。
- Factory：誰が具体生成を引き受け、利用側から何を隠すか。
- State：Contextが状態契約だけを呼び、状態遷移後の自動処理もシステム責任として接続されるか。

共通する説明軸は、分離理由、具体生成の局所化、契約としての受け渡し、具体を意識しない実行、所有・破棄である。
