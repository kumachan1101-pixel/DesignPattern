## 確認済みの問題

第1〜12章のフェーズ6は、ほぼすべて次の順序になっている。

```text
フェーズ6開始
→ 設計判断ごとの部分クラス図
→ システム全体の最終構造
→ 巨大な採用全体クラス図
→ 変更前／変更途中コードのおさらい
→ 所属クラスや生成元を省いた採用後の断片コード
```

この順序では、読者が変更前コード上の問題を思い出す前に、新しいクラス名と完成構造を読むことになる。そのため、次のつながりを追えない。

```text

→ なぜ分けるのか
→ どの責任へ移すのか
→ どの構造関係を作るのか
→ 誰が具体クラスを生成するのか
→ どこへ注入・受け渡しするのか
→ 誰が所有・破棄するのか
→ 安定側が具体を意識せずどう実行するのか
→ 課題の変更影響がどう減ったのか
```

用語や見出しが存在するだけでは不十分である。初見読者が、掲載されたクラス図とコードから上記を再現できる状態にする。

## 継承関係を採用する場合の必須説明

継承矢印をクラス図へ追加するだけでは不十分である。次を順番に説明する。

1. 何が全具体クラスで共通なのか。
2. 何が具体クラスごとに変わるのか。
3. 基底クラスまたはインターフェースが守る契約は何か。
4. 基底クラスへ置く処理・データは何か。
5. 具体クラスが実装または上書きする処理は何か。
6. 共通側が変更されない理由は何か。
7. 誰が具体クラスを選択・生成するのか。
8. 生成したオブジェクトを、どの基底型・インターフェース型として受け渡すのか。
9. 実行側が具体クラスの型判定をせず、共通契約だけを呼ぶこと。
10. 具体クラスを追加した場合に、変更する場所と変更しない場所はどこか。

共通性がない、具体クラスが一つしかない、実行側が引き続き具体型を`if`や`dynamic_cast`で判定する場合は、継承を採用した理由を再検討する。

## 「具体を生成して、契約として渡し、具体を意識せず実行する」を示す

各章で、次の知識配置が成立するかを説明する。

```text
生成する場所だけが具体クラスを知る
                 ↓
生成した具体オブジェクトを共通契約として渡す
                 ↓
安定した実行側は具体クラスを判定せず共通操作を呼ぶ
```

最低限、コードで次の二つを対応づける。

```cpp
// 具体クラスを知る生成・選択側
IContract* component = new ConcreteComponent(...);

// 具体クラスを意識しない実行側
component->execute();
```

上記は説明用の抽象例である。本文へそのまま貼らず、各章の実際のクラス名、入力、契約、実行メソッドに置き換える。

## 分離・生成・注入・所有・再結合を混同しない

各用語を次の意味で使う。

| 用語 | 本書で示す内容 |
|---|---|
| 分離 | 別の理由で変わる判断を別の責任へ移す |
| 選択 | 入力や設定から、利用する具体クラスを決める |
| 生成 | 具体クラスのインスタンスを作る |
| 注入 | 生成済みの依存インスタンスを、必要とするクラスへ外から渡す |
| 受け渡し | Factory等が生成結果を契約型で返し、利用側が受け取る。すべてを依存注入と呼ばない |
| 所有 | インスタンスの生存期間と、最後に破棄する責任を持つ |
| 組み立て | 複数のインスタンスを実行可能なオブジェクト構造へ接続する |
| 再結合 | 分離した責任を、要求を最後まで実行できる一つのシステムへ戻す |
| 実行 | 安定側が具体型を判定せず、契約の操作を呼ぶ |

「接続する」「注入する」「再結合する」だけで済ませず、実際のクラス名とコードで説明する。

## 生成時点と生存期間を分ける

各章で、少なくとも次を区別する。

- アプリケーション起動時に一度だけ生成する長寿命の部品。
- 一つの要求や操作ごとに生成する部品。
- 一回のメソッド実行中だけ存在する一時オブジェクト。
- 登録先や履歴が継続して所有するオブジェクト。
- 外側の部品が内側の部品を所有する合成構造。

生成・注入表には、生成場所だけでなく、生成時点、渡し先、契約型、所有者、破棄者を記載する。

## 掲載コードの必須条件

一メソッドだけの浮いた断片を出さない。設計判断を理解するために、最低限次が分かる範囲を掲載する。

- 変更前か、変更途中か、採用後か。
- 所属クラス。
- 必要なメンバー変数。
- コンストラクタと受け取る依存。
- 対象メソッド。
- 呼び出し元または生成元。
- 入力と戻り値。
- 所有・破棄の責任。

フェーズ6で全完成コードを再掲する必要はない。課題に関係するコードを、読者が途中を推測せず読めるまとまりで示す。全完成コードはフェーズ7へ置く。

各コードブロックの前に「変更前コード」「採用後コード」「採用後コードの関連部分」など、段階を明記する。

## クラス図とコードの型を完全に対応させる

「浮いているクラス」を次の二種類に分け、どちらも残さない。

1. コードには定義されているが、登場型表または採用全体クラス図に載っていない型。
2. クラス図には載っているが、関係線がなく孤立している型、または完成コードに存在しない型。

部分クラス図と採用全体クラス図では基準が異なる。

### 部分クラス図

- その設計判断に関係する型だけへ絞ってよい。
- 抽象型と具体型だけを浮かせず、可能な限り、それを生成・登録・選択・注入・実行する側も含める。
- 図に載せたすべての型へ、継承、実装、保持、生成、登録、選択、引数、戻り値、呼び出しのいずれかの関係線を付ける。
- 部分図の型と関係は、後続の採用全体図の部分集合にする。

### 採用全体クラス図とフェーズ7の完成クラス図

- 完成コードで定義するすべての`class`と`struct`を、登場型表とクラス図へ載せる。
- データ型も、要求・設定・結果を受け渡す責任として省略しない。
- 完成コードに存在しない型を図へ載せない。
- 図中のすべての型に、コード上の根拠を持つ関係線を一つ以上付ける。
- 継承、実装、所有、参照、生成、注入、呼び出しを同じ線種・同じラベルで混同しない。
- 具体クラスの継承関係だけで終わらせず、具体クラスを作る側と、契約型で実行する側まで接続する。
- フェーズ6の採用全体図とフェーズ7の完成クラス図は、同じ構造定義にする。見た目を変えるために型や関係を増減させない。

変更影響グラフやシーケンス図についても、意味のない孤立ノードを残さない。変更対象外の安定クラスを示す場合は、実行・利用・所有など実際の関係へ接続し、「変更線が伸びない」ことと「システムから孤立している」ことを区別する。図の直前または直後に、線と色の読み方を説明する。

## 継承を使わない章の扱い

全章を無理に継承の説明へ統一しない。章で採用した構造に合わせて、次を説明する。

- 委譲：どの処理を、どの契約へ任せるか。
- 合成：外側と内側がどのように接続され、誰が所有するか。
- 登録：誰が具体実装を登録し、誰が契約型で検索するか。
- Factory：誰が具体生成を引き受け、利用側から何を隠すか。
- State：Contextが状態契約だけを呼び、状態遷移後の自動処理もシステム責任として接続されるか。
- Command：Invokerが共通操作だけを呼び、具体操作が要求と実行先を保持するか。

共通する説明軸は、分離理由、具体生成の局所化、契約としての受け渡し、具体を意識しない実行、所有・破棄である。
