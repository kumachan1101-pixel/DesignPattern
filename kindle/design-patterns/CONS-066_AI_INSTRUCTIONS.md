## このタスクの目的

CONS-066は、著者の個別指摘が本文へ存在するかを数えるタスクではない。CONS-064・065の修正後に、全章を初めて読む読者の視点で通読し、次の二点を独立して判定する。

1. 前フェーズの確定事項が次フェーズの入力となり、同じ事実から設計結論まで論理がつながっているか。
2. 情報量が多いだけでなく、読者がシステムの動作と構造変更を自分の言葉で説明できるか。

本文を修正したAIの自己確認だけでCONS-066をPASSにしない。可能なら別AIまたは別コンテキストで監査する。

## 著者指摘を検証してから判定する

著者指摘を無条件に正解として機械適用してはいけない。各指摘または統合原則について次を記録する。

| 項目 | 記録内容 |
|---|---|
| 意図 | 読者のどの困りごとを解消する指摘か |
| 適用範囲 | 全章共通、特定章、特定パターンのどれか |
| 整合確認 | 現行仕様、前後フェーズ、完成コード、他の指摘と矛盾しないか |
| 判定 | 採用、限定採用、不採用 |
| 根拠 | ファイル、見出し、クラス、メソッド、実行ケース |

指摘同士が衝突する場合は、両方を継ぎ足して矛盾した章を作らない。目的を両立する順序または表現を決め、判断理由を残す。

確定例：システム説明の最初の具体物は代表実行結果とする。ただし、未定義の現状仕様を`main()`で先取りしない。順序は「代表実行結果→入力・操作と結果の読み方→現状仕様→同じケースのmain→構造説明」とする。

## 章別の監査順

第11章を最初に監査し、その後、第1〜12章を一章ずつ監査する。第0章・テンプレート・Agent・ルールは、本文で確定した順序と同じ指示になっているか最後に横断確認する。

各章では次の順を守る。

1. 修正を始めず、フェーズ1から章末まで通読する。
2. 現行仕様、ID集合、痛み、原因、課題、採用構造、型集合、実行結果を監査表へ写す。
3. 以下のゲートを順に判定する。
4. FAILなら、壊れた最初のフェーズへ差し戻す。後工程の文章だけを合わせない。
5. 修正後は章頭から再通読し、意図しない仕様・コード差分がないことを確認する。

## ゲート1：現行システムの動作像

フェーズ1の最初の具体物として、現行システムの中心動作を表す実行結果があるか確認する。

- 誰または何が、何を入力・指定したか。
- どの公開操作を行ったか。
- 主要処理がどの順に起きたか。
- 数値、状態、履歴がどう変化したか。
- 出力、保存、通知、エラーのどれが生じたか。
- 同じケースの`main()`または利用例と対応しているか。
- 変更後要素、将来機能、コードで初めて分かる役職・状態が混ざっていないか。

デバッグログの断片や最終メッセージ一行だけではPASSにしない。コードを読まずに主要動作を説明できるか、初見読者として文章で回答する。

## ゲート2：フェーズ間の入力と出力

各フェーズ末の確定事項と、次フェーズ冒頭の入力を横に並べる。

| 接続 | 確認するもの |
|---|---|
| 1→2 | 現行仕様・機能・要求・変更のどこを観察するか |
| 1→3 | 同じ変更ID・変更文を仮実装へ渡したか |
| 2→6 | リスクIDを未来実装せず、設計条件として考慮したか |
| 3→4 | 仮実装コードと観測した痛みだけを原因分析へ渡したか |
| 4→5 | 確定した原因文を同じ文言で候補検討の入力にしたか |
| 5→6 | 課題ID・接続点・変わる側・守る側・完了条件を同じ文言で渡したか |
| 6→7 | 採用構造・生成・注入・所有・実行規則を初出なしで実装したか |

完全一致を目的に不自然な文章を複製しない。ただし、名詞、ID、確定した短い結論の意味を無断で変えない。言い換えや追加判断には理由が必要である。

## ゲート3：原因から課題を確定する論理

- フェーズ3の痛みが変更途中コードから観測されているか。
- フェーズ4の原因が、責任・知識・状態・生成・依存の集中としてコード事実から説明されているか。
- 原因からいきなり課題IDへ飛ばず、課題候補を出した理由があるか。
- 候補の重複、統合、分割、必要性をシステム全体で評価したか。
- 評価後の課題IDが連番で、接続点・変わる側・守る側・完了条件を持つか。
- 要求IDと課題IDを一対一にしていないか。

## ゲート4：対策検討の現在地と構造変更

フェーズ6を読んで、常に「全体があって今ここ」が分かるか確認する。

- 冒頭に、現在構造、目標構造、変わる側、守る側を抽象語で示しているか。
- 各節に、全体の構造変更、今回の位置、抽象的な設計操作、具体クラス・メソッドの対応があるか。
- 変更前／変更途中コードのどの判断を扱うか分かるか。
- なぜ分けるか、どの責任へ移すか、何を守るかが順に説明されるか。
- 責任移動を着色した部分クラス図で示しているか。
- 採用後コードが、所属・呼出元・呼出先・省略範囲を含む読めるまとまりか。
- 抽象説明だけ、具体コードだけのどちらかになっていないか。

新しい進捗図は作らない。現在地は短い文章、一覧、またはクラス図の着色で示す。

## ゲート5：分離後の再結合

各課題について、次を実際のクラス名とコードで追う。

```text
変更前の責任
→ 分離先の契約と具体
→ 具体の選択・生成
→ 契約型での注入または受け渡し
→ 所有・破棄
→ 安定側による具体を意識しない実行
→ 具体入力でのオブジェクト構造と結果
```

継承・実装関係を使う場合は、共通部分、可変部分、基底契約、上書き箇所、生成者、多態実行を説明する。分離したクラスが図やコードで孤立せず、一つの要求を最後まで実行できることを確認する。

## ゲート6：図・コード・結果

- 部分クラス図が採用全体図の部分集合である。
- 完成コードの全`class`・`struct`が完成図にあり、図だけの型と孤立型が0件である。
- Mermaidにリテラル`\n`、構文エラー、意味不明な線種がない。
- 生成者、注入者、所有者、破棄者が図・説明・コードで一致する。
- フェーズ3と7の変更影響グラフが同じ変更ID・粒度で比較できる。
- 内部数値・状態変化とエラーが、対応する実行結果で観測できる。
- システムが自動で行う処理を`main()`の手動呼出しで代替していない。

## ゲート7：回帰と未使用入力

- 現行機能IDと全有効要求IDが完成コード・受入結果へ到達する。
- 変更要求で廃止していない既存機能・要求が消えていない。
- 仕様変更と関係のない保存方式、API、ログ、検証、結果が変わっていない。
- 仕様・要求・入力型の全フィールドがコードで使用されるか、使わない意図が仕様にある。
- フェーズ6の説明順修正によって、完成コード自体が不要に変化していない。

## 禁止事項

- 見出しや表の存在だけでPASSにしない。
- 本文を修正したAIの記憶だけで監査しない。
- 著者指摘を全章へ同じ文章で一括追加しない。
- 後工程の文言を合わせるために、前工程の事実を改変しない。
- 分量が多いことを説明が十分である根拠にしない。
- 自動検査だけで初見読者の理解を代替しない。
