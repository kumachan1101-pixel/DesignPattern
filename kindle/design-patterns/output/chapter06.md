## 第6章 機能を重ねて追加する ―― Decorator パターン

―― 思考の型：基本の処理と追加の処理が混在している

### この章の核心

**基本の振る舞いへ複数の追加機能を任意の順で重ねる場面では、土台と追加責任を同じ契約で扱います。組み合わせごとのクラスや条件分岐が積のように増えているなら、独立して変わる追加機能を一つの固定構成へ焼き込んでいることが兆候です。各追加機能が内側の同じ契約へ処理を委ね、利用時に必要な順で合成できるかが判断軸になります。**

---

### この章を読むと得られること

この章のテーマは「機能の組み合わせが増えるたびにクラスが爆発する」という問題です。「継承で全部作ろうとしたら間に合わなくなった」という経験がある方は、この章が直撃します。

* **得られること1：** 「機能の組み合わせ」という観点で、コードの変動箇所を識別できるようになる。「後から増える機能」と「守りたい基本機能」を区別する問いを立てる習慣が、変動箇所を見抜く目を育てる。
* **得られること2：** 接続点で基底となるオブジェクトが拡張機能の種類・コスト・組み合わせをどこまで知っているかを調べ、変更の痛みが生まれる理由を説明できるようになる。
* **得られること3：** 接続点の約束をそろえると、トッピング追加の変更を実装クラスと組み立て箇所へ寄せられることを説明できるようになる。
* **得られること4：** 基本機能と追加機能を同じインターフェースで扱うことで、呼び出し側に違いを意識させずに機能を何層でも重ねていく視点が身につく。「追加するたびに呼び出し側も変える必要が生じます」という痛みを経験したとき、この構造の必要性が実感として伝わってくる。

## 🔵 フェーズ1：現状把握 ―― 仕様を整理し、システムと紐付ける

ドリンク注文カスタマイズが何を入力として受け取り、どの処理で加工し、何を出力するのかを整理します。

### 1-1：このシステムの仕様

このシステムは、カフェのドリンク注文を**カスタマイズ**し、合計金額と注文名称を算出します。利用者から基本ドリンクIDと順序付きのトッピングIDを受け取り、メニュー表とトッピング表から名称、価格、販売可否を取得します。入力と販売可否を検証し、選択順に名称と価格を重ね、最終的な注文名称・合計金額または拒否理由を返します。

#### まず代表入力と実行結果から動きをつかむ

詳細な仕様やコードへ入る前に、1-4の`main()`で利用者がホットコーヒーを1点注文する入力を確認します。

**代表入力（1-4の`main()`から抜粋）：**

```cpp
    // 準備：メニュー台帳（DRINK001＝ホットコーヒー 400円）を用意する
    MenuDatabase db;

    // 同じ商品へ、トッピングの選択だけを変えて3回注文する
    showOrder(db, "DRINK001", false, false, false);  // なし
    showOrder(db, "DRINK001", true,  false, false);  // ミルク
    showOrder(db, "DRINK001", true,  false, true);   // ミルク＋シロップ
```

この入力に対する代表的な実行結果は次のとおりです。

```
注文内容: ホットコーヒー
合計金額: 400円
注文内容: ホットコーヒー + Milk
合計金額: 450円
注文内容: ホットコーヒー + Milk + Syrup
合計金額: 480円
```

3回並べると、この章が扱うものが見えます。基本のホットコーヒー400円に、ミルクで+50円、シロップで+30円と積み上がり、注文名称にもトッピング名が足されていきます。**変わるのはトッピングの選択だけで、基本ドリンクの価格と名前は動きません。**

この入力と出力から、(1)注文する商品を受け取り、(2)名称と価格を合成して合計を計算し、(3)注文内容と合計金額が表示される、という一連の動きが読み取れます。同じ入力を含む完全なコードと実行結果は1-4に掲載します。

#### 最初にシステム全体をつかむ

- **入力：** 基本ドリンクのメニューIDと、指定順に並んだトッピングを受け取る。
- **処理：** メニューと組み合わせを検証し、基本ドリンクへ各トッピングの名称と価格を順番に加える。
- **出力：** 完成した注文名称と合計金額を返し、未登録商品や利用不可の組み合わせでは注文を確定しない。
- **掲載コードでの代替：** 実システムの商品DBはメモリ上のメニューマスター、注文画面は標準出力で表す。名称と価格の合成、入力検証は実際に行う。

まずこの一連の動きを押さえ、以降で要求、商品と組み合わせ、システム境界、クラス、コードの順に詳細を確認します。

#### 現行要求ベースライン

| 要求ID1 | 登録済みの基本ドリンクを選ぶ | ドリンク名と基本価格を取得し、未登録IDを拒否する |

**現在のメニューと価格**

この章のカフェ注文システムでは、「基本ドリンク」と「トッピング」を分けて管理します。基本ドリンクは注文の土台（ベース価格）として固定されており、トッピングはあとから積み上げて合計価格に加算されます。

| 種別 | ID/指定名 | 表示名 | 価格 |
|---|---|---|---|
| 基本ドリンク | DRINK001 | ホットコーヒー | 400円 |
| トッピング | Milk | Milk | +50円 |
| トッピング | Syrup | Syrup | +30円 |
| トッピング | Whip | Whip | +70円 |

価格は商品企画部が決定する想定ですが、現状システムでは基本価格だけが基本ドリンク表にあり、トッピング価格は注文計算へ直書きされています。この業務上の置き場所とシステム上の置き場所のずれも、後で構造を見直す材料になります。

トッピングは複数追加できます。注文名称の表示例：ホットコーヒー + Milk + Syrup

この「注文名称」はお客様向けの表示ではなく、ドリンクを作る**スタッフへの作業指示**として使われます。「ホットコーヒー + Milk + Syrup」と表示されれば、スタッフはその順番で材料を足していけばよい、という設計です。表示のルールや区切り文字（「 + 」など）は店舗ごとに独自のルールを持つことがあり、このシステムでは店舗オペレーション部が管理する領域です。

### 1-4：実装コード（現状）

#### コードを読む前に：クラスの責任と境界

この表は、基本ドリンクと追加機能がどこで接続するかを示す読解用の地図です。画面やデータ表の代替方法は簡略化節へ集約しました。

| 対象 | 主な責任 | 接続先・結果 |
|---|---|---|
| `MenuDatabase` | メニューIDから基本ドリンクを検索する | 商品名・基本価格を返す |
| `CustomDrink` | 基本情報と3つの選択フラグを受ける | 合計金額・注文名称を返す |
| 3つの真偽値 | Milk・Whip・Syrupの有無を保持する | 選択された固定トッピングを計算へ渡す |
| 表示処理 | 計算後の名称と金額を受ける | 注文結果として表示する |

固定3種の選択が価格加算と名称生成へどう使われるかを次のコードで確認します。

このシステムには、注文対象となる次の2件の基本ドリンクがあらかじめ登録されています。食品は対象外なので、ドリンク用トッピングを食品へ適用する入力はありません。

| メニューID | 商品名 | 基本価格 |
|---|---|---|

**MenuItem と MenuDatabase**

```cpp
struct MenuItem {
    string name;      // 商品名
    int basePrice;    // 基本価格（円）
};

class MenuDatabase {
private:
    map<string, MenuItem> items;
public:
    MenuDatabase() {
        items["DRINK001"] = {"ホットコーヒー", 400};
        items["DRINK002"] = {"アイスコーヒー", 450};
    }

    bool exists(const string& id) const {
        return items.count(id) > 0;
    }

    MenuItem get(const string& id) const {
        return items.at(id);
    }

    void save(const string& id, const MenuItem& item) {
        items[id] = item;             // 実行中のメニュー表へ追加
    }
};
```

**CustomDrink**

この章の中心です。1-1の「注文内容の合成」——基本ドリンクにトッピングを重ねて金額と表示名を作る処理——に対応します。

```cpp
class CustomDrink {
private:
    string baseName;
    int basePrice;
    // トッピングごとの状態をフラグで管理している
    bool hasMilk;
    bool hasWhip;
    bool hasSyrup;

public:
    CustomDrink(string name, int price, bool milk, bool whip, bool syrup)
        : baseName(name), basePrice(price),
          hasMilk(milk), hasWhip(whip), hasSyrup(syrup) {}

    int getPrice() const {
        int total = basePrice;
        // トッピングごとの追加料金を計算
        if (hasMilk)  total += 50;
        if (hasWhip)  total += 70;
        if (hasSyrup) total += 30;
        return total;
    }

    string getDescription() const {
        string desc = baseName;
        // トッピングごとの名前を追加
        if (hasMilk)  desc += " + Milk";
        if (hasWhip)  desc += " + Whip";
        if (hasSyrup) desc += " + Syrup";
        return desc;
    }
};
```

トッピングの有無を `hasMilk` / `hasWhip` / `hasSyrup` の3つのフラグで保持します。`getPrice()` は各フラグを `if` で見て追加料金を足し、`getDescription()` は各フラグを見て表示名にトッピング名を足します。**トッピングの種類・価格・表示名を、このクラスがすべて直接持っています。**

```cpp
// 1件分の注文を表示する（mainから呼ぶ表示ヘルパー）
void showOrder(MenuDatabase& db, const string& itemId,
```

### 2-1：変わりそうな仕様の見当をつける

変わりそうな仕様は、1-3のクラス図の中心 `CustomDrink` の `getPrice()` / `getDescription()` の中にあります。トッピングごとの価格・表示名・組み合わせを、どんな仕様が、誰の何をきっかけに変わりそうかと一緒に整理します。

| 変わりそうな仕様 | 所在（クラス・メソッド） | 変える主体・きっかけ | 変わりやすさの見立て |
|---|---|---|---|
| トッピングの種類 | `CustomDrink` のフラグと両メソッドの分岐 | 商品企画部の毎月のキャンペーン | 高い |
| トッピングの追加価格 | `getPrice()` 内の `total += ...` | 料金・プロモーション管理の価格改定 | 高い |
| 表示名とその並び順 | `getDescription()` 内の `desc += ...` | 店舗オペレーション部の運用見直し | 高い |
| 販売可否（販売停止・在庫切れ） | 注文作成時の可否判定 | 商品/店舗運用の在庫・キャンペーン終了 | 中〜高 |
| 基本価格にオプションを積み上げる骨格 | `getPrice()` の加算の枠組み | ドリンク注文の基本フロー | 低い |

見えてくるのは、**1つの `CustomDrink` の中で、トッピングの種類・追加価格・表示名・販売可否という仕様が、商品企画部や店舗オペレーションの都合で変わりやすい**という見立てです。逆に、基本価格にオプションを積み上げるという処理の骨格は、当面変わらない前提に置けます。

ここで見るのは所在だけです。責任の多さや構造の善し悪しは、変更を当てて痛みを観測してから判断します。上の表は、変わりそうな仕様が `CustomDrink` のどのメソッドのどの行にあるかという所在の見立てです。トッピングの知識を1つのクラスにまとめている今の配置が、変更要求を当てたときに**実際に痛みになるか**はフェーズ3で確かめ、なぜ辛いのかはフェーズ4で原因として言語化します。2-1は、その検証対象に当たりをつける段階です。

**CustomDrink（変更あり）**

```cpp
class CustomDrink {
    string baseName;
    int basePrice;
    // 変更ID2：選ばれたトッピングを、選択順にそのまま積む
    vector<string> toppings;
public:
    CustomDrink(string name, int price)
        : baseName(name), basePrice(price) {}

    void addTopping(const string& name) {
        toppings.push_back(name);           // 変更ID2：積むだけ
    }

    int getPrice() const {
        int total = basePrice;
        for (size_t i = 0; i < toppings.size(); ++i) {
            const string& t = toppings[i];
            // 変更ID1：Matcha・Chocoのために分岐を2本足した
            if      (t == "Milk")   total += 50;
            else if (t == "Whip")   total += 70;
            else if (t == "Syrup")  total += 30;
            else if (t == "Matcha") total += 60;
            else if (t == "Choco")  total += 40;
        }
        return total;
    }

    string getDescription() const {
        string desc = baseName;
        for (size_t i = 0; i < toppings.size(); ++i)
            desc += " + " + toppings[i];    // 変更ID2：積んだ順に取り出す
        return desc;
    }
};
```

- **コンストラクタ引数が5個から2個へ：** トッピングは `addTopping()` で後から積む形になりました
- **`getDescription()` が2行に：** 種類ごとの `if` が消えました。積んだ順に読むだけです
- **`getPrice()` の `if` は残り、2本増えた：** 価格の知識は依然として `CustomDrink` の中の1か所に集まっています

順番の管理という変わる理由はクラスから消えましたが、**価格の知識は残りました。**

## 🟠 フェーズ4：原因分析 ―― なぜ辛いのかを構造で言語化する
### 4-1：痛みの根源を探る（観察と原因）

フェーズ3では、種類を足すたびに価格の分岐を開くこと、その足し忘れが金額の食い違いになること、種類名のつづり違いが素通りすること、販売可否の置き場所がクラスに無いことの4つの痛みを確認しました。入力順は素直な変更で解けたので、残ったのはこの4つです。この痛みがなぜ発生するのか、コードを注意深く観察することで根源が見えてきます。

第一に、新しいトッピングを追加するとき、なぜ毎回 `CustomDrink` を開かなければならないのでしょうか。それは、このクラス自身が「ミルクなら50円」「ホイップなら70円」といった具体的なトッピングの条件をすべて直接知ってしまっている（抱え込んでいる）からです。

第二に、なぜ変更の影響範囲が読めず、呼び出し側まで壊れるのでしょうか。それは、「基本ドリンクの価格を保持する」という変わらない骨格と、「各トッピングの価格と名前を知っている」というビジネスロジックが、同じクラスの同じメソッドの中で物理的に混ざり合っているからです。

この「症状（痛み）」と「根本原因」を整理すると、以下のようになります。

| **観察した症状** | **構造的な原因** |
|---|---|
| トッピングを追加するたびにクラス内の複数の `if` 文を探して修正が必要になります | `CustomDrink` が各トッピングの価格・名前という具体的な条件を直接知っているから |

### 4-2：変わるもの/変わってほしくないもの

> **「変わらないもの」と「変わってほしくないもの」は異なります。** 「変わらないもの」は経験的事実（今まで変わっていない）、「変わってほしくないもの」は設計意図（ここを安定させてほかを守りたい）です。ここで整理するのは後者です。

原因の方向性が見えたところで、「変わり続けるもの」と「変わってほしくないもの」を明確に切り分けてみましょう。ここをしっかり整理することが、後で適切に分けるための土台になります。

| **変わり続けるもの** | **変わってほしくないもの** |
| --- | --- |
| トッピングの種類、それぞれの追加価格、表示名、販売可否、表示順 | 基本となるドリンクの価格を保持し、注文で選ばれたオプションを順に重ねて合計金額と注文内容を返すという処理の骨格 |

**【変わる部分（変わり続けるif文と価格・名前の知識）】** `CustomDrink::getPrice()` の中で、トッピングごとの加算を並べている部分です。
```cpp
    if (hasMilk)  total += 50;  // ← 商品企画部の判断で変わる
    if (hasWhip)  total += 70;  // ← 商品企画部の判断で変わる
    if (hasSyrup) total += 30;  // ← 商品企画部の判断で変わる
```

**【変わってほしくない部分（守りたい骨格）】** 同じ `CustomDrink::getPrice()` の中で、基本価格から合計を組み立てている部分です。
```cpp
    int total = basePrice;
    // ここにトッピングの処理が入る
    return total;
```

トッピングに関する情報は、商品企画部や店舗オペレーションの都合で今後も変わり続けます。価格だけでなく、販売停止・在庫切れの判定、スタッフが確認する表示順、「ホイップをダブルにする」といった組み合わせも変化の対象です。

一方で、ベースとなる飲み物にオプションを足していくという計算の大枠自体は、この章の変更要求では守りたい前提です。この「後から増える側」をうまくカプセル化できれば、「守りたい側」を安定させやすくなります。

### 4-3：接続点に漏れているトッピングの知識を確認する

現在のシステムで、基本ドリンクとトッピングの境界にどの知識が漏れているかを確認します。

`CustomDrink`の中には、`"Milk"`なら50円、`"Whip"`なら70円という種類名と価格の対応が並んでいます。基本ドリンク側が、追加できるトッピング名、価格、説明の作り方まで知っている状態です。ここへ販売停止や在庫切れの判定を足すと、基本ドリンク側が「このトッピングを注文へ重ねてよいか」まで抱えることになります。

新しいトッピングが来るたびに、`CustomDrink`へ条件分岐を追加する必要があります。接続点で本当に必要なのは「注文へ重ねてよいトッピングを、選択順に価格と説明へ反映すること」ですが、トッピングの種類と価格の知識が基本ドリンク側へ残り、販売可否と種類名の正しさは呼び出し側へ漏れています。

一つの考え方として、基本となるドリンクの役割と、後から追加されるトッピングの役割は、変わる理由が異なるという点が重要です。これらが一つの場所に混在していることが、今回の痛みの根本につながっています。

フェーズ4で根本原因が言語化できました。「どこを分けるか」は明確です。次のフェーズ5では、その境界で実際に何が流れているかを値・型のレベルで具体化し、「何を変え、何を守るか」を明確にします。

> **📌 原因（確定）**
> `CustomDrink`が各トッピングの名前と価格を種類名の分岐として知っている。トッピングを1種類足すたび、基本ドリンクのクラスまで修正する必要がある。そしてトッピングを表す型が無いため、種類名の正しさと販売可否は呼び出し側の注意力に委ねられている。

## 🟡 フェーズ5：課題定義 ―― 原因から課題を検討して確定する

### 5-1：原因から課題候補を洗い出す

| 原因ID1：一つの注文クラスが全トッピングの価格を種類名で分岐し、トッピング自体を表す型が無い | 種類の追加が同じクラスへ集中し、種類名の誤りも分岐の漏れも実行時まで気づけない | トッピングごとの価格・説明を独立した部品へ分離する | 各トッピングは独立して追加・停止される |

### 課題ID1を6段で解く

**【課題の原因】** 問題ID1・問題ID2・問題ID3（種類を足すたび価格の分岐を開き、つづり違いも分岐の足し忘れも実行時まで止まらない）＝原因ID1（基本骨格とトッピングの知識が `CustomDrink` に同居し、トッピングを表す型が無い）。問題ID4（販売可否が呼び出し側の責任になった）＝原因ID2（販売可否の確認を受け取る場所が契約に無い）。この2つの原因が課題ID1へ集約されます。

**この課題（何を解きたいか）：** トッピングを1種足すたび、注文クラスを開いて種類名の分岐を1本足すことになります。足し忘れても、つづりを間違えても、実行時まで止まりません。そして販売停止のトッピングを断る判断が、注文を組み立てる呼び出し側へ残っています。**販売可能な部品だけを入力順に重ね、種類の追加を新しい部品と登録だけに閉じる**ようにするのが課題ID1です。

**どう解決するか（方針）：** 基本ドリンクと追加機能を同じ契約にそろえ、追加機能は内側の1つを包んで自分ぶんだけを足す形にして、包む順で組み合わせを表します（装飾連結構造＝Decorator）。

**この章の課題は1つですが、進め方は課題が複数の章と同じです。** 前半3段（契約・安定骨格・具体）は分ける対象ごと、後半3段（生成・注入・利用開始）は共通で決める——という形は、課題の数によらず変わりません。5-2で候補を2つ挙げて1つの接続点へ統合したのも、部品だけ分けても組み立てが利用側へ残るからでした。

| 段 | 何を決めるか | 軸ごとか |
|---|---|---|
| 1【契約】 | 分けるかを決め、境界に何が渡るかを決める | 軸ごと |
| 2【安定骨格】 | 呼ぶのは、変わらない側 | 軸ごと |
| 3【具体】 | 契約の裏を埋める | 軸ごと |
| 4【生成】 | 実体を作り、持つ人を決める | **共通** |
| 5【注入】 | 実装が骨格へ入る | **共通** |
| 6【利用開始】 | 結果として、呼び方はこうなった | **共通** |

**出発点。** やることはもう決まっています。注文の骨格から、種類ごとの追加料金・表示名・販売可否を分けることです。分ける対象も5-3で決まっています。まだ決まっていないのは、**分けた後にどう繋ぐか**だけです。

書き換える前のコードは3-1にあります。**ここで全部を再掲することはしません。** 各段で、その段が触る数行だけを3-1から抜き出し、変更後と並べます。

---

**1. 分けるかを決め、境界に何が渡るかを決める 【契約】**

**まず、分けないで済まないかを確かめます。** 5-3が確定したのは「この接続点を解く」ことであって、「クラスを増やす」ことではありません。次の2つがどちらも成り立つなら、契約を作らず、条件表を外へ出すだけで止めます。

1. 変わる側の判断が、コード上1か所にしか現れない
2. その種類が増える見込みが、2-4のリスクIDにも5-2の評価にも挙がっていない

**この章では、1つ目は成り立ちます。** 3-1で `getDescription()` の分岐は消えたので、種類名で分ける判断は `getPrice()` の1か所だけです。**しかし2つ目が成り立ちません。** 2-4のリスクID1（種類の増減）とリスクID2（価格改定）が、どちらも「変わり続ける」と言っています。**現に変更ID1で、MatchaとChocoの2種類が増えました。** 両方が成り立つときだけ止められるので、契約まで進みます。

**もう1つ理由があります。** 原因ID2の「販売可否の確認を受け取る場所が契約に無い」は、条件表を外へ出しても残ります。表を引くのは結局呼び出し側で、確認せずに積む経路を止められません。

**ただし、この章では「契約を作らず、種類ごとの値をデータの表として持つ」案が、途中状態ではなく完成案として残ります。** 6段を解き終えた後の「システム全体の最終構造を決める」で、その案と並べて判断します。ここでは、種類が現に増えたという事実を根拠に契約へ進みます。

分けると決めたので、コードに線を引きます。

**掲載箇所：`CustomDrink::getPrice()`** ―― 3-1の合計金額（対策前）

```cpp
    int getPrice() const {
        int total = basePrice;                     // ← 変わらない側（合計の始め方）
        for (size_t i = 0; i < toppings.size(); ++i) {
            const string& t = toppings[i];         // ← 変わらない側（積んだ順に読む）
            if      (t == "Milk")   total += 50;   // ← 変わる側（種類と追加料金）
            else if (t == "Whip")   total += 70;   // ← 変わる側
            else if (t == "Syrup")  total += 30;   // ← 変わる側
            else if (t == "Matcha") total += 60;   // ← 変わる側
            else if (t == "Choco")  total += 40;   // ← 変わる側
        }
        return total;                              // ← 変わらない側
    }
```

**割り方の根拠は、種類が増えたときに触るかどうかです。** 種類を1つ足すと `if` の連鎖は1本増えますが、外側の4行（合計の始め方・積んだ順に読むこと・返すこと）は1行も増えません。変更前のコードでは、この2種類が同じ関数の中で入れ子になっています。

**5-3の接続点定義表が挙げているのは、境界を跨ぐ「候補」です。実際に何がいくつ流れるかは、この段で形を決めた結果として決まります。**

**5-3が挙げた候補は5つです。** トッピングID、選択順、販売状態、価格、説明。1つずつ形を決めます。

| 接続するもの（5-3の候補） | 決めた形 | そう決めた理由 |
|---|---|---|
| トッピングID | 引数で渡さない。**種類ごとに別のクラス**を用意し、そのクラスであること自体が種類を体現する | 引数で渡すと、受け取った側がまた種類で分岐する。上の `if` 連鎖が移動するだけになる |
| 選択順 | 引数で渡さない。**重ねた順序そのもの**が並び順を表す | 順番号を渡すと、受け取った側が並べ替えを持つ。順序の管理は3-1でクラスから消えたのに、また戻ってくる |
| 販売状態 | **この境界を流れない。** 部品を作る前に確かめる別の場所で扱う | 契約へ載せると、基本ドリンクにも販売可否の操作が要る。守る側の「基本ドリンクが価格と説明を返す契約」が崩れる |
| 価格 | 合計金額（`int`）を**戻り値で返す** | 変更前の `getPrice()` が返していた値そのもの |
| 説明 | 注文名称（`string`）を**戻り値で返す** | 変更前の `getDescription()` が返していた値そのもの |

**候補は5つでしたが、境界を実際に流れるのは2つです。** トッピングIDと選択順は「クラスそのものが体現する」「重ねた順序が表す」と決めたので、引数にも戻り値にもなりません。**消えたのではなく、値として渡す代わりに構造で表すことにしたのです。** 販売状態は5-3の守る側「基本ドリンクが価格と説明を返す契約」に照らして、この境界から外しました。残る価格と説明の2つが、戻り値として流れます。

**候補の数と実数が一致しないのが普通です。** 5-3は境界を跨ぐものを漏れなく挙げる表で、この段はそれを形へ変える段です。形を決めれば、値として流れなくなるものが出ます。

**「返す情報の使い道を、まだ決めていないのに形を決めてよいのか」** ——根拠は変更前のコードにあります。3-1の `main()` が消費していたのは `getPrice()` の `int` と `getDescription()` の `string` の2つだけでした。**将来こう使うだろうという見込みではなく、変更前が実際に消費していたものを、そのまま契約の戻り値にしています。**

**契約を置く場所も、ここで決められます。** 5-3の完了状態が「基本ドリンクとトッピングを同じ注文契約で扱う」と言っている以上、**契約を満たすものが2種類（基本と追加機能）あることは前工程で決まっています。** 契約をどれか1つの基底クラスの内側へ置く形は、その基底を継いだものだけが契約を満たす形なので、もう一方が満たせません。だから独立した型として置きます。**この判断が骨格と噛み合うかは、2で確かめます。**

```cpp
// 課題ID1接続点：基本ドリンクと追加機能が満たす共通契約
class IDrink {
public:
    virtual ~IDrink() = default;
    virtual int getPrice() const = 0;
    virtual string getDescription() const = 0;
};
```

境界を流れると決めた2つが、そのまま2つの操作になりました。引数は1つもありません。

**契約だけでは、決めた形が本当に成立するのか確かめられません。** 実装を1つ見ます。まず基本ドリンク側です。

```cpp
// 基本のドリンク：自分の名前と基本価格だけを持つ
class Coffee : public IDrink {
    string name;
    int basePrice;
public:
    Coffee(const string& itemName, int price)
        : name(itemName), basePrice(price) {}
    int getPrice() const override { return basePrice; }
    string getDescription() const override { return name; }
};
```

- **「トッピングIDを引数で渡さない」の実態。** `getPrice()` に引数がありません。基本ドリンクはトッピングの種類を1つも知らないまま、自分の価格を返せます
- **「選択順を引数で渡さない」の実態。** 並び順を受け取るメンバーも引数もありません。基本ドリンクは常に連なりの内側の端にいます
- **「価格と説明を返す」の実態。** `basePrice` と `name` の2つだけを返します。合計でも連結後の名称でもなく、自分ぶんです

変更前の `CustomDrink` にあった `if` 連鎖と、種類ごとの加算が、ここにはありません。**では、追加ぶんを足すのは誰の仕事になるのか。それは2で決めます。**

```mermaid

    class Coffee
    IDrink <|.. Coffee

    classDef focus fill:#FFF2CC,stroke:#D6B656,stroke-width:2px
```

契約と、それを満たすものが1つだけ描けました。**追加機能側の箱がまだありません。** この段で決めたのは契約の形だけで、誰が重ねるかは決めていないからです。基準の図にある `MenuDatabase`・`MenuItem` は、この段では変わりません。

**この段の守る範囲の照合：** 4つのうち「注文が返すもの」に触りました。契約が返すのは注文名と合計金額の2つで、守る範囲で挙げた2つと同じです。返すものを増やしても減らしてもいないので、範囲内です。基本ドリンクの選び方・合計の出方・入力順の意味には触っていません。

**では、この契約を誰が呼ぶのか。**

---

**2. 呼ぶのは、変わらない側 【安定骨格】**

呼べるのは、種類が増えても変わらない側だけです。出て行った側が出て行った側を呼べば、種類が増えるたびに両方を触ることになり、分けた意味が消えます。

**変わらない側には2つの型があります。どちらなのかを、ここで見分けます。**

| 型 | 骨格の正体 | 契約の置き場 | 見分け方 |
|---|---|---|---|
| **残った側** | 分岐を外した後に残った手順 | 骨格とは**別のクラス** | 同じ実行の途中で相手が入れ替わる |
| **取り出した順序** | 変更前から存在していた共通手順 | 骨格と**同じクラス**（基底クラスの内側） | 実体を作った時点で相手が決まる |

**この章は、どちらの型にも当てはまりません。** 順に当ててみます。

**見分け方で当てると、下の型です。** 追加機能の実体を1つ作った時点で、その内側は決まります。`getPrice()` を何度呼んでも相手は入れ替わりません。実行の途中で相手が差し替わる第9章型ではありません。

**しかし契約の置き場は、下の型が言う「骨格と同じクラス」になりません。** 1で確かめたとおり、基本ドリンクも同じ契約を満たす必要があります。基本ドリンクは追加機能ではないので、追加機能の基底クラスを継げません。契約を基底の内側へ置くと、基本ドリンク側が契約から外れます。**置き場は、上の型と同じ「骨格とは別のクラス」になります。**

**骨格の正体も、どちらの説明とも合いません。** 上の型の「分岐を外した後に残った手順」を当てると、3-1の `getPrice()` から種類の分岐を外して残るのは `int total = basePrice;` と `return total;` ですが、それは1で `Coffee::getPrice()` へ行きました。下の型の「変更前から存在していた共通手順」を当てると、3-1に「内側へ委譲して自分ぶんを足す」という手順はありません。ループの1周ぶんに当たる形ですが、委譲としては変更前に存在していません。

**そこで、この章の骨格を定義します。** この章の骨格は、**「1段ぶんの重ね方」**です。内側へ同じ契約で尋ね、返ってきた値へ自分ぶんを1つだけ足して返す——この2行が骨格です。種類が何種類増えても、何段重なっても、この2行は変わりません。

**置き場を決める基準も、2型の見分け方とは別のものになります。** この章で効く基準は「**骨格の相手が、骨格自身になりうるか**」です。追加機能の内側は、基本ドリンクのこともあれば別の追加機能のこともあります。骨格自身が相手の位置に立てる以上、契約は骨格の外の独立した型でなければ、骨格が自分を相手として持てません。**第9章（実行の途中で相手が入れ替わるから外）でも第4章（実体を作った時点で決まるから内）でもない、第3の理由です。**

**骨格を置くクラスに名前を付けます。** 持たせるのは「1段ぶんの重ね方」だけで、種類固有の値は1つも持ちません。内側を包む仲介そのものなので `ToppingWrapper` とします。

**掲載箇所：`ToppingWrapper`（クラス宣言・この段で分かるところまで）**

```cpp

public:
    int getPrice() const override {
        return baseDrink->getPrice() + myPrice();   // ←この myPrice() が未定
    }
    string getDescription() const override {

             + " + " + myLabel();                   // ←この myLabel() も未定
```

**穴が2つ空きました。名前は仮です。** `myPrice()` と `myLabel()` は、自分ぶんの追加料金と表示名を得るところに付けた名札で、まだ実体がありません。

- **なぜ書けないか。** ここへ `50` や `"Milk"` を直接書くと、骨格が種類ごとの値を知ることになります。1で「種類ごとに別のクラス」と決めた意味が消えます
- **どの段で決まるか。** 値をどこから読むかは4で決めます
- **安定側の名前を書けない理由。** 骨格に種類名を書いた時点で、種類を1つ足すたびに骨格を開くことになります。それは分ける前と同じです
- **`baseDrink` も未定です。** 包む相手をどこから受け取るかは、実体を作る人が決まってからでないと書けません

**宣言も、ここまでで止めます。** コンストラクタはまだ書きません。誰が何を渡すかが決まっていないからです。

**ここで検算します。種類を1つ足したとき、この2行は変わるか。** 変わりません。段を1つ増やしても、外側から見れば「内側へ尋ねて自分ぶんを足す」1回が増えるだけで、この2行は同じです。**穴が空いたままでも、この検算はできます。** 変わってしまうなら割り残しがあるので、1へ戻って線を引き直します。

**変更前の `CustomDrink` は、どこへ行ったのか。** 1-3のクラス一覧では、その役割を「ドリンク1注文の全情報を保持し、合計金額と注文名称を返す」と書きました。内訳は4つです。基本ドリンク名と基本価格の保持は1で `Coffee` へ、トッピングの保持は包んだ連なりそのものへ、合計金額と注文名称を返すことは `IDrink` の2操作へ移りました。**4つとも移った結果、名前を据え置く先が残りません。** 改名ではなく、役割が分かれた結果としてこのクラスが無くなります。責任が変わっていないのに名前だけ変えることはしませんが、ここは責任のほうが残っていません。

**この段の守る範囲の照合：** 「合計の出方」に触りました。ただし触ったのは置き場所だけで、「基本価格から始めて1要素につき1回だけ足す」という規則は変えていません。「入力順の意味」にも掛かります。この2行が固定したのは「内側の表示名が先、自分ぶんが後」という並べ方だけで、先に重ねたものが先に出るという関係は保たれています。包む順と利用者の入力順を対応づけるのは4なので、そこでもう一度照合します。基本ドリンクの選び方・注文が返すものには触っていません。

**では、契約の裏は誰が埋めるのか。**

**3. 契約の裏を埋める 【具体】**

契約と、それを呼ぶ骨格が決まりました。1では基本ドリンク側の実装を1つ見て、渡すもの・返すものを確かめました。**ここで追加機能側を埋めます。**

具体の個数は1で決まっています。「種類ごとに別のクラス」と決めた時点で、3-1の `if` 連鎖の5分岐がそのまま5クラスになります。**この段が決めるのは、各具体が何を書かないかです。**

**掲載箇所：`Milk`（クラス全体）** ―― 代表として1つ見ます

**`getPrice()` も `getDescription()` もありません。** 上書きしないので、2で書いた骨格の2行がそのまま動きます。**このクラスが書いているのは、自分がどの種類かを名乗る1つの文字列だけです。** 変更前は「`t == "Milk"` なら50を足す」という条件と結果の組で表していたものが、条件が消えて識別子だけになりました。条件が要らないのは、**このクラスであること自体が『ミルク』だから**です。

**4. 実体を作り、持つ人を決める 【生成】**

**2で穴が2つ空きました。** 自分ぶんの追加料金・表示名の出どころ（`myPrice()`／`myLabel()`）と、包む相手（`baseDrink`）です。この段では、まず値の出どころ、次に実体を作る人、最後に所有と生存期間を決めます。

**値をどこへ置くか。箱は部品ごとか、1つか。**

- **部品ごとに持つ。** `Milk` に `50` と `"Milk"` を書く。作るのは簡単ですが、価格改定（リスクID2）のたびにクラスを開きます。そして販売可否（要求ID3）は部品を作る前に確かめたいのに、部品の中にあると作らないと読めません
- **1つの保存データへ寄せる。** 種類を1つ足すときに触るのは、部品クラス1つと登録1行。価格改定は登録値だけ。販売可否は部品を作る前に読めます

**1つへ寄せる形を採ります。** 判断の基準は「種類を1つ足したとき、価格を1つ変えたときに触る場所」です。3で確認した完了条件が「新部品と登録に閉じる」と言っている、その「登録」がこの保存データです。**名前は `ToppingCatalog` とします。** 表示名・追加料金・販売可否の3つを、トッピングIDごとに持ちます。

```cpp
// トッピングの表示名・追加料金・販売可否を保持する保存データ（境界）
struct ToppingSpec {
    string label;   // 表示名（スタッフ向け作業指示に使う）
    int price;      // 追加料金（円）
    bool onSale;    // 販売可否（販売停止・在庫切れはfalse）
};

class ToppingCatalog {
private:
    map<string, ToppingSpec> specs;
public:
    ToppingCatalog() {
        specs["Milk"]         = {"Milk",   50, true};
        specs["Syrup"]        = {"Syrup",  30, true};
        specs["Whip"]         = {"Whip",   70, true};
        specs["Matcha"]       = {"Matcha", 60, true};
        specs["Choco"]        = {"Choco",  40, true};
        specs["SeasonalMint"] = {"SeasonalMint", 80, false};
    }
    bool exists(const string& id) const { return specs.count(id) > 0; }
    bool onSale(const string& id) const {
        auto it = specs.find(id);
        return it != specs.end() && it->second.onSale;
    }
    int priceOf(const string& id) const { return specs.at(id).price; }
    string labelOf(const string& id) const { return specs.at(id).label; }
};
```

**中身は3つに分かれます。**

- **メンバー：** トッピングIDから `ToppingSpec` を引く1つの表です。3-1で `getPrice()` の `if` 連鎖にあった数値と、`ToppingSale` が別に持っていた停止リストが、ここで1つの表に合流しました
- **`exists()`／`onSale()`：** 部品を作る前に読める2つの問い合わせです。原因ID2の「販売可否の確認を受け取る場所が契約に無い」に対して、確認する相手をここに置きました
- **`priceOf()`／`labelOf()`：** 2で穴だった `myPrice()`／`myLabel()` の行き先です。**種類を1つ足すときに触るのは、この表への登録1行だけです**

**穴の1つが埋まりました。** 骨格の2行は次のようになります。

**掲載箇所：`ToppingWrapper`（クラス宣言・完成）**

```cpp
// 変わる部分を繋ぐ仲介役：トッピングの基底クラス

protected:
    IDrink* baseDrink;             // 中身（基本ドリンクや他のトッピング）

    string toppingId;              // 自分がどのトッピングか

    int getPrice() const override {
```

**2で仮に置いた `myPrice()` が `catalog->priceOf(toppingId)` に、`myLabel()` が `catalog->labelOf(toppingId)` になりました。** 骨格の形——内側へ尋ねて自分ぶんを1つ足す——は1行も変わっていません。変わったなら、2の切り方を間違えていたことになります。

**次に、具体を誰が作るか。** 持つ者の条件は2と3から分かっています。

- **具体クラスを全部知っていること。** `new Milk(...)` と書く以上、その名前を知っていなければなりません
- **骨格ではないこと。** 骨格が具体の名前を知った時点で、1で分けた意味が消えます

**この2つを満たす場所を、組み立て役として新しく置きます。名前は `OrderAssembler` です。** 5-2で「順序・販売状態を含む組み立ての分離」を課題ID1へ統合したので、検証と生成と連結を同じ場所が引き受けます。トッピングIDは名前付き定数（`ToppingId`）にして、直文字列の打ち間違いが分岐へ紛れ込まないようにします。

**掲載箇所：`OrderAssembler::wrapOne(const string&, IDrink*)`** ―― トッピングID1つを、内側のドリンクへ1層かぶせる

```cpp
    if (id == ToppingId::Syrup)  return new Syrup(base, &catalog);
    if (id == ToppingId::Whip)   return new Whip(base, &catalog);
```

**具体クラスの名前を知っているのは、この関数だけです。** 3-1では種類名の分岐が価格の計算そのものでしたが、ここでは部品を1つ作るだけです。種類を1つ足すときに触るのは、この関数へ1行と、`ToppingCatalog` の登録へ1行です。

**入力順に重ねる責任も、この組み立て役が持ちます。** 骨格は「1段ぶんの重ね方」しか知らないので、何段を何の順で重ねるかは骨格の外で決まります。要求の並びをそのままループの順にすれば、包む順が入力順になります。

**掲載箇所：`OrderAssembler::assemble(const OrderRequest&)`** ―― 検証してから、選択順に重ねる

```cpp
OrderResult OrderAssembler::assemble(const OrderRequest& req) {
    if (!db.exists(req.baseItemId)) {
        return {false, "", 0,
                "メニューID " + req.baseItemId + " は存在しません"};
    }
    // 手順1：全トッピングの登録と販売可否を先に確認する
    for (const auto& toppingId : req.toppingIds) {
        if (!catalog.exists(toppingId)) {
            return {false, "", 0,
                    "トッピング " + toppingId + " は未対応です"};
        }
        if (!catalog.onSale(toppingId)) {
            return {false, "", 0, "トッピング " + toppingId
                    + " は販売停止または在庫切れです"};
        }
    }
    // 手順2：検証を通ったので、選択順に基本ドリンクへ重ねる
    MenuItem base = db.get(req.baseItemId);
    IDrink* drink = new Coffee(base.name, base.basePrice);
    for (const auto& toppingId : req.toppingIds) {
        drink = wrapOne(toppingId, drink);
    }
    OrderResult r{true, drink->getDescription(),
                  drink->getPrice(), ""};
    delete drink;
    return r;
}
```

**手順1と手順2の順序に意味があります。** 全件を先に確認し、それから生成へ進みます。逆にすると、途中で拒否したときに生成済みの層が宙に浮きます。**これで「販売可能な部品だけを入力順に重ね」という完了条件の前半が埋まりました。** 呼び出し側は確認を書きません。

**その持ち主自身は、誰が作り、誰が持つのか。** ここまで答えないと「生成」に答えたことになりません。

**この章は2つ目です。** 決め手は「誰を渡したか」で、組み立て時に1回決まります。次の表で、それが実際にどこで決まるかを追います。

| 軸 | 実装が決まる決め手 | 決め手の出どころ | 入る場所 |
|---|---|---|---|

**決め手が「組み立て時に1回」であることを、この章の言葉で確かめます。** `Milk` の実体を1つ作ると、その `baseDrink` はもう変わりません。`getPrice()` を何度呼んでも、同じ相手へ尋ねます。第9章のように保存済みデータを見て呼び出しごとに引き当てる形とは、ここが違います。

**この段で押さえることは4つです。**

1. **何が入るか。** 内側のドリンク1つです。基本ドリンクのこともあれば、1つ前に作った別のトッピングのこともあります
2. **誰が入れるか。** `OrderAssembler::wrapOne()` です。骨格ではありません
3. **骨格が何を知らないままか。** `ToppingWrapper::getPrice()` は、内側が `Coffee` なのか `Milk` なのかを最後まで知りません。何段目にいるのかも知りません

**この章のコンストラクタは、2種類のものを同時に運んでいます。** そこを分けておきます。

| 何が入るか | 決め手 | 入る瞬間 | 課題ID1の分離か |
|---|---|---|---|
| 内側のドリンク（`IDrink*`） | `wrapOne()` が第2引数に何を渡したか | `new Milk(base, &catalog)` の第1引数 | **そう。これが課題ID1** |

**同じ1行が、上の行では「包む相手を渡すこと」、下の行では「読む先を貸すこと」として働いています。** 種類を1つ足したときに増えるのは上だけで、下はどの部品でも同じ1つを指します。

**骨格が保存データへ届く方法は、注入とは別の話です。** 4で借用の参照と決めましたが、仮に部品が自分で表を持ったとしても、内側のドリンクが `baseDrink` へ入ることは変わりません。

| 7. 【契約】 | `IDrink::getPrice()` | 内側の実体（トッピングでも基本ドリンクでもよい）へ動的ディスパッチする | `Milk::getPrice()`／`Coffee::getPrice()` |
| 8. 【具体】 | `Coffee::getPrice()` | 400を返して連なりを折り返す。外側で50、30が順に足される | 外側の【安定骨格】へ戻る |

**【注入】が2回現れています。** 装飾は重ねた段数だけ内側を持つので、注入も段数ぶん起きます。ただし**どれも組み立て時に1回きり**で、`getPrice()` を何度呼んでも相手は変わりません。第9章のように呼び出しごとに引き当てる形とは、ここが違います。

**6〜8が同じ経路を2周します。** `Syrup` の骨格が `Milk` を呼び、`Milk` の骨格が `Coffee` を呼びます。**骨格が骨格を呼べるのは、骨格自身が契約を満たしているからです。** 2で置き場を独立した型にした判断が、実行経路でも確認できます。

```cpp
// 変わる部分を繋ぐ仲介役：トッピングの基底クラス
class ToppingWrapper : public IDrink {
protected:
    IDrink* baseDrink;             // 中身（基本ドリンクや他のトッピング）
    const ToppingCatalog* catalog; // 価格・表示名の保存データ
    string toppingId;              // 自分がどのトッピングか
public:
    ToppingWrapper(IDrink* base, const ToppingCatalog* cat,
                   const string& id)
        : baseDrink(base), catalog(cat), toppingId(id) {}
    ~ToppingWrapper() override { delete baseDrink; }
    int getPrice() const override {
        // 価格は自分で持たず、カタログ（保存データ）から読む
        return baseDrink->getPrice() + catalog->priceOf(toppingId);
    }
    string getDescription() const override {
        return baseDrink->getDescription()
             + " + " + catalog->labelOf(toppingId);
    }
};
```

`ToppingWrapper` が「中に別のドリンクを包む」仕組みを提供します。具体的なトッピングはこのクラスを継承するだけで済みます。

注文は `OrderRequest`（基本ドリンクIDと、選択順のトッピングID列）という要求オブジェクトで表します。どの種類をどの順で重ねるかは `new Whip(new Milk(...))` のような入れ子ではなく、要求データとして持ちます。`OrderResult` は注文名・金額、または失敗理由を返します。

```cpp
// 注文要求：基本ドリンクIDと、選択順のトッピングID列をデータで持つ
struct OrderRequest {
    string baseItemId;
    vector<string> toppingIds;
};

// 注文結果（結果オブジェクト）：成功可否・注文名・金額・エラー理由
struct OrderResult {
    bool ok;
    string description;
    int totalPrice;
    string error;
};

```

`OrderRequest` は基本ドリンクIDとトッピングの並びをデータで表し、`OrderResult` は成功可否・注文名・金額・エラー理由を返します。

**OrderAssembler::wrapOne()**

トッピングID1つを、内側のドリンクへ1層かぶせます。

```cpp
IDrink* OrderAssembler::wrapOne(const string& id, IDrink* base) {
    if (id == ToppingId::Milk)   return new Milk(base, &catalog);
    if (id == ToppingId::Syrup)  return new Syrup(base, &catalog);
    if (id == ToppingId::Whip)   return new Whip(base, &catalog);
    if (id == ToppingId::Matcha) return new Matcha(base, &catalog);
    if (id == ToppingId::Choco)  return new Choco(base, &catalog);
    return base;
}
```

**具体クラスの名前を知っているのは、この関数だけです。** 判定は `ToppingId` の名前付き定数で行うので、直文字列の打ち間違いを防げます。トッピングを追加するときに触るのは、ここと `ToppingCatalog` の登録です。

**OrderAssembler::assemble()**

```cpp
OrderResult OrderAssembler::assemble(const OrderRequest& req) {
    if (!db.exists(req.baseItemId)) {
        return {false, "", 0,
                "メニューID " + req.baseItemId + " は存在しません"};
    }
    // 手順1：全トッピングの登録と販売可否を先に確認する
    for (const auto& toppingId : req.toppingIds) {
        if (!catalog.exists(toppingId)) {
            return {false, "", 0,
                    "トッピング " + toppingId + " は未対応です"};
        }
        if (!catalog.onSale(toppingId)) {
            return {false, "", 0, "トッピング " + toppingId
                    + " は販売停止または在庫切れです"};
        }
    }
    // 手順2：検証を通ったので、選択順に基本ドリンクへ重ねる
    MenuItem base = db.get(req.baseItemId);
    IDrink* drink = new Coffee(base.name, base.basePrice);
    for (const auto& toppingId : req.toppingIds) {
        drink = wrapOne(toppingId, drink);
    }
OrderResult r{true, drink->getDescription(),
              drink->getPrice(), ""};
delete drink;
return r;
}
```

- **順序に意味：** 手順1で全トッピングを先に検証し、手順2で初めて生成へ進みます。逆にすると、途中で拒否したときに生成済みの層が漏れます
- **失敗の扱い：** どの検証で落ちても `OrderResult` の `error` に理由を入れ、注文を作りません
- **所有：** `delete drink;` が連鎖の先頭を消すと、`ToppingWrapper` のデストラクタが内側を順に消します

```cpp
        {"DRINK001", {"Milk"}},               // ミルク1種を1個
        {"DRINK001", {"Milk", "Syrup"}}, // ミルク＋シロップ
        {"DRINK001", {"Milk", "Whip"}},  // ミルク＋ホイップ
        {"DRINK001", {"Syrup", "Whip"}}, // 指定順(Syrup→Whip)が表示名に反映
        {"DRINK001", {"Milk", "Syrup", "Whip"}}, // 3種盛り

        {"DRINK001", {"Milk", "Syrup",
                      "Whip", "Matcha"}},
        {"DRINK001", {"Choco"}},              // 追加種類チョコ単体
        // 抹茶＋チョコ混在
        {"DRINK001", {"Milk", "Matcha", "Choco"}},

        {"DRINK001", {"SeasonalMint"}},       // 販売停止トッピング → エラー

        if (res.ok) {
            cout << res.description << " → " << res.totalPrice
                 << "円" << endl;
            log.add(req.baseItemId, res.description,
                    res.totalPrice);

            cout << "エラー：" << res.error << endl;
        }

}
```

### 第0章の3つの設計原則はどう適用されたか

**原則1「変わるものをカプセル化せよ」の現れ**

- 具体化された場所：各トッピングクラス（`Milk`, `Matcha` など）
- 解説：トッピングという「変わる理由」を個別のクラスに分離し、計算ロジックを隠蔽しました。新しいトッピングが追加されても `Coffee` や既存のトッピングクラスは無影響です。

**原則2「実装ではなくインターフェースに対してプログラムせよ」の現れ**

- 具体化された場所：`IDrink` インターフェース
- 解説：呼び出し側は具体クラスを知らず、`IDrink*` というインターフェースを通じて価格や説明を取得するようになりました。`ToppingWrapper` が `IDrink*` 型で内部のドリンクを保持していることが、デコレータの連鎖を可能にしています。

**原則3「継承よりコンポジションを優先せよ」の現れ**

- 具体化された場所：`ToppingWrapper` 内での `IDrink*` 保持
- 解説：「ホットコーヒー + Milk + Whip」を継承で表現しようとすると `MilkCoffee`, `WhipMilkCoffee`, `MilkWhipCoffee` …と組み合わせ爆発が起きます。コンポジション（保持）によって機能を動的に重ね合わせることで、この爆発を防いでいます。

## あなたのコードで考えてみてください

この章で辿った思考プロセスを、あなた自身のコードに当てはめてみましょう。

1. **変動の兆候を探す：** あなたのコードに「機能の組み合わせが増えるたびに、既存クラスを継承した新しいサブクラスを作っている」構造がありますか？
2. **変える理由を問う：** その機能の組み合わせは、どの業務機能に属しますか？コンパイル時に決まるものですか、それとも実行時に動的に変わるものですか？
3. **継承の限界を測る：** トッピングの種類が n 種類になったとき、継承で全組み合わせを表現すると 2ⁿ 個のサブクラスが必要になります。あなたのコードは現実的に管理できる数に収まっていますか？
4. **包んだ後を想像する：** もし「機能を追加する層」をクラスとして独立させると、既存のクラスに触れずに新しい機能を加えられますか？組み合わせの数はどう変わりますか？

**題材を置き換えるときの共通手順**

この章の題材名を、自分の現場のシステム名に置き換えて考えます。

1. そのシステムは、誰が何を達成するために使うものか。
2. 入力、加工、出力は何か。
3. 最近入った変更要求、または次に来そうな変更要求は何か。
4. その変更で、触りたくない場所まで修正や再テストが広がるか。
5. 変えたいものと守りたいものを分けると、接続点には何を残すべきか。
6. 全課題を満たす完成構造が複数成立するか。成立するなら、責任配置・変更影響・導入コストの差は何か。

## パターン解説：Decorator パターン

Decorate（装飾）という名の通り、既存のオブジェクトに「動的に」新しい機能を追加できる構造です。

### パターンの骨格

基本機能を持つオブジェクトを、それと同じインターフェースを持つ「装飾オブジェクト」で包み込むことで、機能を多層的に重ね合わせます。

```mermaid
classDiagram
    class IDrink {
        <<interface>>
        +getPrice()
        +getDescription()
    }
    class ConcreteBeverage {
        +getPrice()
        +getDescription()
    }
    class Decorator {
        -IDrink* base
        +getPrice()
        +getDescription()
    }
    class ConcreteDecorator {
        +getPrice()
        +getDescription()
    }
    IDrink <|.. ConcreteBeverage
    IDrink <|.. Decorator
    Decorator o-- IDrink
    Decorator <|-- ConcreteDecorator
```

### 抽象骨格の実行シーケンス

```mermaid
sequenceDiagram
    participant C as Client
    participant D2 as OuterDecorator
    participant D1 as InnerDecorator
    participant B as Component
    C->>D2: operation()
    D2->>D1: operation()
    D1->>B: operation()
    B-->>D1: 基本結果
    D1-->>D2: 機能1を加えた結果
    D2-->>C: 機能2を加えた結果
```

外側から内側へ同じ契約を呼び、戻りながら各Decoratorの機能を重ねます。

### この章の実装との対応

GoF（Gang of Four）とは、1994年に出版された書籍『Design Patterns』の4人の著者の総称です。彼らが整理した23のパターンは、現在も設計の共通言語として広く使われています。

| GoFの名前 | この章での対応 |
|---|---|
| Component（インターフェース） | `IDrink` |
| ConcreteComponent（基本機能） | `Coffee` |
| Decorator（装飾の基底） | `ToppingWrapper` |
| ConcreteDecorator（具体的な装飾） | `Milk` / `Whip` / `Matcha` 等 |

### 使いどころと限界

- **使うと良い状況：** 実行時に動的に機能を組み合わせたい場合。クラスの継承爆発（`MilkCoffee`, `WhipMilkCoffee`…とクラスが激増する現象）を防ぎたい場合。同じ機能を複数回重ねる（ダブル・トリプル）要件がある場合。
- **使わない方が良い状況：** 組み合わせが全くない、あるいは固定されている場合。単に継承で済む単純な構造に使うと、いたずらにクラスが増えて複雑になります。

### この章のまとめ

コーヒートッピングというドメインと Decoratorパターンの関係を一言で言うなら、基本ドリンクとトッピングが同じインターフェースを共有することで、組み合わせを条件分岐なしに積み重ねられる、ということです。「包む」という構造が成立するのは、包むものと包まれるものが同じ契約を持っているからであって、それこそがこのパターンの核心です。`CustomDrink` がトッピングのフラグを知っていた構造では、組み合わせが増えるたびにクラスを増やすか条件分岐を増やすかしかありませんでした。

7つのフェーズを通じて、読者はトッピングの組み合わせ爆発という観察から始まり、「どの業務機能にトッピングの種類が属するか」の分析を経て、同じインターフェースで包み重ねるという設計へと進みました。フェーズ2のヒアリングで「トッピングの組み合わせは自由に増える」と確認した時点で条件分岐では対処できないことが見え、フェーズ4で基本ドリンクがトッピングの知識を抱えていることを接続点として特定した時点で、「包む」という方向性が定まりました。

あなたのコードの中にも、基本機能にオプション機能を組み合わせるために条件分岐やフラグを使っている箇所があるはずです。「このオプションを自由に組み合わせる必要が来るか」を問うことが、追加機能を重ねられる構造が必要かどうかを判断する入口になります。
