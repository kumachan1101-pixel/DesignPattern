## 第5章 操作をオブジェクトにする ―― Command パターン

―― 思考の型：「操作（アクション）」と「それを実行するロジック」が混在している

### この章の核心

**操作の実行に加えて、履歴、取消、再実行、遅延実行を扱う場面では、依頼する側と実行内容を分け、操作そのものを扱える単位にします。呼び出し元が実行先・メソッド・引数まで知り、操作管理の追加で呼び出し元まで直しているなら、依頼と実行が直結していることが兆候です。操作を共通契約で保持し、実行時点と履歴を呼び出し元から独立させられるかが判断軸になります。**

### この章を読むと得られること

この章の痛みは「やった操作を取り消したい」「操作の履歴を残したい」という要求が来たとき、呼び出し元が処理の詳細を直接知っているために実現できない、という問題です。

* **得られること1：** 「操作の種類」という観点で、ユーザーの指示と処理の実行箇所を識別できるようになる


* **得られること2：** 呼び出し元が個別の処理を直接知っている状態を「依存の過多」と判断できるようになる


* **得られること3：** 操作をオブジェクトに包むことで、操作の履歴保持や取り消しを構造から説明できるようになる


* **得られること4：** 操作を「いつ実行するか」や「取り消すか」を判断する際の、柔軟な設計手法がわかるようになる

## 🔵 フェーズ1：現状把握 ―― 仕様を整理し、システムと紐付ける
この章では、家計簿アプリにおける操作履歴管理を扱います。

家計簿アプリが何を入力として受け取り、どの処理で加工し、何を出力するのかを整理します。

### 1-1：このシステムの仕様

このシステムは、利用者が日々の**収入・支出を記録・管理**するアプリです。利用者が操作種別、カテゴリ、金額を指定すると、登録済みカテゴリと金額を検証し、収入または支出の台帳へ記録します。記録後は残高を再計算し、操作内容と現在残高を表示します。不正入力では台帳と残高を変えません。

#### まず代表入力と実行結果から動きをつかむ

詳細な仕様やコードへ入る前に、1-4の`main()`で利用者が「食費1000円」の支出を1件登録する入力を確認します。

**代表入力（1-4の`main()`から抜粋）：**

```cpp
    // 準備：カテゴリ台帳と画面ボタンを組み立てる
    CategoryDatabase db;
    UIButtons buttons(db);

    // 1回目：カテゴリCAT002（食費）へ 1000円 の支出
    buttons.onAddExpenseClick(1000, "CAT002");

    // 2回目：カテゴリCAT001（給与）へ 5000円 の収入
    buttons.onAddIncomeClick(5000, "CAT001");

    // 3回目：存在しないカテゴリへの支出
    buttons.onAddExpenseClick(500, "CAT999");
```

この入力に対する代表的な実行結果は次のとおりです。

```
支出を追加しました：食費 1000円
現在残高：-1000円
収入を追加しました：給与 5000円
現在残高：4000円
エラー：カテゴリID「CAT999」は存在しません
現在残高：4000円
```

3回続けて実行すると、**残高が前の操作の結果から積み上がっていく**ことが分かります。-1,000円に5,000円が足されて4,000円になり、3回目はカテゴリが存在しないため残高が4,000円のまま変わりません。失敗した操作は残高に触れない、という約束がこの出力に現れています。

この入力と出力から、(1)操作（支出登録）と金額を受け取り、(2)検証→記録→残高計算の順に進み、(3)登録内容と現在残高が表示される、という一連の動きが読み取れます。同じ入力を含む完全なコードと実行結果は1-4に掲載します。

#### 最初にシステム全体をつかむ

- **入力：** 利用者の支出追加または収入追加、カテゴリID、金額を受け取る。
- **処理：** カテゴリと金額を検証し、成功時だけ収入または支出を記録して、収入合計から支出合計を引いた残高を計算する。
- **出力：** 登録結果と変更後残高を返し、不正入力では残高を変えない。
- **掲載コードでの代替：** 画面のボタン操作は `main()` からのメソッド呼び出し、カテゴリDBはメモリ上の登録表、表示は標準出力で表す。検証と残高計算は実際に行う。収支明細を台帳へ保存する仕組みは1-5の変更要求で加わる範囲で、現状コードにはない。

まずこの一連の動きを押さえ、以降で要求、入力と残高規則、画面と保存の境界、クラス、コードの順に詳細を確認します。

#### 現行要求ベースライン

| 要求ID | 現行要求 | 受入条件 |
|---|---|---|
| 要求ID1 | 登録カテゴリへ1円以上の収入を追加する | 収入記録と更新後残高を返す |
| 要求ID2 | 登録カテゴリへ1円以上の支出を追加する | 支出記録と更新後残高を返し、負残高も許可する |
| 要求ID3 | 未登録・種別不一致カテゴリ、1円未満を拒否する | エラー時に記録件数と残高を変えない |
| 要求ID4 | 操作の増減を積み上げた現在残高を表示する | 操作のたびに変更前→変更後の残高を確認できる |

ボタン操作で支出・収入を追加でき、現在の残高（収入合計 − 支出合計）がリアルタイムで表示されます。登録されていないカテゴリIDを指定した場合や、金額が1円未満の場合は、エラーとして受け付けず、残高は変わりません。

この章の残高は銀行口座の利用可能額ではなく、登録済み収入合計から支出合計を引いた収支差額です。開始時は0円で、収入を登録する前に支出を登録すれば負の値になります。残高不足で支出を拒否する仕様はなく、負数は「支出超過」を表す正常な集計結果です。

この章で扱う現状仕様は、次の範囲です。

| 仕様項目 | この章で扱う値 | 具体例 | 何に使うか |
|---|---|---|---|
| 操作 | 支出追加・収入追加 | 食費 1,000円を支出追加、給与 200,000円を収入追加 | 押されたボタンに応じて記録を追加する |
| カテゴリID | 登録済みカテゴリ | CAT002 は食費、CAT001 は給与 | 収入または支出として扱えるカテゴリかを確認する |
| 金額 | 1円以上 | 1,000円、200,000円 | 残高計算に反映する |
| 出力 | 更新後残高またはエラー | 残高 -1,000円、カテゴリ未登録エラー | 正常入力と不正入力の結果を照合する |

ここで確認する対象は、どの入力で残高が変わり、どの入力で止まるかです。

| カテゴリID | 名称 | 種別 |

| CAT001 | 給与 | income（収入） |
| CAT002 | 食費 | expense（支出） |
| CAT003 | 交通費 | expense（支出） |
| CAT004 | 副収入 | income（収入） |

**利用できる操作**

現状の仕様で利用できる操作は、「支出登録」と「収入登録」の2種類です。「業務機能」の列は、どの業務機能に属する知識かを明示するためのものです。UIに表示する操作の追加・削除はプロダクト管理の業務機能によって決まり、その実現方法はシステム開発の業務機能が担う——この2つは変わる理由が異なります。

| 操作 | 処理内容 | 残高への影響 | 業務機能 |
|---|---|---|---|
| 支出登録 | 金額とカテゴリを入力し残高へ負の増減値を反映する | 指定金額だけ減る | UI・表示管理 / プロダクト管理 |
| 収入登録 | 金額とカテゴリを入力し残高へ正の増減値を反映する | 指定金額だけ増える | UI・表示管理 / プロダクト管理 |

現時点で扱う操作は、支出登録と収入登録です。

**エラー条件**

正常系の仕様を一通り確認したうえで、最後に、正常系の登録へ進めない入力を分けて整理します。

| エラー条件 | どこで分かるか | 出力 | 保存・通知などの副作用 |
|---|---|---|---|
| カテゴリIDが登録されていない | カテゴリ確認時 | カテゴリ不存在エラー | 残高変更なし |
| 金額が1円未満 | 金額確認時 | 金額エラー | 残高変更なし |

**現状システムの処理シーケンス**

静的な関係に続けて、正常系（支出登録1件）で各クラスがどの順に呼ばれ何を受け渡すかを時系列で示します。操作ごとの具体の分岐は `UIButtons` の注記に、エラー系はメモとして添えます。現状では支出・収入の登録だけを扱います。1-4の現状コードを読む前の地図です。

```mermaid

    participant UI as UIButtons
    participant EM as ExpenseManager
    participant DB as CategoryDatabase

    EM->>DB: exists(category)
```

**この章での簡略化**

`UIButtons`という名前でも、実際の画面やボタン部品を生成しているわけではありません。クラス名から実装済みと誤解しないよう、現状コードが実際に行うこと、代替すること、扱わないことを分けます。

| 実システムの要素 | 現状の掲載コードで行うこと | 代替・省略する範囲 |
|---|---|---|
| 画面とボタン | `main()`が`UIButtons::onAddExpenseClick()`などを直接呼ぶ | GUI部品、クリックイベント、入力フォームは作らない |
| 利用者・認証・口座選択 | 固定した動作例の金額とカテゴリIDを`main()`から渡す | ログイン、利用者照合、利用者別口座、セッション管理は本章の要求にないため扱わない |
| カテゴリマスタ | `CategoryDatabase`の`std::map`へ4件を起動時に固定登録し、存在と種別を実際に照合する | 外部DBからの読込、永続更新、管理画面は行わない。終了すると登録内容は消える |
| 収支登録 | 各Managerがカテゴリと金額を検証し、残高へ反映する正負の値を返す | 収支明細の永続保存、DBトランザクションは行わない |
| 現在残高 | `UIButtons`の整数メンバーへ実行中だけ保持する | 口座台帳からの読込・保存や複数口座の残高管理は行わない |
| 表示 | 成功・エラー・残高を`std::cout`へ出す | 画面描画、通貨書式、通知サービスは標準出力で代替する |
| 操作履歴 | 現状コードでは保持しない | Undo・Redo・一括補償は1-5で追加される変更要求であり、現状へ先取りしない |

したがって、現状コードで実物として確認するのは、固定したカテゴリ表に対する入力検証、支出・収入の増減値、実行中残高の更新です。画面、認証、永続DB、利用者・口座管理が実装済みだとみなして読み進めないでください。

| 各Manager | 金額・カテゴリIDを検証する | 残高へ加える正負の値を返す |

支出・収入の入力が各Managerを通り、`UIButtons`の残高へ反映される出発点を確認します。

操作実行部分のコード例です。

このシステムでは、操作時にカテゴリIDを指定します。カテゴリIDは「食費」「給与」などのカテゴリ名を一意に参照するための識別子です。フェーズ1の現状コードには以下の4件のカテゴリデータがあらかじめ登録されています。

|---|---|---|
| CAT001 | 給与 | 収入（income） |
| CAT002 | 食費 | 支出（expense） |

|---|---|---|---|
| `CategoryDatabase` | 各ManagerからカテゴリID | `std::map` で存在確認しカテゴリを返す | カテゴリ情報。未登録ならManagerが処理を止める |

**Category と CategoryDatabase**

カテゴリIDからカテゴリ名・種別を引きます。エラー条件「登録されていないID」もここで判定します。

```cpp
struct Category {
    std::string name;  // カテゴリ名
    std::string type;  // "income"（収入）または "expense"（支出）
};

class CategoryDatabase {
    std::map<std::string, Category> records;
public:
    CategoryDatabase() {
        records["CAT001"] = {"給与",   "income"};
        records["CAT002"] = {"食費",   "expense"};
        records["CAT003"] = {"交通費", "expense"};
        records["CAT004"] = {"副収入", "income"};
    }
    bool exists(const std::string& id) const {
        return records.count(id) > 0;
    }
    Category get(const std::string& id) const {
        return records.at(id);
    }
    void save(const std::string& id, const Category& c) {
        records[id] = c;                // 実行中のカテゴリ表へ追加
    }
};
```

- **責任：** カテゴリIDから存在確認と情報取得を行う
- **副作用：** `save()` を呼んだときだけ登録表が増える

`type` が `"income"` か `"expense"` かで、どちらのManagerが受け付けるかが決まります。実システムのDBを、実行中のインメモリ表で代替しています。

```cpp
    if (!db.exists(categoryId)) {
        std::cout << "エラー：カテゴリID「" << categoryId
                  << "」は存在しません" << std::endl;
        return 0;
    }
    if (amount <= 0) {
        std::cout << "エラー：金額は1円以上を指定してください"
                  << std::endl;
        return 0;
    }
    Category cat = db.get(categoryId);
    if (cat.type != "expense") {
        std::cout << "エラー：支出カテゴリを指定してください"
                  << std::endl;
        return 0;
    }
    std::cout << "支出を追加しました：" << cat.name
              << " " << amount << "円" << std::endl;
    // 現状コードでは保存せず、残高へ反映する増減値を返す

}
```

### 1-5：変更要求

「利用者から、誤って登録したデータを簡単に取り消したいという要望が多く届いています。来週までに、直近の操作を取り消す『Undo機能』と、取り消した操作をやり直す『Redo機能』を実装してください。あわせて、月初の定型支出をまとめて登録する『一括登録』も、途中で失敗したら成功分を巻き戻す形で入れてほしいのです」と、プロダクトマネージャーから連絡がありました。

依頼文を、実行結果で判定できる変更依頼へ分けます。

| 変更依頼ID | 確定した変更内容 | 入力 | 受入条件 |
|---|---|---|---|
| 変更ID1 | 直前の収入・支出操作を取り消す | Undo操作、実行済み履歴 | 対象操作が逆向きに実行され、残高と収支データが操作前へ戻る |
| 変更ID2 | Undoした同じ操作をやり直す | Redo操作、Undo済み履歴 | 同じ金額・カテゴリの操作が再実行され、実行済み履歴へ戻る |
| 変更ID3 | 複数操作を一括実行し、途中失敗時に成功分を巻き戻す | 順序付き操作列、各保存結果 | 失敗時は成功済み操作を逆順に取り消し、開始前の残高へ戻る |

#### 変更後要求ベースライン

| 要求ID | 変更種別・根拠となる変更ID | 変更後要求 | 受入条件 |
|---|---|---|---|
| 要求ID1 | 継続<br/>根拠: — | 登録カテゴリへ1円以上の収入を追加する | 収入記録と更新後残高を返す |
| 要求ID2 | 継続<br/>根拠: — | 登録カテゴリへ1円以上の支出を追加する | 支出記録と更新後残高を返す |
| 要求ID3 | 継続<br/>根拠: — | 不正入力を拒否し、記録件数と残高を変えない | 各エラー前後の数値が一致する |
| 要求ID4 | 変更<br/>根拠: 変更ID3 | 保存済み記録から残高を求める | 操作・取消・再実行後の件数と残高を照合できる |
| 要求ID5 | 追加<br/>根拠: 変更ID1 | 最後に成功した操作を取り消す | 記録件数と残高が操作前へ戻る |
| 要求ID6 | 追加<br/>根拠: 変更ID2 | 取り消した操作を同じ内容で再実行する | 記録件数と残高が取消前へ戻る |
| 要求ID7 | 追加<br/>根拠: 変更ID3 | バッチ途中失敗時に当該バッチだけを逆順ロールバックする | バッチ開始前の数値へ戻り、過去履歴は残る |

**変更前→変更後の要求対照（今回変える要求IDだけ）**

現行ベースラインと変更後ベースラインを往復せずに済むよう、今回変える要求IDだけを取り出し、変更前と変更後を同じ行へ並べます。

| 要求ID | 変更前の要求（現行） | 変更後の有効要求 | 根拠変更ID |
|---|---|---|---|
| 要求ID4 | 操作の増減を積み上げた現在残高を表示する | 保存済み記録から残高を求める | 変更ID3 |
| 要求ID5 | （新規・現行なし） | 最後に成功した操作を取り消す | 変更ID1 |
| 要求ID6 | （新規・現行なし） | 取り消した操作を同じ内容で再実行する | 変更ID2 |
| 要求ID7 | （新規・現行なし） | バッチ途中失敗時に当該バッチだけを逆順ロールバックする | 変更ID3 |

要求ID1〜要求ID3は継続（変更前＝変更後）のため対照表には載せません。変更後ベースラインで内容を確認できます。要求ID4を変更に含めたのは、一括インポートの途中失敗を逆順で取り消す（変更ID3）には、走行中の整数残高だけでは戻す対象を特定できず、収支明細を台帳へ保存して残高をそこから求める必要が生じたためです。

なるほど、ボタンクリックという「操作」を記録しておき、それを巻き戻したり再適用したりする必要があるのですね。一括登録も、複数の操作を1つの操作単位として扱えれば、途中失敗時の巻き戻しが素直に書けそうです。

**仕様変更の内容**

変更要求を受けて、利用できる操作がどう変わるかを整理します。今回の要求はUndo・Redo・一括登録の3つです。

Redoは、Undoで取り消した操作をもう一度適用する、つまり「取り消しの取り消し」です。編集ソフトや会計入力では、利用者が誤ってUndoしたときに元の操作を復元でき、同じ金額・カテゴリを入力し直すミスも防げます。今回の変更要求に含まれるため、「実行済み」と「Undo済み」の二つの履歴を同じ操作単位で扱えるように実装します。

| 操作 | 変更前 | 変更後 |
|---|---|---|
| 支出登録 | 支出をDBに保存し画面を更新 | **変更なし**（ただし操作履歴への記録が必要になる） |
| 収入登録 | 収入をDBに保存し画面を更新 | **変更なし**（ただし操作履歴への記録が必要になる） |
| **Undo実行（新規）** | —（なし） | **直前の操作を取り消し、残高を操作前に戻す** |
| **Redo実行（新規）** | —（なし） | **取り消した操作を再実行し、履歴へ戻す** |
| **一括登録（新規）** | —（なし） | **複数の操作を順番に実行し、途中失敗時は実行済み分を取り消す** |

今回変えるのは操作の記録・取消・再実行です。カテゴリ情報を取得する保存基盤は仕様変更の対象ではないため、`CategoryDatabase` のカテゴリ取得契約は変更前後で**変更なし**とします。

支出登録と収入登録そのものの意味は変わりません。変わるのは「その操作をどう記録し、どう取り消すか」という管理層です。言い換えると、「何をする操作か」は保ちながら、「操作の記録をどう扱うか」という責任が加わります。

**Undo動作の詳細**

- 支出登録の直後にUndoを実行 → その支出が取り消され、残高が元に戻る
- 収入登録の直後にUndoを実行 → その収入が取り消され、残高が元に戻る
- Undoを連続実行 → 操作の順番を逆に遡って取り消しを繰り返す
- Redoを実行 → 直前に取り消した操作を再実行する
- 一括登録の途中で保存に失敗 → それまで成功した操作を逆順に取り消し、失敗前の状態へ戻す
- 取り消せる操作が履歴に1件もない場合 → 何もしない（エラーにはしない）

**変更後の操作履歴と確認点**

| 追加する複雑さ | 具体例 | この章で見ること |
|---|---|---|
| 操作履歴 | 支出、収入、Undo/Redoを順に残す | 操作の種類を知らずに履歴へ積めるか |
| 複合操作 | 一括インポートで複数の支出を順番に登録する | 単発操作と同じ単位で並べて実行できるか |
| 永続化失敗時の補償 | 3件中2件目の保存で失敗したら1件目を取り消す | 成功した操作だけ履歴に残し、失敗時に逆向き実行できるか |
| 再実行 | Undoした操作をRedoする | 実行と取り消しを同じオブジェクトに持てるか |

**変更前後の入力・判定・加工・出力差分**

1-1の現状仕様を退避し、変更要求を当てた後の仕様と同じ粒度で並べます。以降の分析では、この差分を追います。

| 要素 | 変更前（1-1の現状仕様） | 変更後（今回の要求） | 差分として追うもの |
|---|---|---|---|
| 入力 | 支出追加、収入追加、カテゴリID、金額 | 支出追加、収入追加、Undo、Redo、一括登録、カテゴリID、金額、操作履歴、保存結果 | 操作履歴、再実行、複合操作、失敗結果が増える |
| 判定 | カテゴリが有効か、金額が有効か | カテゴリ/金額判定に加え、取り消せる履歴があるか、再実行できる操作があるか、保存に成功したか | 履歴操作と失敗時補償の判定が追加される |
| 加工 | 残高を更新する | 残高更新後に操作を履歴へ記録し、Undo/Redo時は同じ操作を逆向き/再実行し、複合操作失敗時は成功済み分を逆順に戻す | 実行・取消・再実行・補償を対応させる必要がある |
| 出力 | 更新後残高またはエラー | 更新後残高、履歴更新、Undo/Redo後残高、補償後残高、失敗ログ | 操作履歴と残高の両方を追う |

**変更後の入力・加工・出力**

変更後は、収支データに加えて操作履歴を保存します。履歴には「どの操作を、どの金額・カテゴリで実行したか」と「取り消すときに何を戻すか」が残ります。

変更後の仕様は、入力が異なる二つの流れへ分けます。登録・一括登録は金額やカテゴリを入力に取り、Undo／Redoは履歴を入力に取るからです。

この図から読み取ることは、次の4点です。

- 支出登録・収入登録の判定と加工は1-1のまま変わらず、実行に成功した操作だけを履歴へ記録する。
- Undo/Redoは金額やカテゴリを入力とせず、履歴だけを材料に「直前の操作を逆向きに実行する」「取り消した操作を再実行する」という加工を行う。
- 一括登録は複数の操作を順番に実行し、途中で保存に失敗した場合は成功済み操作を逆順に取り消す。
- 履歴が空のときのUndo/Redoはエラーではなく、何もせずに終わる。

図に加わった「履歴へ記録」「履歴から外す」が実際にどこへ書かれるかは、フェーズ3「問題特定」で変更を試すコードと、フェーズ7の最終コード・実行結果で追います。

既存の2つの登録操作をUndo対象として記録し、新たに「Undo実行」という履歴操作を加える点が、この変更の核心です。

| 変更ID2 | Undoした同じ操作をやり直す | 要求ID6 |
| 変更ID3 | 複数操作を一括実行し、途中失敗時に成功分を巻き戻す | 要求ID4、要求ID7 |

## 🟣 フェーズ2：仮説立案 ―― 何が変わるかを観察し、ヒアリングで裏付ける
フェーズ1「現状把握」で、家計簿アプリがUIボタンから各マネージャクラスを直接呼び出している現状を把握しました。次に、ユーザーから寄せられた「操作を取り消したい」という要望を起点に、この設計における変わる見込みと今回維持する範囲を整理します。

「操作」と「実行」は、変わる理由が異なります。たとえば、支出登録のDB保存方法が変わるのはシステム設計・生成管理の業務機能（RDBからNoSQLへ移行など）によるものです。一方、「履歴管理が必要かどうか」はプロダクト管理の業務機能（ユーザー要望・法令対応など）によるものです。変わる理由がどの業務機能によるか——それが「分けるべき」サインです。

### 2-1：変わりそうな仕様の見当をつける

ここで作る一覧は、思いつきで「変わりそう」と感じたものを並べる表ではありません。フェーズ1「現状把握」で確認した仕様・動作例・クラス図を材料に、次の順で候補を絞ります。

1. 仕様図と動作例から、入力・判定・加工・出力のうち条件や値が変わりそうな箇所を拾う。
2. その箇所が、1-3のどのクラス・メソッドに書かれているかを対応づける。
3. その仕様が、どんな理由で、何をきっかけに、どのくらいの頻度で変わりそうかを仮説として書く。
4. 逆に、当面変えない前提にできる処理の骨格も分けておく。

この手順で見ると、「家計簿の操作を実行する」という大きな処理全体ではなく、その中のどの操作種類・履歴管理・呼び出し方が変更候補なのかを読者自身で追えるようになります。

フェーズ2「仮説立案」では、フェーズ1「現状把握」で見た仕様のうち、どの操作種類・呼び出し・履歴管理が変わりそうかを見当づけます。責務の配置は、変更要求を当てた後の痛みと合わせて確認します。

| 仕様候補 | 仕様上の場所 | フェーズ1の現状コードでの場所 | 見立て |
|---|---|---|---|
| 支出登録操作 | 入力、操作実行 | `UIButtons` から `ExpenseManager.addExpense()` を呼ぶ箇所 | 支出の入力項目や登録手順が変わる可能性があるため、今回見る |
| 収入登録操作 | 入力、操作実行 | `UIButtons` から `IncomeManager.addIncome()` を呼ぶ箇所 | 収入の入力項目や登録手順が変わる可能性があるため、今回見る |
| ボタン押下 | 入力イベント | `UIButtons` | クリックを契機に処理する大枠は当面維持する前提で見る |
| 操作履歴 | 1-5の変更要求で追加 | フェーズ1の現状コードにはない | Undo機能に必要な新しい要求として見る |
| 複合操作 | 一括登録、口座移動、一括削除 | フェーズ1の現状コードにはない | 複数の単発操作を同じ単位として並べられるかを見る |
| 保存失敗時の補償 | DB保存結果、ロールバック | 収支データの保存呼び出し | 成功した操作だけ履歴へ残し、失敗時に戻せるかを見る |

この表から、今回の検討対象は「操作の実行単位」「操作履歴」「複合操作と失敗時補償」です。UIと実行先の呼び出しが同じ場所に書かれて困るかどうかは、フェーズ3「問題特定」で変更を入れてから確認します。

#### ヒアリングで確認すること

操作単位と履歴の見当から、Undoの次に必要になる変化を質問へ変換します。

| 見当 | 現時点の仮説 | 確認する質問 | 確認先 |
|---|---|---|---|
| 履歴操作 | Undo後のRedoも必要になる | 取り消した操作をやり直す要求があるか | UIデザイナー |
| 操作種類 | 対象操作が増える | 口座移動やカテゴリ編集も履歴対象になるか | システム開発担当 |
| 複合操作 | 一度に複数件を扱う | 一括削除など複数データへ作用する操作が増えるか | UIデザイナー |

この質問を2-3で確認し、今回確定する変更と、将来リスクとして残す範囲を分けます。

### 2-2：今回の変更で確実に変わること

1-5で確定した変更IDを、そのまま今回確実に変わることとして確認します。章ごとに異なる色や記号は使わず、以降でも同じ変更IDで追跡します。

- **変更ID1：直前の収入・支出操作を取り消す**
- **変更ID2：Undoした同じ操作をやり直す**
- **変更ID3：複数操作を一括実行し、途中失敗時に成功分を巻き戻す**

ただし「この変更が1回限りか、今後も続くか」によって、どこまで設計を変えるべきかが大きく変わります。関係者に確認します。

### ヒアリングに向けた背景確認

このアプリは、利用者が日々の支出や収入を手軽に記録するためのものです。現在のシステムは、シンプルなボタン操作でマネージャクラスを直接呼び出す構成になっています。

これまではデータを記録するだけのシンプルな作りでしたが、現在は「操作の取り消し（Undo）」や「やり直し（Redo）」という、より高度な操作が求められるフェーズにあります。当時の開発者が、ボタンクリックに応じて直接処理を呼び出すよう実装したコードが、今、その限界を迎えようとしています。

一見すると、このコードは各ボタンに対応するメソッドが綺麗に分かれており、直感的で読みやすい構造をしています。このシンプルな設計は当初の要件（記録のみ）には十分でした。ただ、操作履歴を管理するという新しい要件では、この設計の延長線上では解決しにくい構造的な課題が生まれます。

### 2-3：関係者ヒアリング

確定変更の背景をさらに深掘りするため、UIデザイナーとシステム開発担当に確認を行いました。この会話が、次の「将来リスクテーブル」の根拠になります。

* **開発者：** 「Undo機能以外に、操作をやり直す『Redo機能』を追加する予定はありますか？」
* **UIデザイナー：** 「あります。ユーザーからは『一度取り消したものを戻したい』という声も根強いです。」
* **開発者：** 「操作を履歴として記録する仕組みは、将来的に他の機能にも適用する可能性はありますか？」
* **システム開発担当：** 「あります。今は支出と収入の追加だけですが、将来的に口座の移動やカテゴリ編集といった複雑な操作もUndo対象にしたいと考えています。」
* **開発者：** 「操作そのものの『意図』が変わることはありますか？」
* **UIデザイナー：** 「ええ、例えば『一括削除』のような、一度に複数のデータに作用する操作も追加されるかもしれません。」

ヒアリングの結果、操作の「実行」と「取り消し」の仕組みは、将来的に複雑な操作が追加されても安定している必要があると分かりました。

### 2-4：ヒアリングで判明した将来リスク

ヒアリングで明らかになった「今後変わるかもしれないリスク」を整理します。これは今回の変更で確実に起きることではなく、将来の拡張リスクです。

| リスクID | 将来リスク | 時期の目安 | 根拠 |
|---|---|---|---|
| リスクID1 | 操作の種類の追加（削除・一括削除など） | 機能追加・操作内容の変更時 | UIデザイナーとの確認 |
| リスクID2 | Undo対象となる操作の複雑化（口座移動・編集など） | 口座管理機能の追加時 | システム開発担当との確認 |

なお、記録・残高の出力方法自体（画面表示からCSVエクスポート・帳票出力への変更）もヒアリングで話題になりましたが、今回の変更対象ではないためリスクIDには起こさず対象外として記録します。出力方法は操作履歴の軸とは独立した境界であり、本章で扱う操作の取消・再実行の分離には影響しません。

フェーズ2「仮説立案」で「今回確実に変わるもの」と「将来変わるかもしれないもの」の両方が整理できました。ここで立てた仮説——「操作の実行方法」と「操作の管理方法」は変わる理由が異なる——が正しいかどうかを、次のフェーズ3「問題特定」で実際にUndoを追加しようとすることで確かめます。仮説を「痛みとして体験する」ことが、このフェーズの目的です。

### 2-5：変わる見込みと今回維持する範囲を確定する

2-4のリスクIDを、操作ごとに変えられるようにする部分と、操作を受け付けて履歴を管理する安定側へ分けます。「はい」は、フェーズ6で**操作の種類や補償方法が変わっても、呼び出し元と履歴管理へ条件分岐を広げない構造か**を判定するための印です。

| リスクID・変化軸 | 変わる見込み | 変えられるようにする部分 | 今回維持する部分 |
|---|---|---|---|
| リスクID1：操作の種類の追加（削除・一括削除など） | はい | 操作ごとの実行方法と取り消し方 | 操作の受付、実行済み・取消済み履歴の管理 |
| リスクID2：Undo対象となる操作の複雑化（口座移動・編集など） | はい | 操作ごとの復元データと補償順序 | 実行・取消・再実行という入口、履歴の移動規則 |

したがって2-5の出力は、「具体操作と補償方法は変えられるようにし、操作の受付と履歴管理は守る」という設計条件です。フェーズ3「問題特定」では変更ID1〜変更ID3だけを現在の構造へ適用し、リスクIDはフェーズ6の構造評価に使います。

**UIButtons::runBatch()（追加）**

成功した操作を覚えておき、途中で失敗したら逆順に戻します。

```cpp
// 変更ID3：複数操作を一括実行し、途中失敗なら成功分を巻き戻す
void UIButtons::runBatch(const std::vector<HistoryItem>& items) {
    std::vector<HistoryItem> done;
    for (size_t i = 0; i < items.size(); ++i) {
        const HistoryItem& it = items[i];
        int delta = 0;
        if (it.type == "Expense") {         // ← 同じ種別分岐が4つ目
            delta = em.addExpense(it.amount, it.categoryId);
        } else if (it.type == "Income") {
            delta = im.addIncome(it.amount, it.categoryId);
        }
        if (delta == 0) {
            std::cout << "一括実行が失敗したので巻き戻します\n";
            for (size_t k = done.size(); k > 0; --k) {
                const HistoryItem& d = done[k - 1];
                if (d.type == "Expense") {  // ← 逆操作の分岐が5つ目
                    balance += em.removeExpense(
                        d.amount, d.categoryId);
                } else if (d.type == "Income") {
                    balance += im.removeIncome(
                        d.amount, d.categoryId);
                }
                history.pop_back();
            }
            std::cout << "巻き戻し後残高: " << balance << "円\n";
            return;
        }
        balance += delta;
        history.push_back(it);
        done.push_back(it);
    }
    std::cout << "一括実行後残高: " << balance << "円\n";
}
```

- **種別分岐が4組目と5組目：** 順方向で1組、巻き戻しでもう1組。1つの関数の中に2組あります
- **業務フローが3つの新しい知識を持つ：** どこまで成功したかを覚える `done`、どの順で戻すかという逆順ループ、失敗時に履歴も巻き戻すという規則

## 🟠 フェーズ4：原因分析 ―― なぜ辛いのかを構造で言語化する
フェーズ3「問題特定」で、Undo機能の実装において、呼び出し元のUIクラスが各操作の実行手段をすべて知らなければならないという「過度な依存」が確認できました。本来、画面（UI）は「どのボタンが押されたか」だけを知っていれば十分なはずです。「それをどのメソッドで、どのクラスで実行するか」まで知っている状態——これが「過度な依存」の意味です。このフェーズでは、なぜそのような辛さが生じるのかをコードの構造的な観点から分析します。

### 4-1：痛みの根源を探る（観察と原因）

ここで2つの問いを立てて、構造的な原因を掘り下げます。

- **なぜ、操作が増えるたびに `UIButtons` クラスを開かなければならないのか？**
- **なぜ、Undo機能を追加しようとすると影響範囲が読めなくなるのか？**

この2つの「なぜ」を出発点に、問題の根を辿ります。

フェーズ3「問題特定」で観察した痛みと、その根本的な原因を対応させます。

| **観察** | **原因の方向** |
| --- | --- |
| Undo機能を実装しようとすると、UIクラスが全マネージャクラスの全メソッドを知っている必要がある | 操作ボタンが「実行したい操作」の意図だけでなく、「具体的な実行手順（メソッド呼び出し）」まで直接知っているから |
| 操作の種類が増えるたびに、UIクラスの条件分岐が巨大化する | 「何をしたいか」という操作の意図と、どのクラスのどのメソッドを呼ぶかという実行手順を、同じ条件分岐に置いているから |
| 複合操作や保存失敗時の補償を入れると、何をどの順番で戻すかをUIや履歴管理側が知る必要がある | 実行・取消・再実行・補償が「同じ操作の別の向き」としてまとまっておらず、操作ごとの知識が外側へ漏れているから |

### 4-2：今回変える責任/ほかの変更から守る責任

> **「今回守る」と「変わらない」は異なります。** 左列は今回の変更試行とヒアリングで変更理由を確認した責任、右列はその変更に巻き込まず守りたい責任です。将来ずっと変わる／変わらないという分類ではありません。

原因分析の結果として、「今回変える責任」と「ほかの変更から守る責任」を明確に分けます。

| **今回変える責任** | **ほかの変更から守る責任** |
| --- | --- |
| 入力端（UIボタン、API、バッチ）と操作内容（支出、収入、振替など） | 入力端に依存せず「操作を依頼する」アプリケーション境界 |
| DBやファイルなど台帳の保存方式 | 収支レコードと現在残高が一つの正本として整合する契約 |
| 操作ごとの実行ロジックと取り消しロジック | 履歴のリストを管理し、Undoを実行する仕組み |
| 操作ごとの失敗時補償、再実行、複合操作の内訳 | 操作を同じ単位として実行・取消・再実行できる契約 |

UIそのものを固定するのではありません。画面、API、バッチは変わる入力アダプタとして扱います。どの入力端からでも同じ操作単位をアプリケーション境界へ渡せることを守ります。現在の構造では、操作の意図、実行手段、残高の正本がUIに結合しているため、操作や入力端が増えるたびにUIへ変更が波及します。

### 4-3：接続点に漏れている実行手段の知識を確認する

現在の`UIButtons`は、ボタンの意図だけでなく、どのマネージャーのどのメソッドをどの引数で呼ぶかまで知っています。接続点で渡したいのは「実行でき、必要なら取り消せ、再実行もできる操作」ですが、実行先と引数の知識がUI側へ漏れています。

漏れている知識を具体的に書くと、`ExpenseManager` / `IncomeManager` というクラス名、`addExpense()` / `addIncome()` というメソッド名、金額とカテゴリIDの組み合わせ、取り消すときに呼ぶ逆向き処理、保存失敗時にどこまで戻すか、という情報です。これらをUIや履歴管理が個別に知るほど、新しい操作や複合操作の追加時に同じ分岐が増えていきます。

フェーズ4「原因分析」で「UIとマネージャを切り離す場所」が言語化できました。「どこを分けるか」は明確です。次のフェーズ5「課題定義」では、その境界で実際に何が流れているかを値・型のレベルで具体化し、「何を変え、何を守るか」を明確にします。

---
> **📌 原因（確定）**
> `UIButtons`がボタン押下という「操作の意図」だけでなく、「どのクラスのどのメソッドを何の引数で呼ぶか」という実行手段まで知っている。さらに、Undo/Redoや保存失敗時の補償を入れると、実行・取消・再実行の対応関係まで外側が知る必要がある。操作が増えるたびにUIと履歴処理の両方へ知識が追加される。
---

フェーズ3の問題IDに対応づけて、構造上の原因へ`原因ID`を付けます。次のフェーズ5は、この原因IDから課題IDを導きます。

| 原因ID | 構造上の原因（何が同じ責任へ集まっているか） | 対応する問題ID |
|---|---|---|
| 原因ID1 | 操作ボタンが「実行したい操作の意図」だけでなく「具体的な実行手順」まで直接持ち、実行と取消の対応を同じ単位で受け渡す接続点がない | 問題ID1・問題ID2・問題ID4 |
| 原因ID2 | 実行・取消・再実行・補償が「同じ操作の別の向き」としてまとまらず、台帳更新・補償・履歴積替えの規則が複数箇所へ漏れる | 問題ID3・問題ID4 |

（原因は、操作の意図と実行手段が同じ場所にあることだと分かりました。次のフェーズ5「課題定義」では、その接続点で何を渡せばよいかを値・型のレベルで見ていきます。）

## 🟡 フェーズ5：課題定義 ―― 原因から課題を検討して確定する

フェーズ4「原因分析」で確定した原因は、まだ課題そのものではありません。まず変えるべき構造を候補として導き、システム全体で候補の関係を整理してから、解くべき接続点を確定します。

### 5-1：原因から課題候補を洗い出す
| 原因ID・確定した事実 | そのままだと残る痛み | 課題候補 | 候補を導いた理由 |
|---|---|---|---|
| 原因ID1：UIとバッチが収入・支出の具体呼出しと引数を知る | Undo・Redo・一括実行ごとに入口へ逆操作の分岐が増える | 実行可能な操作を同じ単位として扱う | 操作の種類と実行入口は別の理由で変わる |
| 原因ID2：台帳更新・取消・履歴積替えの規則が複数箇所に漏れる | 途中失敗時にどこまで戻すかを各入口が判断する | 操作効果と補償、履歴管理の責任を分離する | 台帳の正本と操作履歴は異なる責任だから |

ここで挙げるのは、原因のどの構造を変える必要があるかまでです。それをどのクラスへどう置くかは、課題を確定してからフェーズ6で決めます。

### 5-2：課題候補の重複と依存を整理する

| 課題候補 | 必要性・他候補との関係 | 統合／分割の判断 | 整理結果 |
|---|---|---|---|
| 操作単位の分離 | 必須。変更ID1・変更ID2で同じ引数を逆向きに再構成している | UI・バッチ共通の実行境界として残す | 課題として残す |
| 補償と履歴管理の分離 | 必須。操作だけ分けても一括失敗の巻戻し範囲が決まらない | 操作単位と連携する独立責任 | 課題として残す |

ここでは対策案の採否を決めません。原因から出した候補の重複と依存を整理し、同じ変更理由なら統合し、別の変更理由なら課題として残します。

変更IDと課題IDは一対一とは限らないため、変更依頼の数に合わせて課題を増減させません。

### 5-3：課題IDと接続点を確定する

#### 全体経路を決めるための確認観点

全体経路を決めるとき、次の二点を同時に確認します。

- **契約と具体による分離**：入口に残す受付処理と、操作・履歴の判断を持つ契約・具体をセットで決める。
- **実体の組み立て**：操作と履歴を誰が生成・所有し、画面とバッチへ渡してどう実行するかを一本で決める。

### 全体のデータと実体の流れを先に決める

最初に、生成した操作が登録・実行され、同じ実体で取り消されるまでの全体経路を決めます。支出1件の登録と取消を一本で固定します。

| 実行順・ポイント | 掲載箇所 | 実際のコード接続 | 次の呼出先 |
|---|---|---|---|
| 1. 生成 | `main()` | 台帳・履歴・2つの係を作り、`AddExpenseAction cmd1(em, 1000, "CAT002");` で操作を1つ作る | 操作の受け渡しへ |
| 2. 操作を入口へ渡す | `BudgetApp::onAddExpenseClick(IAction*)` | `app.onAddExpenseClick(&cmd1);` で生成済み操作への参照を渡す | 実行開始へ |
| 3. 実行開始 | `BudgetApp::onAddExpenseClick(IAction*)` | `history->execute(cmd)` の1行 | `ActionHistory::execute()` |
| 4. 骨格 | `ActionHistory::execute(IAction*)` | `cmd->execute()` を呼び、成功したら `undoStack` へ積む | `IAction::execute()` |
| 5. 契約→具体 | `AddExpenseAction::execute()` | 内包する金額とカテゴリで `em.addExpense()` を呼ぶ | 台帳が残高を更新 |
| 6. 骨格取消 | `ActionHistory::undo()` | `undoStack` の末尾を取り出し、`cmd->undo()` を呼ぶ | `IAction::undo()` |
| 7. 契約→具体取消 | `AddExpenseAction::undo()` | 同じ金額とカテゴリで `em.removeExpense()` を呼ぶ | 台帳が残高を戻す |

**5と7が、同じ実体の2つのメソッドです。** 金額もカテゴリも、全体経路の受け渡しで使ったものを7がそのまま使います。**3-1では、この2つが離れた場所に別々に書かれていました。**

**4と6のどちらにも、種別の判定がありません。** 履歴は `IAction` としか知らずに、積む順と逆順を管理しています。**これが課題ID1と課題ID2が分かれている実態です。**

### 全体の流れを実現するコードを決める

**【課題の原因】** 課題ID1は、問題ID1・問題ID2・問題ID4（実行手段と種別分岐が入口へ集中）＝原因ID1（操作の意図と具体手順を同じ場所が持ち、共通の接続点がない）。課題ID2は、問題ID3・問題ID4（補償・巻戻し範囲を外側が判断）＝原因ID2（実行・取消・補償がまとまらず台帳・履歴規則が漏れる）。問題ID4は両方の原因が重なった症状として扱い、この2つを分離対象にします。

**この課題（何を解きたいか）：** 操作を1種類足すだけで入口の分岐が増え、Undoを足すだけで種別ごとの逆操作を入口が書くことになる。**画面とバッチが同じ操作契約で実行・取消できる**ようにするのが課題ID1、**成功した操作だけを記録し、失敗時に対象範囲だけを逆順に戻せる**ようにするのが課題ID2です。

**ここで全体経路と対応づけるコード：** 実行と取消の対応をどの単位で受け渡すか、台帳と履歴に何を持たせるか、それらを誰が生成・所有して入口へ渡すかをコードで示します。

操作の種類と履歴の積替え規則は別々の理由で変わります。ただし、失敗時に対象範囲だけを逆順で戻すには、履歴へ積む各操作が自分の取消方法を持つ必要があります。そのため、実行操作の契約を決める時点で `undo()` まで含めます。

**全体経路との対応。** フェーズ5「課題の確定（5-3）」で決まったのは、種別ごとの実行・取消手順、履歴の積替え、残高の保持を、別々の変更へ閉じる境界を作ることです。全体経路で決めた接続を、ここから**境界を関数・表・クラス契約のどれで表し、どのコードで繋ぐか**へ落とします。

書き換える前のコードはフェーズ3「変更を試みる（3-1）」にあります。**ここで全部を再掲することはしません。** 分離と組み立ての判断に必要な数行だけを変更試行（3-1）から抜き出し、変更後と並べます。

#### 1. 契約と具体をセットで決める（分離）

ここでは契約だけを先に完成させません。境界へ残す操作・値と、その裏で変わる判断を持つ具体を往復し、両側がかみ合うところまでを一つの判断として扱います。

##### 契約：境界の形と受け渡しを決める

**関数を一つ切り出すだけでは、変更を閉じ込められません。** 種別ごとの分岐は `onAddExpenseClick`・`onAddIncomeClick`・`undo`・`redo` の4か所に現れます。しかも**同じ組み合わせを逆向きに書いています。** 登録側で「支出なら `addExpense`」と書き、取消側で「支出なら `removeExpense`」と書く。種別が1つ増えれば、両方に1本ずつ足します。そして2-4のリスクID1（操作の種類の追加）とリスクID2（Undo対象の複雑化）が、どちらも「増える」と言っています。登録と取消が同じ操作を呼べるクラス契約まで分けます。

分けると決めたので、コードに線を引きます。

**掲載箇所：`UIButtons::undo()`** ―― 3-1の取消処理（対策前）

```cpp
void UIButtons::undo() {
    if (history.empty()) return;                 // ← 残る側（履歴の積替え）
    HistoryItem last = history.back();           // ← 残る側
    int before = balance;
    if (last.type == "Expense") {                // ← 出て行く側（種別の判定）
        balance += em.removeExpense(             // ← 出て行く側（逆操作の手順）
            last.amount, last.categoryId);
    } else if (last.type == "Income") {          // ← 出て行く側
        balance += im.removeIncome(
            last.amount, last.categoryId);
    }
    history.pop_back();                          // ← 残る側
    redoStack.push_back(last);                   // ← 残る側
}
```

**割り方の根拠は、操作の種類が増えたときに触るかどうかです。** 「口座移動」を足すと真ん中の `else if` が1本増えます。前後の履歴操作は1行も増えません。**変更前のコードでは、この2種類が交互に並んでいます。**

**この `if` を消すには、`HistoryItem` では足りません。** `HistoryItem` は種別を文字列で持つだけのデータなので、**取り出した側が「この種別なら何を呼ぶか」を知る必要があります。** データが自分で自分を取り消せないから、判定が外に残ります。

**5-3が挙げた候補は2つです。** 金額・カテゴリを含む操作と、実行結果。**このうち何がいくつ境界を流れるかは、まだ決まっていません。** 形を決めます。

| 接続するもの（5-3の候補） | 決めた形 | そう決めた理由 |
|---|---|---|
| 金額・カテゴリを含む操作 | 引数で渡さない。**操作そのものをクラスにし、金額とカテゴリはその中に持たせる** | 引数で渡すと、受け取った側が種別を見て呼び分ける。3-1の `if` が移動するだけになる |
| 実行結果 | **成否の真偽で返す** | 変更前は `delta == 0` を成否として使い、`0` のとき履歴へ積んでいなかった。積むかどうかの判断に必要なのは成否だけ |

**1つ目が、この章のいちばん大事な判断です。** 第9章では「現在状態はクラスが体現する」と決めました。**この章で体現するのは値ではなく、操作そのものです。** 「1000円の食費を支出登録する」という**行為が1つのオブジェクトになります。**

**そうすると、金額もカテゴリも境界を流れません。** オブジェクトを作るときに中へ入り、外へは出てきません。**境界を流れるのは、実行結果の真偽1つだけです。**

**候補2つのうち、境界を流れるのは1つです。** 候補の数と実数が一致しないのが普通です。5-3は境界を跨ぐものを漏れなく挙げる表で、ここはそれを形へ変える段です。

**ここで、課題ID2の完了条件を先に読みます。** 課題ID2は「失敗時は対象範囲だけ逆順に戻せる」ことを求めています。**逆順に戻すには、積んだものが自分の戻し方を知っていなければなりません。** 履歴の側が「支出だったから `removeExpense`」と判断するなら、いま外へ出そうとしている `if` が履歴へ移動するだけです。

**だから契約には、実行と取消の両方を置きます。**

| 決めたこと | 内容 |
|---|---|
| 契約が持つ操作 | 実行と、取消の2つ。どちらも成否を返す |
| 根拠 | 課題ID2の完了条件「対象範囲だけ逆順に戻せる」。取消を持たない契約では満たせない |

**契約の名前を決めます。** 実行できる1つの行為を表すので `IAction` とします。表示用の説明を返す操作も添えます。履歴が記録を残すときに、種別を見ずに文字列を得るためです。

**掲載箇所：`IAction`（クラス全体）**

```cpp
// 実行と取消を1つの部品にまとめる契約
class IAction {
public:
    virtual bool execute() = 0;
    virtual bool undo() = 0;
    virtual std::string describe() const = 0;
    virtual ~IAction() = default;
};
```

**引数が1つもありません。** 金額もカテゴリも、実装が自分の中に持つからです。**戻り値は成否だけです。**

**契約だけでは、決めた形が本当に成立するのか確かめられません。** 実装を1つ見ます。

**掲載箇所：`AddExpenseAction`（クラス全体）** ―― 支出登録の操作

```cpp
class AddExpenseAction : public IAction {
    ExpenseManager& em;
    int amount;
    std::string categoryId;
public:
    AddExpenseAction(ExpenseManager& em,
                      int amount, std::string categoryId)
        : em(em), amount(amount), categoryId(categoryId) {}
    bool execute() override {
        return em.addExpense(amount, categoryId);
    }
    bool undo() override {
        return em.removeExpense(amount, categoryId);
    }
    std::string describe() const override {
        return "支出登録: " + categoryId + " "
               + std::to_string(amount) + "円";
    }
};
```

- **「操作そのものをクラスにする」の実態。** 金額とカテゴリがメンバーになりました。**作った時点で「1000円の食費を支出登録する」という行為が確定しています**
- **「種別を引数で渡さない」の実態。** `if (type == "Expense")` の比較がありません。**このクラスであること自体が『支出登録』だから**です
- **「実行と取消を1つに」の実態。** `execute()` と `undo()` が同じメンバーを使っています。**3-1では登録側と取消側の2か所に分かれて書かれていた組み合わせが、1クラスの中で隣り合っています**

**同じ値を2度書かなくなりました。** 3-1では `history.push_back({"Expense", amount, categoryId})` と `em.removeExpense(last.amount, last.categoryId)` が離れた場所にあり、対応が合っているかは読んで確かめるしかありませんでした。

**課題ID2（履歴・台帳軸）。** 同じことを残高と履歴にします。

**掲載箇所：`UIButtons::onAddExpenseClick(int, const string&)`** ―― 3-1の登録処理（対策前）

```cpp
void UIButtons::onAddExpenseClick(
        int amount, const std::string& categoryId) {
    int before = balance;
    int delta = em.addExpense(amount, categoryId);   // ← 出て行く側（実行）
    if (delta == 0) return;
    balance += delta;                                // ← 出て行く側（残高の保持）
    history.push_back({"Expense", amount, categoryId});
    std::cout << "現在残高: " << before
              << " -> " << balance << "円\n";
}
```

**残高が入口のメンバーとして持たれています。** 画面が残高の正本を持っている、ということです。**バッチからも同じ操作を実行するなら、残高がどちらにあるのかが決まりません。**

**5-3が挙げた候補は3つです。** 収支記録、残高前後値、実行済み・取消済み操作。形を決めます。

| 接続するもの（5-3の候補） | 決めた形 | そう決めた理由 |
|---|---|---|
| 収支記録 | **台帳が持ち、台帳だけが持つ** | 守る範囲の「台帳を残高の正本にする契約」。入口が別に残高を持つと2つの正本ができる |
| 残高前後値 | **境界を流れない。** 実行のたびに台帳から求める | 前後の差を持ち回ると、途中で失敗したときにどちらが正しいか決められない |
| 実行済み・取消済み操作 | **契約への参照を、積む順に保持する** | 逆順に戻すには順序が要る。中身は見ないので、種別を知る必要はない |

**候補3つのうち、境界を流れるのは2つです。** 残高前後値は「流さない」と決めました。**これが「台帳を残高の正本にする」の実態です。**

**履歴を管理するクラスの名前を決めます。** 操作を積み、取消と再実行を仲介するので `ActionHistory` とします。


**では、この契約を誰が呼ぶのか。**

---

##### 分離の検算：守る処理が契約だけを呼べるか

呼べるのは、操作の種類が増えても今回維持する側だけです。出て行った側が出て行った側を呼べば、種類が増えるたびに両方を触ることになり、分けた意味が消えます。

**この章では、契約を骨格の外へ置きます。** 一括インポートで10件の操作を実行するとき、**同じ `ActionHistory` の中で相手が10回入れ替わります。** ロールバックでも、積んだ順の逆に相手が替わります。**1つの履歴が複数の操作を扱う**以上、履歴とは別の型として `IAction` を置きます。

**残った側は2つあります。** 履歴を積み替える `ActionHistory` と、画面の入口です。**役割が違うので、分けて見ます。**

**掲載箇所：`ActionHistory::execute(IAction*)` と `undo()`** ―― 骨格

```cpp
    bool execute(IAction* cmd) {
        if (!cmd->execute()) {                    // 種別を見ずに実行を頼む
            executionLog.push_back("失敗: " + cmd->describe());
            return false;
        }
        undoStack.push_back(cmd);                 // 成功したものだけ積む
        executionLog.push_back(cmd->describe());
        redoStack.clear();
        return true;
    }
    void undo() {
        if (undoStack.empty()) return;
        IAction* cmd = undoStack.back();
        if (!cmd->undo()) { /* …失敗時は履歴を変えない（省略）… */ return; }
        undoStack.pop_back();
        redoStack.push_back(cmd);
    }
```

**`if (type == ...)` が1つも残っていません。** 3-1の `undo()` にあった種別判定が消えました。**消えたのではなく、`cmd->undo()` の向こう側へ移りました。**

**この骨格は、操作の種類を1つも知りません。** それでも「成功したものだけ積む」「取消に失敗したら履歴を変えない」という規則を持っています。**これが課題ID2の完了条件「成功操作だけ記録し」の実装です。**

**もう1つの残った側は、画面の入口です。**

**掲載箇所：`BudgetApp::onAddExpenseClick(IAction*)`** ―― 骨格

```cpp
    void onAddExpenseClick(IAction* cmd) {
        history->execute(cmd);          // ←この history が未定
    }
```

**1行になりました。** 3-1では残高の計算と履歴の積み込みと表示を書いていた場所です。**すべて `execute()` の向こうへ行きました。**

**このコード片で未接続なのは、`history` です。** `ActionHistory` を入口ごとに作ると、画面で登録したものをバッチのロールバックが戻せず、履歴が2つに分かれます。全体経路で決めたとおり、`main()` が一つを所有して両入口へ渡すコードを後で示します。

**ここで検算します。操作の種類を1つ足したとき、この骨格は変わるか。** 変わりません。`execute()` も `undo()` も `IAction` だけを見ています。**穴が空いたままでも、この検算はできます。**

**ここで図に描けるのは、2つの骨格から契約への依存だけです。**

##### 具体：契約の裏へ変わる判断を置く

契約と、それを呼ぶ骨格が決まりました。契約の確認では契約の裏を1つ覗いて、持つもの・返すものを確かめました。**ここで残りを埋めます。**

**課題ID1（操作軸）。** 契約の確認で見た `AddExpenseAction` の対になるものを見ます。

**掲載箇所：`AddIncomeAction`（クラス全体）** ―― 収入登録の操作

```cpp
class AddIncomeAction : public IAction {
    IncomeManager& im;
    int amount;
    std::string categoryId;
public:
    AddIncomeAction(IncomeManager& im,
                     int amount, std::string categoryId)
        : im(im), amount(amount), categoryId(categoryId) {}
    bool execute() override {
        return im.addIncome(amount, categoryId);
    }
    bool undo() override {
        return im.removeIncome(amount, categoryId);
    }
    std::string describe() const override {
        return "収入登録: " + categoryId + " "
               + std::to_string(amount) + "円";
    }
};
```

2クラスを並べると、3-1の4か所に散っていた組み合わせがそのまま表になります。

| 操作クラス | 実行 | 取消 | 3-1での対応箇所 |
|---|---|---|---|
| `AddExpenseAction` | `em.addExpense()` | `em.removeExpense()` | 登録の `if` 1本と、取消の `if` 1本 |
| `AddIncomeAction` | `im.addIncome()` | `im.removeIncome()` | 登録の `else if` 1本と、取消の `else if` 1本 |

**右端の列が、この章の分離の成果です。** 変更前は1つの操作を書くのに**離れた2か所**を触っていました。いまは1クラスの中に隣り合っています。**片方だけ書き忘れることが、構造的に起きにくくなりました。**

**具体が2つしかありません。** それでも契約を作るのは、2-4のリスクID1が「削除・一括削除などの追加」を挙げているからです。**種類が増える見込みがあるので、契約の確認で契約まで進むと決めました。**

**課題ID2（履歴・台帳軸）。こちらは実装が1つです。** 履歴の積替えは `ActionHistory` の1クラス、残高の正本は台帳の1クラスで、差し替える相手がいません。**契約を作らず、クラスとして分けるだけで止めます。**

**分けたのに契約を作らない、という選択があります。** 課題ID2で止めたかったのは「入口が残高を持ち、巻戻し範囲を外側が判断すること」でした。台帳と履歴へ移した時点でそれは達成されます。**差し替えの必要が出たときに契約を足せばよく、いま足すと使われない抽象が1つ増えます。**

**掲載箇所：`ActionHistory`（メンバー）** ―― 履歴が持つもの

```cpp
class ActionHistory {
    std::deque<IAction*> undoStack;
    std::vector<std::string> executionLog;  // 実行ログ（追記のみ）
    std::deque<IAction*> redoStack;
    static const int MAX_HISTORY = 50;  // Undo履歴の上限（メモリ保護の安全弁）
    // …execute / undo / redo / printLog（分離の検算で示した骨格）…
};
```

**3つとも `IAction` の並びか文字列です。** 種別を表す文字列も、金額も、カテゴリも持ちません。**履歴は「何が起きたか」を知らずに順序だけを管理します。**

**上限を50件にしています。** 積み続けるとメモリが増え続けるので、最古から捨てます。**これは操作の種類とは無関係な、履歴側だけの規則です。** 種類が増えても変わりません。

**もう一度検算します。契約のメソッド以外に書きたくなるものがあるか。** 出てきませんでした。実行・取消・説明の3つで、登録もUndoもRedoも一括の巻戻しも表せています。

**守る範囲との照合：** **台帳を残高の正本にする契約**に触りました。3-1では入口が `balance` を持っていましたが、残高は台帳から求める形になります。**守る範囲で挙げたのは「残高は台帳から求め、画面や履歴が別の残高を持たない」ことなので、これは範囲を満たす方向の変更です。** 表示・入口・一括の巻戻し範囲には触っていません。

**ここまでで、クラスの設計は終わりです。** 残っているのは、これらを誰が作り、どう渡すかだけになりました。**そしてここから先は、2つの軸で共通です。**

#### 2. 全体経路をコードで組み立てる

ここからは三つを別々の設計判断として扱いません。具体を作る行から、契約として骨格へ入り、公開入口から実行される行までを一つの経路として追います。

##### 全体経路の準備：実体と所有者をコードで示す

**分離の検算で穴が1つ空きました。** 入口が持つ `history` です。そしてもう1つ、**操作の実体を誰が作るか**も決めていません。

**まず履歴から決めます。** 持つ者に必要な条件は、分離の検算で分かっています。

- **画面とバッチの両方から届くこと。** 画面で登録したものをバッチのロールバックが戻せなければ、履歴が2つに分かれます
- **入口そのものではないこと。** 入口が持つと、もう一方の入口から見えません

**この2つを満たすのは、両方の入口より外側にいる者です。** この章では `main()` がそれにあたります。

**次に操作の実体です。ここが、他章と違います。**

第9章では状態を、第4章では形式を、**引き当てる相手として組み立て役が全部持っていました。** この章の操作は違います。**「1000円の食費を支出登録する」という行為は、ボタンが押されたときに初めて決まります。** 組み立てのときには、金額もカテゴリもまだありません。

**だから操作を作るのは、値を持っている側です。** この章では `main()` が画面操作を模しているので、`main()` が作ります。

**掲載箇所：`main()`** ―― 組み立てと、操作の生成（対策後）

```cpp

    CategoryDatabase db;
    LedgerRepository repository;
    BalanceViewRenderer renderer;

    IncomeManager im(db, repository, renderer);
```

**組み立てと生成が同じ場所に並んでいます。** 上の6行が組み立て、`cmd1` の行が操作の生成です。**操作は使うたびに1つ作ります。**

**所有と生存期間もここで決まります。**

- `db`・`repository`・`renderer`・`em`・`im`・`hist` は `main()` のローカル変数です。生ポインタも `new` も使いません
- **操作も `main()` のローカル変数です。** `cmd1` は `main()` が終わるまで生きます
- `ActionHistory` が持つ `undoStack`・`redoStack` は **`IAction*` の借用ポインタ**です。所有しません。積んだ操作より履歴のほうが先に消えることはありません

**履歴が操作を所有しない理由があります。** Undoで取り出した操作は `redoStack` へ移り、Redoでまた `undoStack` へ戻ります。**同じ実体が2つの並びを行き来する**ので、どちらかが破棄すると、もう一方が壊れたものを指します。**所有を持ち込むと、どちらが捨てるかを決める規則が増えます。** 借用にすれば、その規則が要りません。

**上限50件を超えた操作も、捨てません。** `undoStack` から外れるだけで、実体は `main()` に残ります。**捨てる規則が無いのは、所有していないからです。**

##### 全体経路の受け渡し：操作を入口と履歴へ渡す

**分離の検算で書いた骨格には、`cmd->execute()` としか書いてありません。** `AddExpenseAction` とは書いていません。それでも実行すれば支出が登録されます。**ここで見るのは、いつ・何によって、その実装が入るのかです。**

**掲載箇所：`main()`** ―― 全体経路の準備コードで作った操作を渡す行

```cpp
    app.onAddExpenseClick(&cmd1);        // ←ここで実装が入る
```

**掲載箇所：`BudgetApp::onAddExpenseClick(IAction*)`** ―― 受け取る側

```cpp
    void onAddExpenseClick(IAction* cmd) {
        history->execute(cmd);           // 契約としてしか見ていない
    }
```

**この1行で、生成済みの操作を入口へ渡します。** 入口と履歴が受け取る型は `IAction*` なので、実体が `AddExpenseAction` でも具体型を判定しません。履歴は同じ実体を保持し、後で `undo()` を呼びます。

**この章は1つ目ですが、1つだけ他と違います。** 第2章や第7章では、組み立てのときに1回渡して、あとは同じ実体を使い続けました。**この章は、操作するたびに新しい実体を渡します。**

| 軸 | 実装が決まる決め手 | 決め手の出どころ | 入る場所 |
|---|---|---|---|
| 操作（課題ID1） | 呼び出し側がどの操作を作ったか | ボタンが押されたときの値（金額・カテゴリ） | `BudgetApp::onAddExpenseClick()`／`ImportService::importTransactions()` |

**「組み立て時に1回」と「呼び出しごと」の中間です。** 第9章のように骨格が引き当てるのでもなく、第2章のように最初に1回決まるのでもありません。**渡す側が、そのつど作って渡します。**

**そして、履歴は渡されたものを保持し続けます。** `undoStack` に積まれた操作は、Undoされるまで残ります。**入る瞬間は1回でも、入ったものは長く生きます。** ここが第2章との違いです。

**入口が履歴へ届く方法（借用ポインタ）は、全体経路の準備コードで示した話です。** 値で持つと画面とバッチで履歴が分かれます。この章で追う受け渡しは、操作を入口へ渡し、同じ履歴へ保持する経路です。

**取消は呼び方が変わりました。** 変更前は入口の `undo()` を呼んでいましたが、いまは履歴の `undo()` です。**取消は画面の機能ではなく、履歴の機能だと決めたからです。** 画面もバッチも同じ履歴を使うので、どちらから登録したものでも同じ場所から戻せます。

**全体経路で先に決めた呼び方を、ここで実コードと突き合わせます。** 章によって公開入口が変わる場合と変わらない場合がありますが、重要なのは先に決めた経路と各コードの接続が一致することです。

**守る範囲との照合：** **操作を依頼する入口**を保っていることを、いま確認しました。ボタンを押すと1件の操作が実行される、という形は変わっていません。**表示**も、実行のたびに内容と残高の前後を出す形のままです（出す場所が台帳側の描画へ移りました）。分離と組み立てを通して、守る範囲の4つはいずれも定義に反していません。最終確認はフェーズ7の受入・回帰エビデンスで行いますが、**そこで初めて確かめるのではなく、全体経路と詳細コードで照合済みです。**

### 6-1：決めた流れとコードの照合

#### 流れを成立させる二つの確認

契約と具体による分離と、生成から実行までの組み立てを二行で確認します。

| 判断 | 変更前の所属 → 変更後の所属 | 設計結論 | 検算 |
|---|---|---|---|
| 契約と具体による分離 | 種別判定付きの実行・取消 → `IAction` と操作具体、種別を見ない `ActionHistory` | 実行と取消を同じ具体へ置き、台帳・履歴規則を入口から外す | 新しい操作で入口と履歴の分岐を増やさない |
| 実体の組み立て | 入口が係と残高を持つ → `main()` が台帳・履歴を所有し、操作を利用時に生成 | 操作を契約として入口へ渡し、成功時に履歴へ保持して実行・取消する | 登録と取消が同じ操作実体を使う |

公開入口には操作を契約として渡し、取消は同じ操作を保持する履歴へ依頼します。生成した操作と実行・取消が一つの経路でつながります。

### 6-2：システム全体の契約とデータ配置を確定する

採用システムの契約、生成場所、依存注入を一表で確定します。接続点で受け渡すのは、実行に必要な値を内包した `IAction*` です。履歴の成否は `bool` で返し、失敗した操作はスタックへ積みません。
フェーズ6ではクラス間の契約（シグネチャ）と責務の配置を示すため、構造の要点となるメソッド（ここでは履歴への追加）のみ実装を示し、その他の実装はフェーズ7の全体コードで示します。

```cpp
class ActionHistory {
    std::deque<IAction*> done;      // 成功済み操作の並び（Undo対象）
    std::deque<IAction*> redoable;  // Undoした操作（Redo対象）
public:
    bool execute(IAction* a) {
        if (!a->execute()) {
            return false;
        }
        done.push_back(a);
        return true;
    }
    bool undo();                    // 実装はフェーズ7を参照
};
```

`undo()` の実装で守るのは「失敗したら履歴を動かさない」ことです。末尾を `back()` で参照したまま取り消しを試し、成功した場合にだけ `pop_back()` して Redo 側へ移します。先に取り出して失敗時に積み直す書き方でも結果は同じにできますが、途中で例外が出ると履歴が壊れます。参照してから取り除く順にすると、不変条件がコードの形として読めます。実装と失敗時の実行結果はフェーズ7で示します。

| 接続点を変える観点 | システム全体での設計判断 | 変えたくない側が知らなくなる詳細 |
|---|---|---|
| 分離方法 | 課題ID1の実行値・逆操作を各Actionへ、課題ID2の残高更新を台帳へ閉じる | 操作種別・引数・取り消し方・残高計算 |
| 配置場所 | 履歴を `ActionHistory`、収支と残高を `LedgerRepository` へ置く | 履歴と残高の保存詳細 |
| 組み立て方法 | Composition Rootが台帳・Manager・History・Appを所有し、ActionへManagerを注入する | 具体操作クラスと実行先の選択 |

操作オブジェクトの所有は `main()`（Composition Root）が担い、スタック変数として生存期間を管理します。`ActionHistory` は成功・失敗した操作を `IAction*` で借用参照として並べるだけで、破棄はしません。UIやバッチは操作を生成して渡すだけです。

**LedgerRepository と BalanceViewRenderer**

収支レコードと現在残高を一体で所有する台帳の正本と、画面表示の境界です。

```cpp
class LedgerRepository {
    std::vector<LedgerEntry> entries;
    int currentBalance = 0;
public:
    bool saveExpense(const Category& category, int amount) {
        entries.push_back({"expense", category.name, amount});
        currentBalance -= amount;
        return true;
    }
    bool saveIncome(const Category& category, int amount) {
        entries.push_back({"income", category.name, amount});
        currentBalance += amount;
        return true;
    }
    bool deleteExpense(const Category& category, int amount) {
        if (!removeLast("expense", category.name, amount)) {
            return false;
        }
        currentBalance += amount;
        return true;
    }
    bool deleteIncome(const Category& category, int amount) {
        if (!removeLast("income", category.name, amount)) {
            return false;
        }
        currentBalance -= amount;
        return true;
    }
    int balance() const {
        return currentBalance;
    }
    // 要求ID4：残高と突き合わせる収支記録の件数
    int recordCount() const {
        return (int)entries.size();
    }
private:
    bool removeLast(const std::string& kind,
                    const std::string& categoryName,
                    int amount) {
        for (std::size_t i = entries.size(); i > 0; --i) {
            const LedgerEntry& entry = entries[i - 1];
            if (entry.kind == kind
                    && entry.categoryName == categoryName
                    && entry.amount == amount) {
                entries.erase(entries.begin() + (i - 1));
                return true;
            }
        }
        return false;
    }
};

class BalanceViewRenderer {
public:
    void showMessage(const std::string& message) {
        std::cout << message << std::endl;
    }
};
```

`deleteExpense` / `deleteIncome` は保存済みレコードを取り消し、同じ操作で残高も戻します。**1-4では `UIButtons` が残高を持っていましたが、正本がここへ移りました。** 利用側が収入合計と支出合計の差を計算する必要はありません。

**IAction**

実行と取り消しを、すべての操作クラスに強制する契約です。

```cpp
// 操作の契約：実行と取り消しをすべての操作クラスに強制する
class IAction {
public:
    virtual ~IAction() {}
    virtual bool execute() = 0;
    virtual bool undo() = 0;
    virtual std::string describe() const = 0;
};
```

`IAction` を定めることで、履歴管理クラスはどの具体的な操作クラスが来ても同じ方法で扱える。この「型の統一」と「成否の統一」が、Undo/Redoと失敗時補償を汎用的に実現する鍵になる。

**ActionHistory**

実行ログ（`executionLog`）はシステム起動時は空で、操作が実行・取り消しされるたびに1件追記されます。`undoStack` とは異なり、削除されることなく全操作の記録として保持します。なお `MAX_HISTORY` は `undoStack` が無制限に伸び続けないためのメモリ保護の安全弁で、仕様要件ではなく本章の動作例では上限に到達しません。

```cpp
// 操作履歴を保持し、Undo/Redoを制御する仲介役
class ActionHistory {
    std::deque<IAction*> undoStack;
    std::vector<std::string> executionLog;  // 実行ログ（追記のみ）
    std::deque<IAction*> redoStack;
    static const int MAX_HISTORY = 50;  // Undo履歴の上限（メモリ保護の安全弁）
public:
    bool execute(IAction* cmd) {
        if (!cmd->execute()) {
            executionLog.push_back("失敗: " + cmd->describe());
            return false;
        }
        undoStack.push_back(cmd);
        executionLog.push_back(cmd->describe());
        if ((int)undoStack.size() > MAX_HISTORY) {
            undoStack.pop_front();  // 最古の操作を削除する
        }
        redoStack.clear();
        return true;
    }
    void undo() {
        if (undoStack.empty()) return;
        // undo()が失敗した場合は、履歴を変えずに終わる
        IAction* cmd = undoStack.back();
        if (!cmd->undo()) {
            executionLog.push_back("取り消し失敗: " + cmd->describe());
            return;
        }
        undoStack.pop_back(); // 成功時のみUndo履歴から外す
        executionLog.push_back("取り消し: " + cmd->describe());
        redoStack.push_back(cmd);
    }
    void redo() {
        if (redoStack.empty()) return;
        // execute()が失敗した場合は、履歴を変えずに終わる
        IAction* cmd = redoStack.back();
        if (!cmd->execute()) {
            executionLog.push_back("再実行失敗: " + cmd->describe());
            return;
        }
        redoStack.pop_back(); // 成功時のみRedo履歴から外す
        executionLog.push_back("再実行: " + cmd->describe());
        undoStack.push_back(cmd);
    }
    void printLog() const {
        for (const auto& entry : executionLog) {
            std::cout << entry << std::endl;
        }
    }
    int historySize() const {
        return (int)undoStack.size();
    }
};

```

`ActionHistory` は `IAction*` として操作オブジェクトを受け取り、`undoStack`／`redoStack` で管理します。具体的な操作クラスは知りません。ここで保持する `IAction*` は**借用参照**で、操作オブジェクトの所有は生成元（`main()`）にあります。`ActionHistory` は生成も破棄もしないため、`undoStack` からあふれた操作を `delete` することはなく、`main()` の各操作オブジェクトが自身のスコープ終了時にまとめて破棄されます。Undo/Redoの実行に失敗した場合は、対象の操作を元のスタックに残す順序にしています。

**BudgetApp と ImportService**

UI以外の呼び出し元の例として、複数の操作をまとめて実行する `ImportService` を追加します。フェーズ2「関係者ヒアリング（2-3）」で「一括削除のような複数データへの操作もあり得る」と予告されていた種類の呼び出し元です。UIと同じ `IAction` インターフェースを通じて操作を実行するため、履歴とUndoの仕組みをそのまま共有できます。まず、UIと一括インポートの2つの呼び出し元クラスを定義します。

```cpp
// UIからの操作を受け取り、Historyに委譲するだけ
class BudgetApp {
    ActionHistory* history;
public:
    BudgetApp(ActionHistory* h) : history(h) {}
    void onAddExpenseClick(IAction* cmd) {
        history->execute(cmd);
    }
    void onAddIncomeClick(IAction* cmd) {
        history->execute(cmd);
    }
    void onUndoClick() {
        history->undo();
    }
    void onRedoClick() {
        history->redo();
    }
};

// 一括インポートからの操作を受け取り、Historyに委譲するだけ
class ImportService {
    ActionHistory* history;
public:
    ImportService(ActionHistory* h) : history(h) {}
    void importTransactions(
            std::vector<IAction*> cmds) {
        int succeeded = 0;
        for (IAction* cmd : cmds) {
            if (!history->execute(cmd)) {
                rollback(succeeded);
                std::cout << "インポート失敗。成功済み操作を補償しました"
                          << std::endl;
                return;
            }
            succeeded++;
        }
        std::cout << succeeded << "件インポート完了"
                  << "（履歴: " << history->historySize()
                  << "件）" << std::endl;
    }
    void rollback(int count) {
        for (int i = 0; i < count; i++) history->undo();
        std::cout << count << "件ロールバック完了"
                  << std::endl;
    }
};
```

操作の意図を独立させた代わりに、操作ごとのクラス、操作オブジェクトの所有権、失敗時の整合性を管理する必要があります。

### 問題・原因・課題・解決策

| | 内容 |
|---|---|
| **問題** | 変更ID1〜変更ID3を適用すると、`UIButtons`の条件分岐と各マネージャへの依存を連動して修正する必要があった |
| **原因** | 操作の意図、実行手段、取り消し方、再実行の仕方、失敗時補償が同じ場所に混在しており、操作追加の頻度ではこの接続コストが合わない |
| **課題** | 具体的な実行手段（クラス名・メソッド名・引数の組み合わせ）と補償手段をUIやバッチから切り離し、差し替え可能なオブジェクトとして独立させる |
| **解決策** | 操作記録構造：操作の実行・取り消し・成否を `IAction` インターフェースに統一し、`ActionHistory` が `IAction*` だけを知る仲介役として履歴を管理する |

## パターン解説：Command パターン

Commandパターンは、リクエストをオブジェクトとしてカプセル化し、呼び出し元が具体的な実行先や引数の組み立てを直接知らずに依頼できるようにするパターンです。CommandはReceiverと実行に必要な引数を保持し、InvokerはCommandの共通契約だけを通じて実行・履歴化します。

### パターンの骨格

```mermaid
classDiagram
    class Command {
        <<interface>>
        +execute()
        +undo()
    }
    class ConcreteCommand {
        +execute()
        +undo()
    }
    class Invoker {
        +setCommand()
        +run()
    }
    Command <|.. ConcreteCommand
    Invoker o-- Command

```

### パターン骨格の実行シーケンス

```mermaid
sequenceDiagram
    participant C as Client
    participant I as Invoker
    participant CMD as Command
    participant R as Receiver
    C->>CMD: Receiverと引数を渡して生成
    C->>I: Commandを登録
    C->>I: 実行を依頼
    I->>CMD: execute()
    CMD->>R: 業務メソッドを呼ぶ
    R-->>CMD: 成功/失敗
    CMD-->>I: 実行結果
    opt 取り消し
        I->>CMD: undo()
        CMD->>R: 逆操作を呼ぶ
    end
```

この順序で重要なのは、InvokerがReceiverを直接呼ばないことです。具体的な呼び出し先と引数、逆操作はCommand内に閉じ、Invokerは `execute()` / `undo()` の契約だけで履歴を進めます。

### この章の実装との対応

`IAction` インターフェースが `Command` ロール、`AddExpenseAction` / `AddIncomeAction` が `ConcreteCommand` ロール、`ActionHistory` が `Invoker` ロールに対応しています。

### 使いどころと限界

* **使うと良い状況**：操作の取り消し（Undo）や再実行（Redo）が必要な場合や、実行タイミングを細かく制御したい場合。


* **使わない方が良い状況**：操作が単発で、履歴管理などが不要な場合。

### この章のまとめ

家計簿アプリというドメインと Commandパターンの関係を一言で言うなら、操作を「動詞（メソッド呼び出し）」から「名詞（オブジェクト）」に変えた瞬間、履歴管理・Undo・バッチ実行という選択肢が設計として自然に現れる、ということです。`AddButton` がどのサービスのどのメソッドをどんな引数で呼ぶかを直接知っていた限り、「いつ実行するか」「取り消すか」「並べるか」という問いに答える余地がUIコードの中にありませんでした。

7つのフェーズを通じて、読者はボタンと処理の直結という観察から始まり、「呼び出し元が知りすぎている」という診断を経て、操作をオブジェクトとして切り出すという判断へと進みました。フェーズ2のヒアリングで「Undo機能は将来ほしい」と確認した時点で操作のオブジェクト化という方向性が見え、フェーズ4でボタンの依存過多を接続点として特定した時点で分離の理由が確定する——その気づきの順序を体験したことが、この章の核心だと思います。

あなたのコードの中にも、UIや呼び出し元が実行先のクラス名・メソッド・引数まで知っている箇所があるはずです。「この操作を後から取り消したり、並べたりする必要が来るか」を問うことが、操作を記録できる構造が必要かどうかを判断する入口になります。
