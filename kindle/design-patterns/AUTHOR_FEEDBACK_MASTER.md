## 著者指摘を無条件に適用しない

著者指摘は重要な入力だが、文言どおり機械的に全章へ当てはめると、過去に確定した仕様や別の指摘と衝突することがある。AIは各指摘について、次を確認してから反映する。

1. 指摘が解決しようとしている読者の困りごとを一文で言い直す。
2. 現行仕様、前後フェーズの確定事項、完成コードと矛盾しないか確認する。
3. 全章共通原則か、特定章だけの問題かを分ける。
4. 既存原則と衝突する場合は、両方の目的を満たす順序または表現へ統合する。
5. 採用、限定採用、不採用のいずれかと、その理由を監査記録へ残す。

著者へ反論が必要なのは、指摘を反映すると現状仕様が変わる、前工程の結論と矛盾する、読者の理解がかえって悪化する、または別の完了条件を破る場合である。迎合のために本文を変えず、根拠と代替案を示す。ただし、単なる好みの違いを理由に指摘を退けない。

| フェーズ2 | 変わる見込み、当面安定、リスクIDと設計条件 | フェーズ3が混ぜてはいけない将来リスク、フェーズ6が考慮する条件 |

| フェーズ4 | 痛みを生んだ構造上の原因、責任・知識・依存の集中 | フェーズ5が検討する課題候補の根拠 |

各フェーズの冒頭に「前フェーズから受け取る確定事項」を置き、ID、名詞、短い結論文は可能な限り同じ文言で再掲する。言い換える必要がある場合は「同じ意味の説明」なのか「新しい判断」なのかを明示する。前フェーズにない判断を、接続文だけで既定事実にしない。

特に次の接続を重点確認する。

```text

→ フェーズ4で確定した原因
→ 同じ原因文を受けたフェーズ5の課題候補
→ 全体評価後に確定した課題ID・完了条件
→ フェーズ6の構造変更
→ フェーズ7のコードと改善結果
```

フェーズ4の結論からフェーズ5へ移るときは、原因を課題へ直変換しない。原因文をそのまま入力欄へ置き、「この原因をなくすにはどの接続を変える必要があるか」を検討して候補を出す。

## フェーズ1：実行結果で動作像を作り、現状仕様を確定する

- 最初の具体物として代表実行結果を示す。
- 実行結果から、利用者、入力、公開操作、主要処理、状態・数値の変化、出力を時系列で読み解く。
- その後に、同じ結果を生む入力・`main()`、入力・主要処理・出力・掲載コードでの代替、詳細仕様を示す。
- 入力コードを代表実行結果より先に出さない。
- 既存要求へ要求IDを付け、完成コードと受入・回帰結果まで追跡する。
- 役職、利用者、状態、通知先、保存値、検証項目など、コードを読んで初めて分かる仕様を残さない。
- 将来予定、未確定機能、変更後だけの役割・状態・通知先を現状仕様へ混ぜない。
- コードで使用する入力項目を仕様へ定義し、仕様にある入力はコードで使用する。
- 本・PDF・メール・外部APIなどをスタブで代替する場合、実際に生成・送信するものとしないものを明記する。
- 現状コードの全`class`・`struct`を登場型表と現状クラス図へ載せる。
- クラス説明は、役割またはクラス名→コード→直後説明の流れを保つ。
- 現状のログ、保存方式、API、検証、内部基盤は、仕様変更がなければ変更後も維持する。

フェーズ1の読書順は次で固定する。

```text
代表的な実行結果を最初に見せる
→ その結果を生む入力・操作と、結果の読み方を文章で説明する
→ 現状仕様をコードなしで確定する
→ 同じケースを実行するmainまたは利用例
→ 入力・コード・結果の対応を確認する
→ システム全体の構造・クラス図
→ クラス別の役割、コード、直後説明
```

最初の具体物は実行結果である。読者が「このシステムは何をするのか」を先にイメージしてから、結果中の値と操作を文章で読み解く。その後、コードを読む前に現状仕様をすべて定義し、同じケースの`main()`または利用例で入力と結果を結ぶ。`main()`内に未説明の役職、状態、入力、通知先、操作を初出させない。

この順序の目的は、見出しを移動することではなく、内部構造を読む前に読者が一連の動作を頭の中で再生できるようにすることである。代表実行結果と直後の説明から、少なくとも次が分からなければならない。

- 誰または何が、どの入力・設定を与えたか。
- どの公開操作を実行したか。
- システム内部で主要処理がどの順に起きたか。
- 主要な数値・状態・履歴がどう変わったか。
- 何が出力、保存、通知、またはエラーとして返ったか。

内部デバッグ行の断片、最終メッセージ一行、互いに無関係な複数出力を並べるだけでは不十分である。現行システムの中心的な価値が伝わる一つのエンドツーエンドケースを優先し、出力は時系列に並べる。コードを読まなくても主要動作を説明できることを人手で確認する。

## フェーズ2：変化の見当と確認を、未来実装へ変えない

- 仕様のどこが変わりそうかを観察し、構造上の良し悪しを先に断定しない。
- 見当→仮説→確認質問→確認先→回答の順を示す。
- 将来リスクはリスクIDで管理する。
- 2-5の「変わる見込み＝はい」は、未来機能を先行実装する指示ではない。
- 「はい」は、フェーズ6で変わる側と守る側を分離し、変更影響を局所化できるか評価する設計条件である。
- リスクIDはフェーズ6で構造上の考慮と将来の変更先を確認するが、フェーズ3・7のコードへ入れない。

## フェーズ3：変更IDを仮実装へ当て、痛みを観測する

- 1-5の確定変更へ変更IDを付ける。
- 1-5と同じ変更ID・同じ変更文を、変更試行表へ引き継ぐ。
- 各変更IDを仮実装コードの具体的な行・分岐・状態・登録・呼出しへ対応づける。
- 変更IDごとに、修正箇所、維持する処理、再テスト範囲、実行・観測ケースを示す。
- 文章で「追加すると大変になる」と想像するだけで済ませず、確定変更を実際の変更途中コードへ反映する。
- 順次実行、自動昇格、通知、再実行などシステムが行うべき処理を、`main()`や利用者の手動呼び分けで代替しない。
- 3-2の変更影響グラフは、3-1で実際に変更・確認した範囲を示す。
- 3-3の痛みは、仮実装と再テスト範囲から導く。
- 1-5、3-1、3-2、3-3の変更ID集合を一致させる。
- 変更IDと課題IDを一対一にしない。課題IDは後で痛みと原因を検討して確定する。
- リスクIDや未来仕様を痛みの根拠にしない。

## フェーズ4：痛みを構造上の原因へ変換する

- 痛みから直接課題IDを付けない。
- 変更途中コードで、どの判断・状態・生成知識・依存が同じ場所へ集まったかを具体的に示す。
- 元のクラスが持つ現状責任と、変更によって漏れ込んだ知識を区別する。
- 別の理由で変わる軸を分け、最後に同じ変更起点へ重なっている事実を統合する。
- 原因はコード上の事実から導き、採用したいパターンを正当化するために書き換えない。
- フェーズ末に「原因確定表」を置き、原因文、根拠となる痛み・コード、集中している責任・知識・依存を確定する。
- 原因確定表の原因文を、フェーズ5の入力で可能な限り同じ文言のまま使う。

## フェーズ5：原因から課題候補を検討し、課題を確定する

- 原因を言い換えていきなり課題IDにしない。
- 原因ごとに課題候補と、その候補を導いた理由を示す。
- 候補の必要性、重複、統合、分割をシステム全体で評価する。
- 評価後にだけ課題IDを連番で付ける。重複IDや欠番を作らない。
- 課題IDごとに接続点、変わる側、守る側、完了条件を定める。
- 課題をすべて解いたシステム全体の完了状態を一文で示す。
- フェーズ5では具体クラス名、継承、インターフェース、パターン名、生成・注入方法を先取りしない。
- 要求IDと課題IDを直接結ばない。要求を満たす場所に必ず設計課題があるとは限らない。

## フェーズ6：構造とコードを、読者が実装できる順に説明する

### 最初にフェーズ5の入力を確認する

- フェーズ5末の課題ID、接続点、変わる側、守る側、完了条件、全体完了状態を同じ文言で再掲する。
- 各課題がフェーズ3の痛みとフェーズ4の原因へ戻れることを確認する。
- 根拠が切れている章だけフェーズ4・5を補正する。
- 原因→課題が成立している章を理由なく全面改稿しない。

### 全体があって、いまどこを変更しているかを示す

フェーズ6の冒頭で、採用予定の詳細型を先取りせず、システム全体の構造変更を抽象語で一枚にまとめる。

```text
現在：安定処理の中に、変わる判断A・Bが同居している
変更後：判断A・Bを別責任へ分離し、組み立て境界で再結合する
守る範囲：入力、共通順、保存、外部契約など
```

その後の各節では、冒頭に短い現在地を置く。

```text
全体の構造変更：Aの分離 → Bの分離 → 生成・注入 → 再結合
今回の位置：Aの分離
抽象的に行うこと：変わる判断を安定処理から外す
この章で説明する具体：OrderServiceの条件分岐をPricingPolicyへ移す
```

抽象的な設計操作と、いま説明している具体クラス・メソッドを必ず対にする。「全体があって今ここ」が見えないまま部分図やコードを続けない。現在地表示は新しい図種にせず、短い文章、一覧、または採用全体クラス図の着色で示す。

### 課題ごとの説明順

```text
課題に関係する変更前／変更途中コード
→ コード上で一緒になっている判断
→ 何と何を分けるか
→ なぜ別の理由で変わるか
→ 何を守るか
→ 着色した部分クラス図
→ 採用後の関連コード
→ 変更前の判断が移った先
→ 完了条件へ効いた結果
```

### 継承・実装関係を採用する場合

- 共通部分、可変部分、基底契約、上書き箇所を説明する。
- 継承矢印を描くだけで済ませない。
- 誰が具体クラスを選択・生成するか示す。
- 生成した具体オブジェクトを、どの基底型・インターフェース型として渡すか示す。
- 安定側が具体型を`if`や`dynamic_cast`で判定せず、共通契約だけを呼ぶことをコードで示す。
- 具体クラス追加時の変更先と変更しない場所を説明する。
- 共通性がない、具体が一つしかない場合は継承の必要性を再検討する。

### 分離した部品を再結合する

- 生成場所、選択条件、生成時点、注入元、注入先、契約型、所有者、破棄者を区別する。
- アプリケーション起動時に一度作る部品と、要求ごとに作る部品を分ける。
- 「注入」は生成済み依存を外から渡すこと、「受け渡し」は生成結果を契約型で返すこととして区別する。
- 具体入力を一つ使い、実際に生成されるオブジェクト構造、内側／外側、実行順、破棄順を示す。
- 生成場所だけが具体クラスを知り、安定した実行側は共通契約だけを呼ぶ状態を示す。
- クラスを分離しただけで終わらず、要求を最後まで実行できる一つのシステムへ戻す。

### 抜粋コードの条件

- 全コードを毎回再掲しない。
- 抜粋前に、全体経路、所属クラス・メソッド、変更段階、呼出元・呼出先、省略範囲、確認目的を示す。
- メンバー変数を使うなら宣言とコンストラクタ、仮想関数なら基底契約と具体実装、生成なら生成側と受取側を示す。
- 複数クラスへまたがる場合、生成→注入・受け渡し→契約による実行→所有・破棄を番号付きで接続する。
- 一メソッドだけを浮かせ、`wrapped`、`renderer`、`service`などの由来を読者に推測させない。
- 抜粋直後に、変更前の何が消え、どこへ移り、安定側が何を知らなくなったか説明する。

### クラス図

- 新しい図種を作らず、責任見直しにはクラス図を使う。
- 着目する型・関係を色で示す。
- 部分クラス図は関連部分だけでよいが、抽象型・具体型だけを浮かせず、生成・登録・選択・利用する側を可能な限り含める。
- 部分図の全型に関係線を付け、採用全体図の部分集合にする。
- 採用全体図は完成コードの全`class`・`struct`を載せる。
- コードにない型、関係線のない孤立型を載せない。
- 継承、実装、所有、参照、生成、注入、呼出しの線種とラベルを実コードへ合わせる。
- フェーズ6の採用全体図とフェーズ7の完成図を同一定義にする。

### 対策検討表・課題カード

- 課題表を置いただけで「一致している」と説明しない。
- 各課題について、どのコードへ何を適用し、結果どうなったかをコードレベルで説明する。
- 分離方法、配置場所、生成場所、注入方法、所有、実行、効果を同じクラス名・メソッド名で追う。
- 6-3、6-4などの節は、前の図・コードから新しい判断を与えないなら削除または統合する。
- 目的のない長い表や重複説明を残さない。

## フェーズ7：完成コードと結果で二つの追跡を証明する

### 要求の追跡

```text
要求ID → 完成コード → 受入・回帰結果
```

- 既存要求を含む全有効要求IDを、完成コードと受入結果へ照合する。
- 継続、変更、追加、廃止を要求ID単位で示し、既存動作のデグレ確認を行う。
- 要求の過不足と、変更後に要求が消失していないことを確認する。

### 設計課題の追跡

```text
課題ID → 採用構造 → コード上の責任移動 → 変更影響の改善結果
```

- 課題IDを要求IDへ直接対応させない。
- 課題ごとの完了条件が構造とコードで成立したことを確認する。
- 変更ID別の改善後変更影響グラフは、フェーズ3と同じ粒度で示す。
- 修正後に共通順・安定クラスへ変更線が伸びないことと、クラスがシステムから孤立していることを区別する。

### 完成コードの説明順

- 完成クラス一覧→完成クラス図→実行シーケンス→クラス別コード→直後説明→実行シナリオ→結果の順にする。
- クラス名だけを列挙せず、役割、入力、内部処理、呼出し先、戻り値・副作用を説明する。
- 実行シナリオの全体像または`main()`を、個別ケースの意味が分かる位置へ置く。
- 実行コードと対応する結果を離さない。
- フェーズ7で、フェーズ6にないクラス・生成規則・注入関係を初出ししない。

## システムが自動で行うべき処理を手動実装にしない

- キャンセル待ちの昇格は、予約済みの取消時にシステムが自動実行する。
- 状態遷移後の通知、後続処理、履歴更新など、仕様上自動の処理を利用者や`main()`の追加呼出しにしない。
- 複数ジョブの順次実行や失敗後続行は、バッチ／Application／Context等のシステム責任へ置く。
- 手動シナリオで結果を作らず、公開操作一回から必要な内部処理が接続されることを示す。

## ログ・状態・エラー

- 内部数値が変化するなら、変更前→変更後の値をログへ出す。
- 満席になるなら予約数の変化を見せ、その後の予約で満席エラーを確認する。
- 受付履歴とデバッグログなど、目的・保持データ・件数が異なる記録を混同しない。
- 現状にある内部デバッグログを、変更要求にないという理由だけで削除しない。
- エラーで業務状態が変わらないなら、エラー専用状態を安易に追加しない。
- 不正操作は結果契約で返し、状態・保存・通知を変えない。
- ログ出力だけで実物の生成・通知・保存が完了したように書かない。

## データ・入力・保存方式

- 仕様にある入力をコードで使う。未使用入力を残さない。
- 使わないユーザー名、電話番号、セキュリティコード等は、照合しない意図を仕様で説明するか、入力から除く。
- データ保存方法に仕様変更がないなら、変更前後で保存表現・Repository契約を変えない。
- 状態オブジェクトやListenerへの解決は、保存方式変更を伴わない組み立て境界で行う。
- 仕様変更と関係のないAPI、データ、検証、ログ、結果の差分を作らない。

## 図の品質

- Mermaidブロックを実レンダリングする。
- 改行にはMermaidで解釈できる`<br/>`等を使い、リテラル`\n`を残さない。
- 全ノードを意味のある関係へ接続する。
- クラス図、変更影響グラフ、シーケンス図の目的と読み方を説明する。
- クラス図に、完成コードの型が欠落しない。
- 図にしか存在しない型、浮いている型、実コードと異なる線を残さない。
- 対策検討図と完成図の見た目・定義が理由なく変わらない。

## 読者が考えそうな別案への対応

- 読者が「関数へ切り出せばよい」「ifを別メソッドへ移せばよい」と考える箇所では、なぜ変更理由・知識・所有が元のクラスへ残るか説明する。
- パターン名を先に出して答え合わせにしない。
- 別案が全課題を満たす完成システムなら比較する。
- 部分対策、作れない案、完了条件を満たさない案を長々と比較しない。
- 採用理由は手段の好みではなく、変わる側・守る側・変更影響・所有・実行経路で説明する。

## 章固有の再発防止事項

### 第3章

- キャンセル待ちの自動昇格を、取消操作の内部処理として接続する。
- 利用者が昇格操作を別に呼ぶ構造へ戻さない。

### 第8章

- 未使用入力を完成コードへ残さない。

### 第11章

- 共通生成順、順序付き装飾、完全要求の操作履歴という三つの変化軸を維持する。

### 第12章

- 保存方式に仕様変更がなければ、状態オブジェクト保存等へ勝手に変更しない。

## 情報量ではなく、初見読者の理解で判定する

章の分量、コード量、表や図の数が多くても、読者が次の問いに答えられなければ説明不足である。

- このシステムへ何を指定すると、何が起き、何が出力されるか。
- 現在読んでいるコードは、システム全体のどこにあるか。
- 前フェーズで何が確定し、このフェーズは何を新しく判断したか。
- いま、どの構造変更のどの段階を説明しているか。
- 抽象的には何を分け、具体的にはどのクラス・メソッドを変えたか。
- 分離した部品を誰が生成・注入・所有し、最終的にどう実行するか。

重複した表、結論を増やさない節、「一致している」と宣言するだけの節は削減対象とする。一方、動作イメージ、全体内の現在地、コード間の接続に必要な説明は、短くても省略しない。

## 完了報告で「一致しています」だけを書かない

各章について次の証拠を残す。

| 監査対象 | 証拠 |
|---|---|
| フェーズ間入力 | 前フェーズ末の確定文、次フェーズ冒頭の同一文、追加・言換え理由 |
| 現状動作の入口 | 代表実行結果、結果の読み方、対応する入力・main、後続の詳細仕様 |
| 変更ID | 1-5、仮実装箇所、観測結果、変更影響グラフ |
| 原因→課題 | 痛みのコード、原因、候補評価、課題ID・完了条件 |
| 分離 | 変更前責任、移動先、守る側、部分クラス図 |
| 生成・注入 | 生成者、選択条件、注入元・先、契約型、コード行 |
| 所有・破棄 | 所有者、移動時点、破棄者、コード行 |
| 具体を知らない実行 | 安定側が呼ぶ契約と、具体型判定がないコード |
