# CLAUDE.md - 設計思考を鍛える本

**design-patterns プロジェクト共有の設定ファイル**

## この本の目的

この本は、デザインパターン名を暗記する本ではない。
変更要求を受けたときに、読者が目の前のコードで次を説明できるようになるための本である。

1. 何が変わるのか。
2. 何を変えたくないのか。
3. 変更を試すとどこが痛むのか。
4. 変わる理由が異なる判断・条件・処理順序・生成判断がどこに混在しているのか。
5. 接続点で何を受け渡しているのか。
6. 呼び出し元へどの判断や前提が漏れているのか。
7. どの判断・条件・処理・生成責任をどの責任へ移すのか。
8. 導入コストに見合うか。
9. 変更要求を再度当てたとき、修正・再テスト範囲がどう変わるか。

パターン名は、問題を解いた後で構造を共有するための語彙として扱う。
パターン名から設計を選ばない。

## 冊の構成と正本の所在

1冊が大きくなりすぎたため、冊へ分けて出す。

| 冊 | 収録 | 原稿の場所 | 出版設定 |
|---|---|---|---|
| 第1冊『デザインパターンで学ぶC++ソフトウェア設計』 | はじめに・第0章・Strategy・State・Observer・おわりに・奥付 | `books/volume01-core-patterns/output/` | `books/volume01-core-patterns/publishing/book.json` |
| 第2冊以降 | 未定（`review-tasks.md` の PLAN-001） | 未定 | 未定 |

**第1冊の正本は `books/volume01-core-patterns/output/` である。**
第1冊に収録した章を直すときは、そちらだけを編集する。`output/` の同名章は
分冊の供給元として残すが、第1冊の内容とは一致しない。

`output/` は第2冊以降の素材と、第二部（第9〜12章）の置き場所として維持する。
どちらを直したか分からなくなるため、同じ内容を両方へ手で書かない。

**第1冊へ取り込んだ4章は、`output/` 側が古い。** 初版に向けた修正はすべて分冊側へ入れた。

| 分冊 | 供給元 | 供給元の状態 |
|---|---|---|
| `01-preface.md` | `output/chapter00_1.md` | 古い（矛盾修正・読みやすさ改修が入っていない） |
| `02-chapter00.md` | `output/chapter00_2.md` | 古い |
| `03-chapter01.md` | `output/chapter01.md` | 古い |
| `04-chapter02.md` | `output/chapter03.md` | 古い |
| `05-chapter03.md` | `output/chapter07.md` | 古い |

第2冊を作るときは、**上の5つを `output/` から複製しないこと**。分冊側を起点にする。
`output/` の第2・4・5・6・8章と第二部は、まだ手を入れていないので複製してよい。

分冊を直したら、次を実行する。

```
python script/check_volume.py --config books/volume01-core-patterns/publishing/book.json
```

`validate_book.py` は `output/` の章ファイル名へ規則を紐づけているため、
分冊には当てられない。冊としての成立（収録外の章への参照、参照先の実在、
見出し階層、宣言した件数と表の一致）は `check_volume.py` が見る。

本文を書き替えたときは、あわせて次も実行する。

```
python script/check_flow.py --config books/volume01-core-patterns/publishing/book.json
```

これは合否を出さない。読者がつまずく箇所の**候補**を挙げるだけの道具である
（根拠なしの帰結、宙に浮いた指示語、説明のないコード、用語の先出し、120字超の
一文、実体のない識別子、唐突な数値）。候補は違反ではないので、必ず実物を読んで
判断する。誤検出を減らすより、読む箇所を絞ることを目的にしている。

合否を出す検査は `run_completion_gate.py` が全部呼ぶ。冊ごとに次の6本が走る。

| 検査 | 見るもの |
|---|---|
| `check_volume.py` | 冊としての成立（24観点） |
| `check_code_runs.py` | 掲載コードが動き、載せた実行結果と一致するか |
| `export_sources.py --verify` | 本文のファイル分割どおりに一式がビルドできるか |
| `check_forward.py` | 上から1回読む読者にとっての前方参照 |
| `check_anchor.py` | 本文が挙げる識別子が、その章のコードに実在するか |
| `check_layout.py` | 6インチ端末で崩れる書き方 |
| `check_diagram.py` | クラス図の線が、掲載コードの関係と一致するか |

### 要求は「外から見て何を満たすか」で書く

**内部でどう実現するかは要求ではない。** 「顧客IDから会員種別を取得する」は
割引を出すための手段であって、要求ではない。要求は「未登録の顧客IDでは注文を
受け付けない」のように、**外から観測できる振る舞い**で書く。

判定はこの問いで行う。**「これは利用者や業務が求めていることか、それとも
それを叶えるために内部で必要になることか」。** 後者なら要求IDを立てず、
前者の受入条件か前提として書く。

### クラス図の線は、コードと1本ずつ突き合わせる

図の線は目分量で引かない。**値メンバーは黒ひし形（`*--`）、参照・ポインタの
メンバーは矢印（`-->`）、メソッド内のローカル変数は点線（`..>`）** である。

`check_diagram.py` が、図の1本ずつを同じフェーズの掲載コードへ突き合わせる。
フェーズ1の図は現状コードと、フェーズ7の完成図は完成コードと照合する。
**同名クラスの別バージョンと突き合わせると誤検出になるので、必ずフェーズを
そろえる。**

### IDには短い名前を併記する

`変更ID1（サマーセール追加）` の形で書く。番号だけだと、10ページ先で出てきたとき
「何の話だったか」を読者が戻って確かめることになる。番号のほうを残すのは追跡の
ためで、「要求ID3の受入結果はどこか」を表で突き合わせるとき番号のほうが
取り違えない。表のセルが80桁を超える場合は、そのセルだけ名前を外す。

**この理由は本文へ書かない。** 読者へ書くのは「括弧の中は思い出すための手がかり
で、正式な内容はその番号を確定した節にある」ことだけでよい。

`check_volume.py` の検査25が、名前の無いIDを落とす。

### 第0章は実践章の題材を先出ししない

第0章は各フェーズの**考え方**を述べる場所である。ここで割引計算・チケット予約・
在庫通知を例に使うと、その章を読む前に答えの半分を渡すことになる。例が要るときは、
どの章にも出てこない題材（送料、ログ出力など）を使う。

`check_volume.py` の検査27が、第0章に出た実践章の題材語を落とす。

### フェーズ3は「追跡」であって「実装」ではない

フェーズ3で変更を当てたコードを載せているのは、**どこを触ることになるかの追跡結果**を
見せるためである。**設計せずにコードを書き始める手順ではない。** 次を必ず明示する。

- 多くの場合、1行も書かずに読むだけで済む
- 手を動かすのは読むだけで追いきれないときで、そのときも**捨てる前提**で書く
- ここで書いたコードは**そのまま本実装にしない**
- 大きなシステムでは全部を追わず、影響が止まるところまでで十分

各章の3-1にも同じ断りを置く。**この誤解は本書の主張を反転させるので、
1箇所で断るだけでは足りない。**

### 変更依頼は前提ではない

本書は変更依頼が届いた場面を題材にしているが、**7フェーズは変更が来ていなくても
使える。** むしろ来る前に使うほうが本来の姿である。「変更依頼が来たら」と書かず、
「この変更が来たら」と仮定で書ける形にする。

### 「どうやるか」を書く

各フェーズの考え方には、**判断の手順**を書く。「原因を言語化する」だけでは
何をすればよいか分からない。

| フェーズ | 書くべき「どうやるか」 |
|---|---|
| 3 | 痛みの判定基準（変更の理由と、修正する場所がずれているか） |
| 4 | 原因の見つけ方（処理を並べる→変わるきっかけを書く→違うものが同居していないか） |
| 5 | 完了条件の決め方（原因の裏返し＋コードを見て真偽が言える形） |

**完了条件そのものより、決め方のほうが大切である。** 完了条件が書けないときは
原因の言語化が足りない合図なので、フェーズ4へ戻る。

### 「考え方」は、読む順の指示ではない

第0章の各フェーズは「このフェーズの考え方」を書く。**手順を並べるだけでは考え方に
ならない。** 「1. 全体図 2. 内部図 3. クラス図 4. コード」は目次であって、なぜその
順なのかを書いていない。

書くのは**理由のほう**である。「`if` 文はそれだけ見ても意味が分からない。分岐の
理由はコードの外の仕様にあるから、仕様を先に読む」と書けば、順序は結論として
ついてくる。

あわせて、**その場で守れないことを書かない。** 「どのファイルを開くか」は、
ファイル構成をフェーズ7まで示さない以上、その時点では答えられない。

### 図が一例なのか全体なのかを、図の前に書く

具体的な数値を入れた図は、読者にとって「この1件の話」なのか「いつもこうなる」
なのか判断できない。**代表の1件を通したものなら、そう書く。**
「この図は、代表となる1件の注文を最後まで通したものです。他のケースは1-2の
動作例で確認します」のように、図の前で断る。

### エラー条件は、起きることと動きだけを書く

「どこで分かるか」（検出位置）は実装の話で、仕様を読む段では要らない。
**「こう入力すると、こう動く」の形で書く。**

| 書かない | 書く |
|---|---|
| どこで分かるか：顧客データ取得前 / 出力：未登録顧客エラー / 副作用：なし | 登録されていない顧客IDで注文すると、「登録されていません」と表示して終わります |

無理に項目へ割ると、かえって読みにくい。**共通する結果（「どのエラーでも保存や
通知は起きません」）は、最後にまとめて1文で書く。**

### 図の記法は、図を見れば分かる範囲で済ませる

変更影響グラフのように、箱に「変更要求：〇〇」「クラス名（何が変わるか）」と
書いてある図は、凡例が無くても読める。**記法の一覧表は置かない。** 置くのは
「フェーズ3とフェーズ7で同じ変更を当てて見比べる」という使い方だけで、これは
各フェーズの考え方の側に書く。

クラス図の線のように**見ただけでは分からない**ものは別で、①〜⑥の実例図に加えて、
その線がどんなコードから生まれるかを短いコードで添える。

### 編集の舞台裏を本文へ書かない

読者が要るのは**どう読むか**であって、**なぜそう書いたか**ではない。次は書かない。

| 書かない | 書く |
|---|---|
| 番号だけだと戻ることになるので名前を付けています | 括弧の中は思い出すための手がかりです |
| 紛らわしくならないよう、各章では〜と書いています | （事実だけを書く。理由は落とす） |
| （本書共通のスタイル）（全章共通の規約） | （付けない） |
| 継続のため対照表には載せません | 変更前と変更後が同じなので、下の表には出てきません |
| 存在しない分岐を読者に推測させないためです | （落とす） |

**「読者」を三人称で呼ばない。** 「読者が検算できます」ではなく「その場で検算
できます」と書く。読者を外から語ると、本人に向けた文でなくなる。

例外は「おわりに」で、制作の裏話を意図して置く章である。

`check_volume.py` の検査26が、この書き方を落とす。

### 掲載コードの見出しは1ブロックに1つ

コードと実行結果は画像として組まれ、**題名は画像の中の帯へ焼かれる**。
`build_epub.py` が直前の見出しか太字行を題名として取り、**その行を本文から
取り除く**ので、原稿では今までどおり `**ここで確認するコード：`X`**` を
コードの直前へ置けばよい。同じ題名が本文と画像で二重に出ることはない。

題名を取れる形は次の3つで、上から順に試す。

1. 直前の見出し（`##` 〜 `######`）
2. 直前の太字だけの行（`**Order**`、`**ここで確認するコード：`X`** ―― 説明`）
3. コード自身が定義している型・関数の名前（`class X` → `X`、`main()` など）。
   実行結果は `--- 行N` があれば「実行結果」、罫線があれば「構成図」

3まで用意しているのは、直前が普通の文になっている箇所でも題名を落とさない
ためである。**題名のある画像とない画像が混ざると、読者は画像の位置づけを
毎回読み取り直すことになる。**

### 6インチ端末で崩れない書き方

Kindleの本文幅は端末と文字サイズで変わる。紙の幅を前提にした書き方はしない。

- **手順を1行へ横に詰めない。** 「A（説明）→ B（説明）→ C（説明）」は、折り返すと
  段の頭が見えなくなる。3段以上で段ごとに補足が付くものは、縦の番号付きリストにする。
- **改行できない欧文を40桁以上つなげない。** 日本語はどこでも折り返せるが、欧文は
  語の途中でしか切れない。6インチ端末の1行はおよそ35桁なので、40桁を超えると
  必ず名前の途中で割れる。`Class::method(引数)` が長くなるときは
  「`Class` の `method()`」と日本語で分け、引数は別に書く。長いパスは文中へ埋めず、
  独立した行へ出す。
- **括弧を3重に入れ子にしない。** 折り返されると対応が取れない。
- **言語指定なしのブロック（実行結果・構成図）は80桁以内に収める。** 画像として
  縮小されるため、それを超えると文字が読めない大きさになる。

### 読者は上から1回だけ読む

答えを先に出さない。とくに**フェーズ1〜5で、完成後のクラス名を並べない**。
ファイル分割の表・完成構造の一覧は、フェーズ7の完成コードより後に置く。

初出の識別子には、その場で役割を添える。本書で「紹介した」と見なす形は次の5つで、
`check_forward.py` もこれを基準にしている。

- クラス一覧表の行（クラス名・役割・担当する仕様）
- 「ここで確認するコード：`X`」の直後にそのコードが続く
- 「◯◯（`X`）」——括弧の前に役割を書く
- 「〜を受け持つ `X`」——直前の修飾句で役割を述べる
- 「第N章の `X`」——先の章のものだと断る

### 設計の説明は、コードのどこの話か分かるように書く

「責任を分ける」「知識が漏れている」は、それだけでは読者がどこを見ればよいか
分からない。設計を言葉で説明する段落には、クラス名・メソッド名・行の内容の
いずれかを置き、**その章に実在するコード**を指す。

## 出版・EPUB生成

EPUB、MOBI、PDF、Kindle向けHTMLの作成・再生成・表示調整を依頼された場合は、独自の変換スクリプトを新しく作る前に `publishing/README.md` と `publishing/book.json` を読む。出版処理の正本は `script/build_epub.py` である。

この出版パイプラインは、各章の概要スライド、Mermaid図、コード／実行結果をPNG化してから本文へ結合する。コード画像はC++等の言語を判定して配色し、長いブロックをKindle向けの高さへ分割する。原稿Markdownを画像参照へ書き換えず、生成物は `publishing/dist/` だけへ出力する。

出版作業では、次の順序を守る。

1. `python script/build_epub.py doctor` でPython依存関係、`wkhtmltoimage`、`mmdc`、`ebook-convert`を確認する。
2. `python script/build_epub.py inventory` で章数、コード数、Mermaid数、未配置の概要スライドを確認する。
3. 概要スライドPDFを受け取った場合は、`python script/build_epub.py slides --pdf "<PDF>"` で章別PNGへ分割し、画像を目視確認する。
4. `python script/build_epub.py all --clean` でHTML、EPUB、MOBI、PDFを生成する。
5. `publishing/dist/build-manifest.json` と生成ファイルを確認し、その後Kindle Previewerで端末別表示を確認する。

`publishing/dist/` はGit管理対象外である。概要スライドの元PNGは `publishing/slides/` に置き、章とPDFページの対応は `publishing/book.json` の `slidePageOrder` を正本とする。

## 7フェーズ

| フェーズ | 目的 | 主な出力 |
|---|---|---|
| 1：現状把握 | 1-1冒頭で入力・主要処理・出力・掲載コードの代替をつかんでから、現行要求ID、仕様、動作、登場クラス、現状コード、変更IDを事実として読む。変更依頼を反映した最終要求ベースラインをコード変更前に確定する。「変化の軸」「責任外」「混在している」などの判断は書かない（フェーズ4以降で書く） | システム全体の要約、変更前／変更後の要求ベースライン、仕様構造、動作例、責任一覧、現状コード、変更差分 |
| 2：仮説立案 | フェーズ1の事実から見当を立て、未確定点を質問へ変換してからヒアリングし、今回確実に変わることと将来リスクを分ける | 仮説、ヒアリング質問表、回答と確認結果、確定変更、将来リスク |
| 3：問題特定 | 今回の変更IDを試し、修正・確認・再テスト範囲として痛みを確認する | 変更後コード、変更影響グラフ、痛みの言語化 |
| 4：原因分析 | 混在する判断・処理・生成判断と、接続点へ漏れている前提を言語化する | 原因表、分離すべき知識、漏れている前提 |
| 5：課題定義 | フェーズ4で確定した原因から課題候補を洗い出し、システム全体で必要性・重複・統合／分割・完了条件を検討した後、解くべき接続点を課題ID1からの連番で確定する。対策の形（クラス・置き場所・繋ぎ方）は書かない | 課題候補の検討、接続点定義表、システム全体の課題 |
| 6：対策検討 | 確定した各課題から、分離方法・配置場所・組み立て方法を決める。契約・具体・生成／所有・受け渡し・公開入口からの実行を一本の構想へまとめ、その構想を成り立たせる要点コードを同じ順で続けて示す。責任配置や依存が異なる完成構造が複数残る場合だけ比較する | 三つの設計決定、構想の対応表、要点コードと確認 |
| 7：対策実施 | 実装・実行し、最終要求ベースラインの全要求IDを受入・回帰エビデンスで確認する。変更IDは変更影響の比較に使い、課題IDは構造改善の結果に使う | 最終コード、要求ID別受入・回帰エビデンス、課題ID別構造結果、シーケンス図、改善後影響グラフ、変更シナリオ |

各フェーズは、前フェーズの出力を次フェーズの入力として使う。
論理の飛躍がある場合は、フェーズの入力または加工が足りない。

## 目的と達成基準

各標準見出しの直下に、本文へ出さない執筆用コメントとして `目的` と `達成基準` を置く。

- 目的：なぜこの項目を置くのか。
- 達成基準：この項目を読み終えた読者が何を説明・予測・判断できる状態になるべきか。

目的を達成しない説明、図、表、コード、実行結果は入れない。
達成基準に関係しない一般論や先取りは削る。

## 図のルール

文章だけで全体像を説明しきろうとしない。
次は、できるだけ図または表で先に見せる。

- 入力→加工→出力の流れ。
- クラス間の責任と依存。
- 変更影響の広がり。
- 接続点で流れる値・型・操作・イベント。
- 改善前後の差分。
- 責任がどこからどこへ移ったか。

図の前には目的を1文で書く。
図の後には、図から読み取るべき結論を1〜3文で回収する。
図だけで新しい仕様や判断を初出ししない。

クラス構成図の節では、Mermaid図の**前**にクラス一覧表（クラス名・役割・担当する仕様）を置く。図を見る時点で各クラスが何をするかを把握できていないと、矢印の意味が掴めない。
クラスの責任一覧は1-3に一度だけ置く。1-4へ責任表を再掲しない。1-4は現状コードと、そのコードを読むのに要る実データ表（顧客・カテゴリ・メニュー・連携先などの登録済みデータ）だけを置く。

完成クラス図はフェーズ7「対策実施」に一度だけ置き、フェーズ6「対策検討」は構想表と要点コードで生成から実行までを確定する。課題の中心となるクラス・契約・依存は完成図で色を付ける。`main()` をクラスとして描かず、実クラスである組み立て役は、その所有・登録関係を完成図へ描く。

完成クラス図を突然提示しない。フェーズ6では、責任、継承、実装、保持、依存を変える理由と対応コードを順に示す。フェーズ7の完成図は、その判断と同じクラス名・関係をまとめ、完成コードとの照合に使う。メソッド内部だけの変更で静的構造が変わらない場合は、不要な関係を足さない。

## フェーズ間整合

各フェーズ単体の達成基準を満たしていても、フェーズ間で対象がずれていれば不合格とする。
仕様、要求ベースライン、動作例、コード、実行結果、クラス構成図、変更依頼、変更影響グラフ、最終コードは同じ対象を追う。
要求の追跡と設計課題の追跡を一つの行へ強制的に結合しない。`要求ID → 最終コード → 受入・回帰エビデンス` は要求の過不足と既存動作の消失を確認し、`課題ID → 構造差分 → コード → 変更影響` は設計課題の解消を確認する。課題IDは`変更ID→変更試行→痛み→原因`からだけ導く。要求IDと課題IDを直接対応させない。まとまった働きを束ねる機能IDは設けず、既存動作の維持・消失は要求IDの受入・回帰エビデンスで確認する。
実行結果は、どのコード・どの動作例ケース・どの確認目的に対応するかを見出しまたはラベルで明示する。

詳細な照合基準は `rules/phase-consistency-check.md` を参照する。

## 仕様粒度と簡略化

仕様は、コードを読むための地図である。
入力→加工→出力の図は分かりやすいだけでなく、後続コードに出る値、状態名、フラグ、判定条件、出力名、エラー条件へ紐づいていなければならない。図に置いた各要素は、後でどの動作例・`main()`・実行結果・変更要求・接続点で使うかを対応表で示す。後で使わない要素は図から外し、後で必要な要素が漏れている場合は仕様説明へ戻して追加する。

掲載コードで `print`、固定データ、スタブ、簡略化した `main()` を使う場合は、実システムの画面、DB、外部API、ファイル出力、通知などの何を代替しているかを本文または図で示す。
1-1では、代表操作の`main()`抜粋と、その呼び出しが生む実行結果を一組にして見せる。複数回呼ぶ場合は「全呼び出し→全結果」とまとめず、1回目の呼び出し→1回目の結果→2回目の呼び出し→2回目の結果、と隣接させる。結果の説明は、その出力に現れた事実だけを「結果から分かること」とし、内部状態や処理はコード・状態表から分かることだと書き分ける。その後「最初にシステム全体をつかむ」で入力・処理・出力・掲載コードでの代替を示す。

掲載コードではlambdaとスマートポインタ（`unique_ptr`、`shared_ptr`、`make_unique`）を使わない。生ポインタが所有するオブジェクトは所有者のデストラクタで破棄し、借用参照とは本文で区別する。用語の説明は第0章に置き、各章の設計説明へ未説明のC++記法を突然持ち込まない。
省略した要素は、存在しないものとして扱わず、この章の設計論点では扱わない範囲として明示する。
論点から外す処理は、実際の動き、掲載コードでの代替表現、割愛する理由、設計論点への影響がないことを補足する。

`main()` はビジネスロジックの詳細を知ってはいけない。バリデーション（存在確認・残高チェック・状態チェック等）は呼び出し先のクラス内部で行う。掲載例で `main()` を Composition Root として使う場合は、完成した部品の生成・所有・注入と「どのユースケースを実行するか」を担当する。登録順や組み合わせが競合時の優先関係を表す場合、その業務方針は専用の組み立てクラスへ置き、`main()`に具体クラス名と順序を並べない。業務上の選択条件や後続処理も、`main()`の手動処理で補わない。

動作テーブルには実際のデータ（口座名・残高・イベント名など）を含め、エラーの根拠が読み手に分かるようにする。抽象的な仮番号（12345678など）は使わない。

実行結果は正常フローだけでなくエラーケースも含む複数シナリオを示す。各シナリオに `--- 行N: 説明 ---` のラベルを付け、実行結果を読むだけでシステムの動作が把握できるようにする。同じ実行から枝分かれする派生ケースは `--- 行Na: 説明 ---` `--- 行Nb: 説明 ---` と枝番で表し、後続の通し番号はずらさない。ラベルは掲載コードの `std::cout` が実際に出力する文字列と一致させる。`--- シナリオN ---` など他の形を混ぜない。

## 執筆ルール

- 既存コードを否定しない。
- 一つの正解を押しつけない。
- 架空の著者体験を書かない。
- 「変更がゼロ」「絶対に壊れない」と断定しない。
- 組み立て、登録、設定、テストに残る変更を隠さない。
- コードは実行可能にし、掲載した出力と照合する。
- AIへの指示文や引用マーカーを本文へ混入させない。
- 「ここでは〜しません」「まだ〜を決めません」のような執筆手順を本文へ書かず、現在確認する事実・目的・次に確定する対象を直接書く。
- `★` 指摘を消す場合は、指摘内容・判断・対応先を `review-tasks.md` 等へ残す。

## Agent の扱い

`agents/` 配下の各 Agent は、テンプレートを正本として使う。
過去章や古いステップ番号を正本にしてはならない。
Agent が章をレビューするときは、`rules/checklist.md` の読者体験、図解、フェーズ別の基準を必ず確認する。
Agent の記載が `AI_HANDOFF.md`、`templates/chapter-template.md`、`rules/checklist.md` と食い違う場合は、Agent 側を疑い、正本へ合わせる。

## 完了条件

章またはルールを修正したら、次を確認する。

1. `templates/chapter-template.md` と第0章が矛盾していない。
2. `rules/checklist.md` が同じ基準を持っている。
3. `rules/phase-consistency-check.md` の照合ラインを満たしている。
4. 仕様がコードに出る値・状態・判定条件・出力名へ紐づく粒度になっている。
5. 掲載コードの簡略化範囲が本文または図で説明されている。
6. 論点から外す処理の実際の動き、代替表現、割愛理由、設計論点への影響が補足されている。
7. `agents/` と `skills/` に古い構成名や古い判断基準が残っていない。
8. 修正の原因を分析し、再発しうるなら正本（テンプレート・ルール・Agent・検証スクリプト）を見直し、`rules/recurrence-prevention.md` に記録した（詳細は同ファイル）。
9. `script/validate_book.py` が通る。
10. `script/audit_book.py --write-baseline` が0件で通る。
11. `git diff --check` が通る。
12. フィーチャーブランチへのプッシュだけでなく、`main` へのマージ・プッシュまで完了した。
13. 現行／変更後の要求IDがあり、継続・変更・追加・廃止が明示され、最終有効要求IDすべてにコードと受入・回帰エビデンスがある。追跡は要求ID・変更ID・課題IDで行い、機能IDは設けない。既存動作の維持・消失は要求ID別の受入・回帰エビデンスで確認する。
14. 原因→課題候補→システム全体での検討→課題確定の過程があり、原因から課題IDへ直接飛んでいない。
15. 執筆用テンプレートの穴埋め（`【確認方法】` のような未記入の角括弧）が本文に残っていない。読者向けの説明と、書き手への様式指定を混ぜない。
16. 種類の違うID（問題・原因・課題）を「＝」で結んでいない。導出の向きが分かる書き方にする。
17. 他の章・「はじめに」・「おわりに」の話題を名指しする文が、実際にその参照先を指している。
18. フェーズ6は構想の対応表と要点コードで生成から実行までを確定し、クラス図はフェーズ7の完成図に一度だけ置く。完成図のクラス集合が完成コードと一致する（省略する場合は理由を書く）。Mermaid全図が実レンダリングでき、注記内に未解釈の `\\n` が残っていない。
