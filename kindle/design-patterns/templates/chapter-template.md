# デザインパターン章テンプレート

このファイルだけを章構成の正本とする。第1章を含む各章は、次の見出し名・
順序・役割に合わせる。第1章は実装例であり、正本ではない。
章固有の補足が必要な場合は、標準見出しを増減させず、その配下に`#### 補足：...`として置く。

このテンプレートは、第0章で説明した「7つのフェーズ」を各章の本文へ落とすための
執筆用設計図である。第0章は読者向けにフェーズの意味を説明する。こちらは執筆者向けに、
各項目の目的、達成基準、必要素材を定義する。第0章の思想とこのテンプレートが食い違う
場合は、両方を見直してそろえる。

章を量産するときは、まず次の入力をそろえる。不足している入力がある場合は、本文で
推測して埋めず、章の題材設計に戻って補う。

| 章作成の入力 | 必須内容 |
|---|---|
| 題材システム | 利用者、目的、扱うデータ、現在の仕様、フェーズ1の現状コード |
| 題材のコア処理 | その題材で読者が最も気にする実処理、処理順序、状態、失敗、非同期、外部連携、手段別の入力差分 |
| この章が扱う複雑さ | 順次実行、非同期/ポーリング、イベント、部分失敗、ジョブ/スレッド、再試行など、この章の設計判断に効く複雑さ |
| 仕様粒度 | 動作例・変更要求・実行結果に出る入力値、状態名、フラグ、ID、金額、判定条件、出力名、エラー条件 |
| 代表動作 | 入力、操作、出力、状態変化、エラー条件、実行結果 |
| 登場クラス | クラス名、責任、主な依存関係、`main()` での使われ方 |
| 現行要求 | 要求ID1から連番を付けた変更前システムの要求と受入条件（まとまった働きを束ねる機能IDは設けない） |
| 変更依頼 | 変更ID1から連番を付けた今回の変更内容と、対象要求ID・影響する要求ID |
| 変化情報 | どの機能・仕様が変わるか、変更契機、変更頻度、将来リスク、分かる場合は担当者・関係者 |
| 簡略化方針 | 実システムでは存在するが掲載コードでは省略するDB、画面、外部API、ファイル出力、通知など |
| 論点外補足 | 実際はどう動くか、掲載コードでは何で代替するか、なぜ章の論点から外すか |
| 制約 | 性能、メモリ、互換性、納期、既存コードを保つ範囲 |

各フェーズは、前フェーズの産物を次フェーズの入力にする。章を書くときは、次の
入出力が本文上で回収されているかを必ず確認する。

| フェーズ | 入力 | 産物 |
|---|---|---|
| 1：現状把握 | 題材システム、現行要求ID、代表動作、登場クラス、現状コード、変更ID | 入力→加工→出力の仕様構造、現行要求ベースライン、動作例、責任一覧、変更後要求ベースライン |
| 2：仮説立案 | フェーズ1の事実、変更ID、関係者情報 | 確定した変更内容、リスクIDを付けた将来リスク、変えられるようにする部分、当面守る部分 |
| 3：問題特定 | 変更ID、フェーズ1の現状コード | 今回の変更で実際に生じた修正箇所、波及範囲、再テスト範囲 |
| 4：原因分析 | フェーズ3の痛み、変更理由、コード構造 | 混在している判定/処理/生成判断、漏れている依存、保ちたい処理の骨格 |
| 5：課題定義 | フェーズ4の原因、接続点候補、制約 | 課題候補、システム全体の候補評価、課題ID付き接続点表と完了条件 |
| 6：対策検討 | フェーズ5の候補評価、確定課題表、システム全体の完了状態 | 分離方法・配置場所・組み立て方法、採用全体図、判断ごとの部分クラス図、段階コード |
| 7：対策実施 | フェーズ6の採用案、変更後要求ベースライン | 改善後コード、要求ID別受入・回帰エビデンス、課題ID別構造結果、変更ID別変更影響、得たもの/諦めたもの |
| 整理・振り返り | フェーズ1〜7の産物 | 問題・原因・課題・解決策の鎖、責任の移動、章冒頭の約束の回収 |

量産時の完了条件:

- 各フェーズの入力が、前フェーズの産物または章作成の入力から来ている。
- 産物が次フェーズの本文で実際に使われている。
- 目的、達成基準、本文、図、表、コード、実行結果が同じ読者状態へ向いている。
- 1-1の仕様が、動作例・変更要求・実行結果に出る値・状態・判定条件・出力と紐づく粒度になっている。入力・加工・出力の各要素は、後でどの動作例・変更要求・接続点で使うかまで示す。クラス名・メソッド名・変数名との対応は1-3以降で扱う。
- 題材のコア処理が、単なるハンドリング・分岐・分類箱に薄められていない。実際のシステムで読者が気にする処理順序、必要データ、状態、失敗、非同期、外部境界を、章の論点に必要な粒度で仕様とコードに残す。 具体的な判定は `rules/checklist.md` の「実システム化ルーブリック（R1〜R5）」で行う：R1 要求／結果オブジェクト、R2 順序を持つ手順、R3 保存データ＋境界、R4 成功／保留／失敗・非同期、R5 代表ケースと全量表の分離。
- 「この章が扱う複雑さ」が、章の中心課題に関係する範囲で扱われている。順次実行、非同期/ポーリング、イベント、部分失敗、ジョブ/スレッド、再試行などを足す場合は、それがフェーズ4の原因、フェーズ5の課題、フェーズ6の対策比較にどう効くかまで示す。複雑さを足しても課題に影響しない場合は、論点外として本文へ入れない。
- システム構成が同期呼び出しやポーリングだけに固定化していないか、`rules/checklist.md` の「システム構成の多様化チェック（ARCH）」で確認する：ARCH-01 イベント駆動、ARCH-02 別スレッド／ワーカー（実スレッドを使わずキューと結果オブジェクトで表す）、ARCH-03 構成の固定化回避、ARCH-04 ロールバック／補償と中断。
- 仕様が分かりづらい原因は、情報不足ではなく対応の断絶である。入力・判定・加工・正常出力の各要素が、動作例・コード・変更要求・接続点のどこで再利用されるかを追える状態にする。異常系は正常系図に混ぜず、エラー条件表で追える状態にする。
- 仕様、動作例、コード、実行結果、クラス構成図、変更要求、変更影響グラフ、最終コードが同じ対象を追っている。
- `rules/phase-consistency-check.md` の照合ラインで、フェーズ間の不一致がない。
- 全体像、入出力の流れ、クラス間の関係、変更前後の差分、変更影響の広がりは、文章だけで説明せず図または表で先に見せる。
- パターン名や一般論が、問題・原因・課題の説明より先に判断理由として出ていない。
- 「知識」「案」「痛み」「コスト」「責任」などの抽象語は、本文中で具体物に置き換えられている。
- 専門用語・略語・英語由来の呼び名は、初出で意味を説明する。説明なしで使うより自然なら、一般的な日本語へ言い換える。

図で示すべき箇所:

| 箇所 | 図の役割 | 推奨形式 |
|---|---|---|
| 1-1：仕様 | 入力→加工→出力の全体像と、各要素が後で使われる場所を示す | flowchart + 対応表 |
| 1-5：変更要求 | 変更後の入力→加工→出力を1-1と同じ形式で示し、1-1との差分を明示する | flowchart（1-1と同じ記法） |
| 1-3後：簡略化範囲 | 実システムの要素と掲載コードで代替する要素を、クラス構成を見た後に示す | graph または表 |
| 1-3：登場クラスとクラス構成図 | クラス責任を読んだ後、依存関係を示す | classDiagram / graph |
| 3-2：変更影響グラフ | 直接変更と巻き込まれた変更を区別する | graph |
| 4：原因分析 | 混在している判定/処理/生成判断と、漏れている依存を示す | graph / 注釈付きコード |
| 5：課題定義 | 解くべき接続点と、境界を流れる値・型・操作、変わる側・守る側を示す | 表 |
| 6：対策検討 | フェーズ1のクラス図を、分離・配置・組み立ての結論として更新する | 変更前後のclassDiagram / 対応表 |
| 7-1：完成後の実行シーケンス | 完成コードを読む前に、改善後の呼び出し順を示す | sequenceDiagram |
| 7-3：変更影響グラフ（改善後） | 改善前後で変更範囲がどう減ったかを示す | graph / before-after 図 |

図を置くときの条件:

- 図の前に、読者が図を見る目的を1文で書く。
- 図に出るクラス名・値・状態名は、本文または表で説明済みにする。
- 図の後に、図から読み取るべき結論を1〜3文で回収する。
- 図だけで新しい仕様や判断を初出ししない。
- 図が細かくなりすぎる場合は、全体図と補足図に分ける。

各フェーズ・各項目は、理解を一段進めるために置く。フェーズ見出しは上表の
入力/産物と矛盾させない。すべての標準見出しの直下に
執筆用コメントとして「目的」と「内部基準」を置く。目的には「なぜこの項目を置くのか」
を、内部基準には「この項目で説明・予測・判断できるようにすること」を明記する。
目的が先にあり、内部基準はその目的を満たすための確認観点として定義する。
このコメントは本文にそのまま出さず、本文・図・表・コード・実行結果によって自然に満たす。

本文では、各項目の冒頭または末尾で「前の項目で何が分かったか」「だから次に何を見るのか」を1〜2文でつなぐ。つながりを書けない場合は、項目の順序が早すぎる、別フェーズへ移すべき内容である、または章の目的に不要である可能性がある。

本文を作るときは、各項目について次の順で確認する。

1. 目的：この項目は読者の理解を何のために進めるのか。
2. 内部基準：この項目で何を自分の言葉で説明・予測・判断できるようにするか。
3. 必要素材：その状態にするために、仕様・図・表・コード・実行結果のどれが必要か。
4. 整合性：前後フェーズの仕様・クラス・動作例・変更要求・コードと食い違っていないか。
5. 不要素材：目的にも達成基準にも効かない説明、先取り、一般論が混ざっていないか。

過去の `★` 指摘から、特に次の観点を必ず確認する。

- 本文で使うID、状態名、フラグ、入力値、金額、エラー条件は、コードや実行結果に出る前に仕様または動作例で説明する。
- 仕様はコードを読める粒度まで具体化する。コードに現れる値・状態・判定条件・出力名が、仕様で説明されていない状態にしない。
- 1-1の現状仕様図には、1-5以降の変更要求で初めて登場する入力・出力・履歴・Undo・通知などを混ぜない。変更後の図は1-5で、1-1と同じ粒度で差分として示す。
- 完成コードにだけ見える要素を、直ちに「変更後の新要素」と判定しない。変更要求を根拠に、今回変える要素と、前後で維持する共通基盤（保存方法、結果契約、検証、履歴、内部デバッグログ、既存の外部境界）へ先に分類する。共通基盤は現状仕様・現状クラス・現状コードにも置く。
- ログは用途で分ける。処理経過を調査する内部デバッグログ、業務上の監査ログ、再実行などの正本になる操作履歴を同一視しない。内部デバッグログが仕様変更前からあるなら、要求IDへ追加せず、現状コードから完成コードまで同じ内部基盤として維持する。
- 1-2の動作例は、フェーズ1の現状コードで確認できる代表ケースを基本にする。最終コードで初めて実現する動作は、変更要求後またはフェーズ7の確認表へ分ける。
- 掲載コードで `print`、固定データ、簡略化した `main()` を使う場合、実際のシステムでは画面・DB・外部API・ファイル・通知などの何を代替しているかを全体図または表で示す。コードを実行して生成・更新されるものと、実際には生成・送信されないものを具体名で区別し、ログだけで実物のPDF・Excel・メール・API送信が完了したように書かない。
- 掲載コードではlambda、`std::unique_ptr`、`std::shared_ptr`、`std::make_unique`を使わない。生ポインタを所有するクラスはデストラクタで破棄し、非所有参照とは本文で区別する。これらの標準ライブラリ用語は第0章で補足するが、設計説明の途中へ新しい所有権記法を持ち込まない。
- 外部処理を `print` で直書きして終わらせない。実システムではAPI、DB、ファイル、通知、描画ライブラリなどを呼ぶ箇所は、掲載コードでも `Repository`、`Client`、`Gateway`、`Renderer`、`Notifier` などの境界クラスまたはインターフェースを呼ぶ形にし、その先のスタブ実装だけを `print` にする。
- 保存を伴う境界クラスは、`print` で捨てるのではなく、実行終了まで状態を覚えるインメモリ保存（`std::map`/`std::vector` 等、必要なら `static`）にし、`save()`/`add()` と `get()`/`find()` を持たせる。読者が `main()` を組み替えてデータを足すと挙動が変わるようにする。各章コードは1つの `.cpp` としてそのままコンパイル・実行でき、章内に「手元で動かすには（`g++ file.cpp -o app && ./app`、`main()` を編集して再実行）」の注記を置く。`std::map`/`std::vector`/`<fstream>` は標準ライブラリなので可、外部DB/APIフレームワーク知識は依然禁止。永続化は不要（実行中だけ保持）。
- 題材の中心となる処理を、都合よく同じ引数・同じ戻り値にそろえない。種類ごとに必要データや制約が異なる場合は、要求オブジェクト、結果オブジェクト、状態、イベントなどで差分を表し、どこを共通契約として残すかを説明する。
- 仕様図が代表ケースなら「代表ケース」と明記し、全種類を示す必要がある値・設定・状態は別表で網羅する。コードに登録されるID、状態、フラグ、手数料、形式、通知先などは、仕様表と一致させる。
- 実システムで認証、外部APIの連続呼び出し、非同期完了、失敗照会、リトライなどが題材の痛みに関係する場合は、簡略化で消さず、境界クラス・状態・結果で表す。論点外なら、その処理が後続の原因・課題・対策に影響しない理由を書く。
- 複雑度を上げた場合は、「複雑度が上がっても同じ論理で対策できること」を章内の整理または変更シナリオ表で回収する。少なくとも、追加した複雑さ、見えた原因、定めた課題、採用した構造の対応が分かる表を置く。
- 簡略化した範囲は「省略したから存在しない」のではなく、「この章の設計論点では扱わない」と明記する。
- 論点から外す処理は、実際の動き、掲載コードでの代替表現、割愛する理由、設計論点への影響がないことを補足する。
- DB保存、API呼び出し、メール/チャット通知、ファイル出力などを省略する場合は、成功時に何が保存・送信され、失敗時にどう扱うのか、処理時間・タイムアウト・リトライ・非同期化が設計論点に入るのかを確認する。論点外なら、なぜ本文では扱わないかを書く。
- 動作例テーブル、`main()`、実行結果は同じケースを同じ粒度で対応させる。計算式や対象データが読者に推測任せにならないようにする。
- 実行結果には、どのフェーズ・どのコード・どの動作例ケースを実行した結果かを見出しまたはラベルで明記する。
- 「現状コード」とだけ書くと対象がぶれる場合は、「フェーズ1の現状コード」「フェーズ3の変更途中コード」「フェーズ6の検討案コード」「フェーズ7の最終コード」のように、対象フェーズを付ける。
- 複数の実行結果を並べる場合は、ケース名または番号と区切り線を入れ、読者がどこからどこまでが1つの結果か迷わないようにする。略語だけのケース名は避け、「ケース1：予約して支払う」のように内容が読める名前にする。
- 登場クラス表、クラス構成図、掲載コード、シーケンス図に出る主要クラス名は一致させる。存在しないクラスを図に出さない。
- 変更要求、変更後コード、変更影響グラフ、改善後シナリオ表は同じ変更要求を扱う。途中で別の要求にすり替えない。
- 登場クラスの責任説明はクラス構成図より前に置く。図は責任を理解した後に依存関係を確認するために使う。
- 1-3で登場クラスとクラス構成を説明する前に、具体的なクラス名、メソッド名、状態定数、変数名、コード風の出力文字列を本文へ出さない。1-1〜1-2では仕様語彙と日本語の操作名で説明する。
- クラス図に出した関数名・変数名は、クラス図の直後から説明してよい。ただし、その関数や変数の中でどんな条件分岐・計算・生成・例外処理をしているかは、実装コードを提示した後に説明する。
- 「一般的」「業界標準」「現場ではよくある」と断定しない。根拠を示せない場合は「この章のシステムでは」「この章では〜として扱う」と範囲を限定する。
- フェーズ2は、フェーズ1の事実から仮説を立て、ヒアリングで裏付け、変わる見込み/当面安定の前提を確定する流れにする。
- フェーズ2の出口で、今回確定した変更ID、将来リスク、実装上の内部契約、今回の対象外を明確に分ける。フェーズ3へ変更として渡すのは変更ID、フェーズ6へ設計条件として渡すのはリスクIDであり、未確定の将来機能を完成コードへ先回りして入れない。
- フェーズ2では「混在」「適切/不適切」「違反」といった原因判定をしない。仕様の値・条件・加工が変わりそうかを、仕様図・動作例・コード上の場所に対応づける。
- フェーズ5では、原因から課題候補を洗い出し、システム全体で必要性・重複・統合／分割・完了条件を検討してから課題IDを確定する。抽象メソッド、サブクラス名、デザインパターン名、最終クラス名などの対策を先に書かない。
- フェーズ6では、分離方法・配置場所・組み立て方法を先に確定する。その結果、責任配置や依存関係が異なる完成構造が複数残る場合だけ比較する。途中状態や、課題を一部しか解かない案を比較対象にしない。

**この章での簡略化**

掲載コードが実物として行うこと、別の手段で代替すること、扱わないことの境界を明示する。

この節では現状コードの境界だけを説明する。変更要求、対策後のクラス名・手順・コード、執筆上の用語選択は先取りしない。変更後に追加の簡略化が必要になった場合は、その要素を初めて扱う節で差分だけを説明する。

| 実システムではどう動くか | 掲載コードでの表現 | 割愛する理由 | 設計論点への影響 |
|---|---|---|---|
| 画面・API・DB・ファイル・通知・描画ライブラリなどで入出力する | 境界クラス/インターフェースを呼び、その先のスタブで `print`・固定データを使う | この章の論点ではないため | 責任分担や変更影響の説明は変わらない |
| 成功・失敗・処理時間・リトライ・非同期化を扱う | 【扱う場合: エラー処理コードを掲載 / 扱わない場合: 補足で本番の扱いを説明】 | 【論点外にする理由】 | 【扱わなくても中心課題の判断が変わらない理由】 |

この表の直後に、掲載コードを実行すると生成・更新されるものと、生成・送信されない実物を具体名で書く。たとえばプレーンテキストの確認用ファイルを作るだけなら「PDF/Excelそのものは生成しない」と明記する。

> 実際のシステムでは【実際の処理】を行います。この章では【境界クラス/インターフェース】を呼び、その先を【掲載コードでの代替】として表します。ここで見たいのは【設計上の論点】なので、【割愛する処理】の詳細は扱いません。

省略した外部境界（DB・画面・API・通知）が実運用で失敗・非同期になりうる場合、その失敗を扱うコードを最低1つ示すか、補足で本番の扱い（例外・リトライ・タイムアウト・非同期）と、境界を流れる値の形（同期の戻り値か、将来値・成否を含む形か）への影響を明記する。処理時間が読者の疑問になりやすい題材では、同期処理で待つのか、ジョブ化するのか、結果だけ記録するのかも補足する。

「変わる見込み＝はい」は、その機能を今回実装するという意味ではない。フェーズ6で、変える側と守る側を分離し、採用構造が影響を局所化できるかを判断するための印である。

これは全章へ空の対象外セクションを強制する規定ではない。並べるべき非目標が実在する章だけがこの一覧を持つ。内部契約や共通基盤の説明に添える「この仕組みはここまでしか扱わない」という一文単位の線引きは、一覧の先出しには当たらず、フェーズ1に置いてよい。

## 🟣 フェーズ3：問題特定 ―― 変更の痛みを発見する

フェーズ3で中心ロジックだけを抜粋する場合は、コードの前に「抜粋の前提（周辺は現状のまま）」を置く。フェーズ1から維持するDatabase / Repository / Registry / Gateway、入力検証、保存・通知・履歴などの副作用を具体名で示し、抜粋の前後で引き続き実行されることを明記する。省略を削除や別仕様として読ませない。

変更要求は、未実装エラーを出すだけで終えず、現在の責任配置のまま**要求が実際に動く状態まで実装して実行する**。その結果、同時に修正したクラス・分岐・復元データ・副作用を変更の痛みとして観察する。要件未実装の失敗を、設計上の痛みの証拠にしない。

変更箇所を示すときは、追加行だけの断片にしない。変更対象のクラス／関数名、既存の類似処理、変更行の前後、呼び出し元と接続先が分かる範囲を掲載する。全コードの再掲は不要だが、コードブロック内の `...` や「既存部分」「同様」は使わない。

変更前コードを批判せず、今回の変更要求を当てたときの修正・再テスト範囲を示す。

## 🟠 フェーズ4：原因分析 ―― なぜ辛いのかを構造で言語化する

<!-- 執筆用：このフェーズの目的・達成基準

### 4-1：痛みの根源を探る（観察と原因）

<!-- 執筆用：この項目の目的・達成基準
目的: 変更が広がった理由を、依存・分岐・責任の混在として観察する。

### 4-2：変わるもの/変わってほしくないもの

<!-- 執筆用：この項目の目的・達成基準

達成基準:
読者が、変更されるべき判定条件・計算式・生成判断などと、保ちたい処理の骨格を区別できる。

全パターン章で、比較表の列見出しは次の2列へ統一する。題材固有の説明や分類は行の内容へ書き、列見出しへ括弧書きや色付き記号を加えない。

| **変わり続けるもの** | **変わってほしくないもの** |
|---|---|

### 4-3：接続点に漏れている判断や前提を確認する

<!-- 執筆用：この項目の目的・達成基準
目的: 境界の外へ漏れているクラス名・生成方法・条件・順序を特定する。
達成基準:
読者が、呼び出し元が相手のクラス名・生成方法・処理順序・条件のうち何を知りすぎているか説明できる。
-->

4-3の題材語は章に合わせてよい。ただし役割は共通とする。

4-3で確認することは、固定リストから選ぶのではなく、4-1/4-2で言語化した原因から抽出する。

抽出手順:

1. フェーズ4の原因文から、守りたい骨格を1文で書く。
2. 同じ原因文から、変わる差分を1文で書く。
3. その差分を動かすために、骨格側が知ってしまっている名前・条件・順序・型を拾う。
4. それを原因タイプに分類し、接続点で見る抽象観点を決める。
5. 接続点に残す最小の約束を、値・型・操作・イベントとして書く。

原因によって、接続点で見る抽象観点は変わる。ただし抽出手順は共通とする。

| 原因タイプ | 接続点で確認する抽象観点 | 具体化するもの |
|---|---|---|
| 判定/条件が漏れている | 条件・定数・選択基準 | `if`条件、比較値、優先順位、対象外条件 |
| 処理手順が漏れている | 呼び出し順・前後条件・失敗時分岐 | open→parse→save→close、リトライ、例外時処理 |
| 生成判断が漏れている | 具体クラス名・生成条件・登録場所 | `new`する型、factory分岐、生成に必要な設定 |
| データ/状態が漏れている | 境界を流れる値・型・状態 | DTO、enum、状態名、フラグ、ID |
| 通知/副作用が漏れている | 通知先・タイミング・成否の扱い | observer、送信先、イベント名、失敗時の扱い |

章本文では、読者が同じ抽出を自分で再現できるように、少なくとも次を明示する。

- 4-1/4-2の原因から、どの骨格と差分を取り出したか
- その原因タイプでは、なぜその抽象観点を見るのか
- 呼び出し元へ漏れているクラス名・生成方法・処理順序・条件
- 境界で本当に受け渡したい値・型・操作・イベント
- 変更要求によって波及する修正・再テスト範囲

固定的な接続分類へ当てはめない。分類名ではなく、今回の原因から「何を知らなくてよい状態にするか」を説明する。

フェーズ4の末尾で、フェーズ3の問題IDに対応づけて、構造上の原因へ`原因ID1`から欠番なく採番し、一覧表で締める。各行は「構造上の原因（何が同じ責任へ集まっているか）」と「対応する問題ID」を持つ。次のフェーズ5は、この原因IDから課題IDを導く。

|---|---|---|
| 原因ID1 | 【一つの責任へ混在している判断・処理・生成】 | 問題ID1 |

## 🟡 フェーズ5：課題定義 ―― 原因から課題を検討して確定する

<!-- 執筆用：このフェーズの目的・達成基準
目的: フェーズ3の変更影響とフェーズ4で確定した原因から課題候補を出し、システム全体で検討して、解くべき接続点と完了条件を確定する。
内部基準:
- 独立した変化軸へ課題ID1から欠番なくIDを振る。
- 境界を越える値・型・操作・イベント、変わる側、守る側を説明できる。
- 現在の波及と、対策後に目指す状態をシステム全体の課題として書ける。
- 新設クラス、配置先、生成・注入方法などの対策を先取りしない。
-->

### 5-1：原因から課題候補を洗い出す

原因を課題IDへ直接言い換えない。原因ごとに「何が独立して変わる必要があるか」「どの処理を変更から守る必要があるか」「どの境界を見直せば原因が解消するか」を問い、課題候補として置く。この時点では課題IDを確定しない。

| 原因ID・確定した事実 | そのままだと残る痛み | 課題候補 | 候補を導いた理由 |
|---|---|---|---|
| 【フェーズ4で確定した原因】 | 【フェーズ3で観測した波及】 | 【構造名を使わず目指す状態】 | 【変化理由と守りたい範囲から導いた理由】 |

### 5-2：課題候補をシステム全体で評価する

候補を課題別の部分最適として採用しない。候補同士の重複、同じ理由で一緒に変わるか、別々に変わるか、すべて解けば原因全体が解消するかを確認し、統合／分割／除外を判断する。変更IDとの一対一対応は条件にしない。要求を局所変更で満たせて設計上の痛みがなければ、対応する課題IDは作らない。

| 課題候補 | 必要性・他候補との関係 | 統合／分割の判断 | 採否 |
|---|---|---|---|
| 【候補】 | 【原因解消に必要か、他候補とどう関係するか】 | 【統合／分割の判断と理由】 | 採用／除外 |

### 5-3：課題IDと接続点を確定する

1. フェーズ3で当てた変更依頼と、フェーズ4で確定した原因を置く。
2. その要求で変えたい条件・式・状態・手順・生成判断を決める。
3. その要求では変えたくない処理・利用側・既存機能を決める。
4. 両者を結ぶメソッド呼び出し、引数、戻り値、生成、イベントを探す。
5. 変更依頼のたびに具体的な判断が漏れ、修正が波及する境界を接続点とする。
6. 5-2の統合／分割判断後にだけ課題ID1から採番し、完了条件を付ける。

接続点の証拠は呼び出し行だけにしない。呼び出し元が何を知って何を渡すか、接続先が何を実行して何を返すか、その結果を後続の保存・状態・履歴・通知がどう使うかまで、関連コードと説明で一続きに示す。

同じ内容を別の「引き渡し表」や「受け入れ条件表」で繰り返さず、次の一表へまとめる。

| 課題ID・接続点 | 接続するもの・変わる側 | 守る側 | 完了条件 |
|---|---|---|---|
| 課題ID1：【境界】 | **接続:** 【値・型・操作・イベント】<br/>**変わる側:** 【変更される具体的な条件・式・状態・手順】 | 【安定させたい処理・利用側・既存機能】 | 【構造名を使わず検証できる状態】 |

複数の変化軸が同じ変更で一緒に変わるか、別々に変わるかは、フェーズ6で分離単位を決める材料として短く説明する。配置先はまだ書かない。

最後に`📌 **システム全体の完了状態**`として、すべての課題IDを解いたとき、変わる側の変更がどこへ閉じ、守る側がどの詳細を知らずに実行できるかを一文で回収する。

課題IDを確定できたら、5-3の末尾で問題ID→原因ID→課題IDを一列で見渡す通し一覧を置き、フェーズ3の痛み→フェーズ4の構造原因→フェーズ5の達成目標が一本の設計線でつながることを示す。この通し一覧が、そのままフェーズ6の入力になる。

| 問題ID（フェーズ3の痛み） | 原因ID（フェーズ4の構造原因） | 課題ID（達成目標） |
|---|---|---|

#### まず全体像 ―― どんな構造へ変えるか（抽象）

#### 接続点の分離・配置・組み立てを決める

課題ID1〜課題IDnは別々の採用案ではなく、一つの完成システムをコードまで追うIDである。次の左列は、接続点をどのように変えるかを考える観点である。

表の前に、フェーズ5の各Pを次の順序で設計判断へ変換した理由を書く。

1. 各Pの「変わる側」のうち、何を一緒の単位として切り出すか。
2. 「守る側」が知らなくてよい詳細と、境界へ残す操作・値・イベントは何か。
3. 切り出した責任をどこへ置くか。
4. 守る側が具象へ再依存しないよう、誰が生成・所有・登録・選択・注入するか。

次の表を左から右へ読むと、各Pがどの契約・クラス・組み立てコードへ変換されるか分かるようにする。「この章での答え」のような曖昧な列名だけで済ませない。

| 接続点を変える観点 | システム全体での考え方 | コードで確定すること | 追跡する課題ID |
|---|---|---|---|
| 分離方法 | 【境界へ残す共通操作・値・イベント】 | 【契約・公開操作】 | 課題ID1 |

各設計判断の理由を書いた後、次の小節に課題IDごとの部分クラス図を置く。採用全体図より先に、たとえば継承を導入するなら基底クラス、派生クラス、移す操作、継承線だけを示す。依存注入では生成・所有者、契約、利用側の関係だけを示す。部分図は最終構造の抜粋であり、未採用案や試行錯誤の履歴にしない。

#### 課題IDごとに、分離→生成→注入→実行を詳しく展開する

各課題IDへ独立したH3見出し `### 課題IDn：【達成目標】` を置き、その課題だけを最初から最後まで通して解く。順序と要素は全章で共通にする。交互配置の「実装ステップ1/2/3」ではなく、**課題ごとにまとめて**展開する。

各 `### 課題IDn` 節の構成：

1. **【課題IDnの原因】** … 対応する問題ID・原因IDを1行で結ぶ（`変更ID→問題ID→原因ID→課題ID`の線を再掲する）。
2. **この課題（何を解きたいか）** … フェーズ3の痛みとフェーズ4の原因を1〜2文で述べ、何を差し替え可能にするかを言う。
3. **どう解決するか（方針）** … 分離の仕方（構造名＝パターン名）を述べ、「【契約】 →【安定骨格】 →【具体】 →【生成】・所有 →【注入】登録・注入 →【利用開始】 の順で組み立てる」と宣言する。パターン名から設計を選ばない姿勢を保つ。
【契約】〜【利用開始】はそれぞれ別の見出しにし、所属の分かる実コードを付ける。特に【安定骨格】（公開入口の内側にある制御順）と【利用開始】（利用者・外部イベントが公開入口を呼ぶ行）は`【安定骨格】【利用開始】` のようにまとめない。呼ばれる側と呼ぶ側で責任が違う。
課題ID節の締めに、代表ケース1件の実行接続表を置く。列は「実行順・ポイント／掲載箇所／実際のコード接続／次の呼出先」とし、説明順【契約】→【利用開始】に対して実行順は【生成】→【注入】→【利用開始】→【安定骨格】→【契約】→【具体】であることを示す。
4. **部分クラス図** … この課題で新設・変更する契約・具象・利用側だけを抜き出して着色する（採用全体図の抜粋。省略クラスは変更なしと明記）。図の前に着目点、図の後に完了条件への応答を1文で回収する。
5. **【契約】〜【利用開始】のコード** … 次の順で、各ブロックの直前に1文の意図を付けて示す。各番号の役割は省略せず、章固有の名前を添える。
   - **【契約】 共通契約**（interface／抽象基底）を定義する。安定側が呼ぶ最小の操作だけを置く。
   - **【安定骨格】**は、具体実装が増減しても維持する利用側の制御を示す。Template Methodの共通順だけでなく、Strategyの選択・委譲、Observerの登録・反復、Commandの実行・履歴移動などもここへ置く。「骨格なし」として省略しない。
   - **【具体】クラス**が差し替え点だけを実装する（共通順・共通処理は書かない）。
   - **【生成】**：どの具体を生成するかを、生成役（Factory／Assembler／Composition Root）の一箇所へ閉じる。生成した生ポインタの**所有者と破棄先**を明記する。
   - **【注入】**：生成物を安定側へ依存として渡す（コンストラクタ・登録・状態遷移など、章の接続方法に合わせる）。
   - **【利用開始】 実行**：安定側（実行部）が契約だけを呼び、具体を知らずに動くことをコードで示す。

`main()` を架空クラスとして図に描かない。生成・所有・登録・注入・破棄は【生成】【注入】のコードと注記で示す。コードブロック内で `...` や「同様」を使わない。全課題を展開し終えたら、次の小節「システム全体の最終構造を決める（再結合）」で一本の実行経路へ束ね直す。
