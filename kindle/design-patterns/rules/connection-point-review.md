# 接続点を見直すための共通ルール

## 目的

本書では、設計を固定的な接続分類へ当てはめない。

着目するのは、変更要求が通過する**接続点**である。接続点とは、クラスや処理を
分けたときに、値・型・呼び出し・生成責任・処理順序などを受け渡す境界を指す。

## フェーズ4：原因分析で確認すること

1. 変わる理由が異なる判定条件・計算式・処理順序・生成判断が、同じクラスやメソッドに混在していないか
2. 呼び出し元が、相手のクラス名・生成方法・呼び出し順序をどこまで知っているか
3. 一方を変更したとき、変更しない側まで修正・再テストが必要になるのはなぜか

4-3の「確認すること」は、固定リストとして先に決めない。4-1/4-2で言語化した原因から、次の順に抽出する。

1. 原因文から、守りたい骨格を1文で書く。
2. 原因文から、変わる差分を1文で書く。
3. 差分を動かすために骨格側が知ってしまっている名前・条件・順序・型を拾う。
4. 原因タイプに応じて、接続点で見る抽象観点を決める。
5. 接続点に残す最小の約束を、値・型・操作・イベントとして書く。

原因によって抽象観点は変わる。

| 原因タイプ | 接続点で確認する抽象観点 |
|---|---|
| 判定/条件が漏れている | 条件・定数・選択基準 |
| 処理手順が漏れている | 呼び出し順・前後条件・失敗時分岐 |
| 生成判断が漏れている | 具体クラス名・生成条件・登録場所 |
| データ/状態が漏れている | 境界を流れる値・型・状態 |
| 通知/副作用が漏れている | 通知先・タイミング・成否の扱い |

旧来の4分類名は使わず、実際に抱えている判断・前提・処理順序と変更影響を文章で示す。

## フェーズ5：課題定義で確認すること

接続点は、クラス図の線やインターフェース名から探し始めない。フェーズ4の原因から課題候補を出し、次の手順で「解くべき境界」に絞り込む。

1. 変更要求を1つ置く。
2. その要求で変えたい側を決める。
3. その要求では変えたくない側を決める。
4. 変えたい側と変えたくない側が、どのメソッド呼び出し・引数・戻り値・生成・イベントでつながっているかを見る。
5. そのつながりのうち、変更要求のたびに知識が漏れて修正が波及する場所を、解くべき接続点とする。

接続点ごとに次を整理する。

| 観点 | 問い |
|---|---|
| 受け渡すもの | 境界を越える値・型・操作・イベントは何か |
| 変わる側／守る側 | 境界のどちら側が変わり、どちら側を安定させたいか |
| 変化の種類 | その仕様は、どの機能・仕様変更で変わるか。担当者や関係者が分かる場合は補助情報として使う |
| 漏れている判断や前提 | クラス名、生成方法、処理順序、条件分岐のうち何が漏れているか |
| 変更影響 | 要求を1つ当てたとき、どのファイルを修正・再テストするか |

候補はそのまま課題にしない。必要性、重複、依存、独立性、網羅性、完了状態をシステム全体で評価し、統合／分割／除外を決める。成果物は `課題ID・接続点 / 接続するもの・変わる側 / 守る側 / 完了条件` の4列表と、全課題を解いたシステム全体の到達状態を表す一文である。接続するものと変わる側は同じセル内でラベルを付けて改行する。採用候補だけに課題ID1から連番を付け、同じ課題を別表で再定義しない。変更IDと課題IDを一対一に強制しない。

フェーズ5では対策の形を書かない。「どこへ移すか」「何を新設するか」は、フェーズ6で契約と具体、生成・所有・受け渡しをコード化するときに決める。引き渡し表、受け入れ条件表、課題カードを追加して同じ内容を繰り返さない。

## フェーズ6：対策検討で確認すること

フェーズ6はフェーズ5の接続点表から直接始め、契約・具体・生成・所有・登録・選択・受け渡し・実行を含む一つの構想を先に作る。クラス名・メソッド名・生成場所も構想へ書き、全点が同時に成立する案かを確認する。

| 構想の要点 | 決めること |
|---|---|
| 契約と具体 | 境界の形と、その裏で変わる判断をセットで決め、守る処理が契約だけを呼べるか検算する |
| 生成・所有・受け渡し | 具体を作る行から、必要な登録・選択・受け渡しまで同じ実体を追う。登録・選択・注入を区別する |
| 公開入口からの実行 | 生成した同じ実体が契約を経て具体の処理へ届くまでを追う |

構想の直後に、契約→代表具体→生成・選択・受け渡し→実行骨格→公開入口の順で要点コードを続ける。変更前コードをまとめておさらいせず、境界を決める材料となる数行だけをフェーズ3「変更を試みる」から抜き、何を読み取るか説明する。

フェーズ6には完成クラス図を置かない。同型の全具体、完成クラス一覧、全コード、実行シーケンス、実行結果も再掲せず、フェーズ7で一度だけ示す。最後は課題IDとの対応と将来リスクの評価だけで採用を確定する。

分離と組み立てから完成構造が一つに定まるなら比較しない。全課題を解き、責任配置や依存関係が異なる完成可能な構造が複数残る場合だけ、次を比較する。

- システム全体の課題をどこまで満たすか
- 変更要求を再適用したときの修正・再テスト範囲
- 増えるクラス、設定、登録、実行時コスト

## 禁止事項

- 旧来の4分類名
- 固定的な分類マトリクスや到達点
- パターンを固定的な接続分類へ無理に割り当てる説明
- 接続点を見ず、インターフェースや仲介役の有無だけで設計を評価すること
- 「知識」を具体化せず、曖昧なまま対策へ進むこと
