# 接続点を見直すための共通ルール

## 目的

本書では、設計を固定的な接続分類へ当てはめない。

着目するのは、変更要求が通過する**接続点**である。接続点とは、クラスや処理を
分けたときに、値・型・呼び出し・生成責任・処理順序などを受け渡す境界を指す。

## フェーズ4：原因分析で確認すること

1. 各問題IDについて、何を変えたくて既存のどこまで直したかをコードで確認する
2. 関係した責任を、今回変える／守るに分ける
3. 同居や直接依存が問題の理由かをコードで確認し、原因IDを付ける

責任はフィールドやメソッド単位に分けない。同じ業務上の理由で一緒に変わる仕事を一つの責任とし、実務で通じる短い名前を付ける。

境界と、そこを越える情報はフェーズ5で決める。型名・操作名・シグネチャ、生成場所はフェーズ6で決める。

## フェーズ5：課題定義で確認すること

接続点は、クラス図の線やインターフェース名から探し始めない。フェーズ4の原因から、次の手順で「解くべき境界」に絞り込む。

1. 対策前の責任配置を、抽象的な責任名の部分クラス図で示す。
2. 原因をなくす目標配置を、同じ責任名と粒度の部分クラス図で示す。
3. 分けた両側で何を渡し、何を受け取るかを決める。一部だけを分けて原因が残る配置は同じ節で退ける。

接続点ごとに次を整理する。

| 観点 | 問い |
|---|---|
| 受け渡すもの | 境界を越える業務上の依頼・入力・結果は何か |
| 変わる側／守る側 | 境界のどちら側が変わり、どちら側を安定させたいか |
| 変化の種類 | その仕様は、どの機能・仕様変更で変わるか。担当者や関係者が分かる場合は補助情報として使う |
| 漏れている判断や前提 | クラス名、生成方法、処理順序、条件分岐のうち何が漏れているか |
| 変更影響 | 要求を1つ当てたとき、どのファイルを修正・再テストするか |

原因が残らないと確認した目標図の番号へ課題IDを付ける。各課題は`解く原因 / 構造の変更 / 接続 / 完了条件`の短いカードにし、目標構造を別の表や長文で再定義しない。接続では送信元・送信先と`入力`・`結果／反映`を一文で区別する。変更IDと課題IDを一対一に強制しない。

フェーズ5では対策の形を書かない。「どこへ移すか」「何を新設するか」、型名・操作名・シグネチャは、フェーズ6で契約と具体、生成・所有・受け渡しをコード化するときに決める。引き渡し表、受け入れ条件表、課題カードを追加して同じ内容を繰り返さない。

## フェーズ6：対策検討で確認すること

フェーズ6はフェーズ5の責任配置と課題カードの`接続`から直接始める。冒頭では、何を分け、何でつなぐと決めたかと、契約・具体・生成・所有・登録・選択・受け渡し・実行の順でコード構造へ変えることだけを示す。まだ説明していないクラス名・メソッド名・生成場所を完成答案の表として先出ししない。

課題カードで確定した業務上の依頼・入力・結果／反映は、フェーズ6で再選別しない。契約節では同じ文言をC++のクラス／インターフェース、メソッド、引数型、戻り値型へ翻訳する。過不足が見つかった場合はフェーズ5へ戻ってカードを修正する。複数実装を同じ形で扱わない箇所には、形式だけのインターフェースを置かない。

| 構想の要点 | 決めること |
|---|---|
| 契約と具体 | 境界の形と、その裏で変わる判断をセットで決め、守る処理が契約だけを呼べるか検算する |
| 生成・所有・受け渡し | 具体を作る行から、必要な登録・選択・受け渡しまで同じ実体を追う。登録・選択・注入を区別する |
| 公開入口からの実行 | 生成した同じ実体が契約を経て具体の処理へ届くまでを追う |

契約→具体の役割→生成・選択・受け渡し→実行骨格→公開入口の順で、判断理由と要点コードを続ける。変更前コードはフェーズ3「変更を試みる」で確認済みなので再掲せず、クラス名・メソッド名と観測結果を一文で受ける。具体クラスの処理本文はフェーズ7へ置く。

責任の移動、継承・実現、保持・注入を決める箇所では、**いま判断している関係だけ**を部分クラス図で示し、契約のシグネチャ、所有・受け渡し、契約経由の実行を示す最小コードと組にする。図の前で省略対象を明記し、完成構造と誤認させない。フェーズ6には具体クラスの処理本文、完成クラス図、同型の全具体、完成クラス一覧、全コード、実行シーケンス、実行結果を置かない。部分図を統合した完成クラス図はフェーズ7で一度だけ示す。最後は採用構造を短文で確定し、責任→クラス対応を表で繰り返さない。完了条件の合否はフェーズ7で、条件を一つずつ証拠へ照合する。

分離と組み立てから完成構造が一つに定まるなら比較しない。全課題を解き、責任配置や依存関係が異なる完成可能な構造が複数残る場合だけ、次を比較する。

- システム全体の課題をどこまで満たすか
- 変更要求を再適用したときの修正・再テスト範囲
- 増えるクラス、設定、登録、実行時コスト

## 禁止事項

- 旧来の4分類名
- 固定的な分類マトリクスや到達点
- パターンを固定的な接続分類へ無理に割り当てる説明
- 接続点を見ず、インターフェースや仲介役の有無だけで設計を評価すること
- 「知識」を具体化せず、曖昧なまま対策へ進むこと
