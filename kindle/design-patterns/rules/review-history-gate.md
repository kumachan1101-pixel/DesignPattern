# 過去指摘の再発防止ゲート

## 目的

このチェックリストは、過去に一度直した指摘が別の章や後の修正で再発することを防ぐための最終合格判定です。

`rules/checklist.md` は執筆時の詳細確認、`rules/phase-consistency-check.md` はフェーズ間整合の確認、このファイルは「過去指摘が再発していないと、どの証拠で判定するか」を担当します。

チェック欄を埋めただけでは合格になりません。各章の節・図・コード・実行結果を証拠として `review-tasks.md` に記録し、自動検査と目視検査の両方が通った場合だけ合格です。

## 合格判定の原則

- 第1章を品質基準として、第0章・第2〜12章を横並びに確認する。
- 「確認済み・修正不要」「対象外」にも、確認した節と理由を書く。
- 一つでも「未確認」「要修正」「★残存」があれば不合格とする。
- 自動検査に通っても、意味・責任・図の読み方に関する目視項目が未確認なら不合格とする。
- 過去の対応ログに「完了」とあっても、現在の原稿を再確認する。
- 合格前に「全章対応済み」「出版可能」と報告しない。

## A. 前工程から後工程への論理接続

### RH-01：第1章との横並び比較

- [ ] 第0章・第2〜12章を、第1章と同じ品質観点で比較した。
- [ ] 各章について、仕様→痛み→原因→課題→構造判断→完成コード→結果の接続を説明できる。
- [ ] 章別の判断を `review-tasks.md` に記録した。

必要な証拠：章名、比較した第1章の節、対象章の節、差分、判断。

### RH-02：節と図の橋渡し

- [ ] 各節の冒頭で、前節で分かったことと次に確認することがつながっている。
- [ ] 連続する図について、前図のどの箱を次図で展開したかが書かれている。
- [ ] 新しい図法・粒度へ変わる場合、拡大・省略・比較対象を説明している。

不合格例：「一致しています」「次の図です」だけで、引き継ぐ判断や要素がない。

### RH-03：現状・変更要求・完成形の分離

- [ ] フェーズ1には現状仕様・現状型・現状コードだけがある。
- [ ] 変更後に初めて追加する状態、結果型、インターフェース、履歴、外部境界が現状へ先取りされていない。
- [ ] 仕様変更に含まれない保存方法、検証、結果契約、履歴、外部境界は変更前後で維持されている。
- [ ] 前後差分は変更要求または課題IDで説明できる。

必要な証拠：変更前後で維持する要素の表、変更対象の表、1-4と7-1の差分理由。

## B. 仕様・入力・システム境界

### RH-04：仕様入力の実使用

- [ ] 仕様にあるID、種別、状態、金額、フラグ、データが公開入口で受け取られる。
- [ ] 入力が判定、データ選択、計算、保存、外部送信のどこで使われるか追える。
- [ ] 入力を固定文字列や別の値へすり替えていない。
- [ ] 動作例、`main()`、実行結果が同じ入力を使う。

不合格例：図には「注文・在庫」があるが、コードは `"data"` を送るだけ。

### RH-05：システム全体図と内部図

- [ ] システム全体図は利用者、対象システム、内部保存データ、外部サービス、最終結果を区別する。
- [ ] 対象システムを `subgraph` などの境界で囲む。
- [ ] 境界を越える全矢印に、実際に渡る要求・データ・結果を書く。
- [ ] 色は役割の凡例として使い、箱の文字と形でも役割が分かる。
- [ ] システム内部図は全体図の言い換えではなく、対象システム内の判定・加工・保存・出力順を示す。

必要な証拠：両図の名称、共通入力名、展開元の箱、最終出力。

### RH-06：最終成果物と内部結果

- [ ] 利用者が本当に欲しい最終成果物を1文で定義している。
- [ ] 中間データ、ログ、履歴、状態保存、通知受付、API結果を最終成果物と混同していない。
- [ ] 複数の中間処理が一つの成果物へ集約される場合、その経路が図と結果で分かる。

不合格例：CSV読込、グラフAPI、PDF出力を別々の最終成果物として並べる。

## C. クラス・コード・変更影響

### RH-07：現状クラス図の完全性

- [ ] 1-4の主要な全 `class` / `struct` が、1-3の責任表とクラス図にある。
- [ ] 一つのユースケースを実現するクラス群が、生成・所有・呼び出し・引数・戻り値で接続されている。
- [ ] 意図的に省略する補助型には省略理由がある。
- [ ] 定義しただけの孤立型や、コードにない先取り型がない。

必要な証拠：責任表、クラス図、1-4の型一覧の照合。

### RH-08：C++の契約とクラス図の線種

- [ ] C++には `interface` キーワードがなく、本書のインターフェースは純粋仮想関数と仮想デストラクタを持つ抽象基底クラスだと説明している。
- [ ] `<<abstract>>` と `<<interface>>` の本書上の使い分けがコードと一致する。
- [ ] 継承、インターフェース実現、一時利用、保持、集約・合成の線種が実コードと一致する。
- [ ] 白三角の実線・点線と、依存の点線矢印を読者が説明できる。

必要な証拠：第8章の説明とコード、全章クラス図の章別判定。

### RH-09：フェーズ3の変更試行

- [ ] 変更要求を現状構造へ実際に実装し、コンパイル・実行できる。
- [ ] 未実装エラーや仮想コメントだけを設計上の痛みの証拠にしていない。
- [ ] DB、Repository、Registry、Gateway、検証など維持する境界がコードまたは「抜粋の前提（周辺は現状のまま）」に残る。
- [ ] 変更影響グラフが、実際に修正した場所と再確認範囲を区別する。

必要な証拠：変更試行コード、実行結果、変更影響グラフ、維持境界。

### RH-10：原因分析の根拠

- [ ] 症状と構造的原因を分けている。
- [ ] 変わる部分と変わってほしくない部分を、クラスと関連コードの文脈付きで示している。
- [ ] パターン名や完成コードから逆算した原因になっていない。
- [ ] 抜粋にはクラス、メソッド入口、条件、呼び出し先、戻り値、後続利用が分かる範囲がある。

不合格例：着目行だけを出し、どのクラス・処理順・結果利用か分からない。

## D. 課題定義と対策検討

### RH-11：フェーズ5の課題ID

- [ ] 課題IDは課題ID1から連番で重複がない。
- [ ] 課題はフェーズ3の実在する接続点に対応する。
- [ ] 接続する値・型、変わる側、守る側が書かれている。
- [ ] 課題IDがフェーズ6の判断、フェーズ7のコードと結果まで同じ意味で使われる。
- [ ] フェーズ5で未来のクラスやパターンを対策として決めていない。

必要な証拠：接続点表、システム全体の課題文、追跡先。

### RH-12：システム全体での構造判断

- [ ] フェーズ6は課題別の部分対策ではなく、一つの完成システムを考える。
- [ ] 「こうなっているから、こういう理由でこう変える」を文章で説明する。
- [ ] 分離方法、責任の配置場所、具象クラスの生成場所、所有、登録、選択、依存注入を決める。
- [ ] 安定側が具体クラスの詳細を意識せず実行できる経路を示す。
- [ ] 最終構造が一つなら比較を入れず、複数なら目的を満たす完成構造同士だけを比較する。

不合格例：関数化、継承、委譲などの手段だけを目的なしに並べる。

### RH-13：クラス図による責任移動

- [ ] フェーズ1のクラス図を基準に、どの責任を残し、移し、新設するか示す。
- [ ] 着目箇所を色と `【残す】` `【移す】` `【新設】` などの文字で示す。
- [ ] 対策検討の採用図と完成後のクラス図が同じ構造である。
- [ ] フェーズ7のコード上の生成・所有・注入関係が図と一致する。

必要な証拠：変更前図、採用図、完成図、実装対応表。

### RH-14：段階的なコード変更

- [ ] 対策検討の最初に、課題部分の変更前コードを必要な文脈付きで振り返る。
- [ ] 現状全コードを目的なく再掲していない。
- [ ] 各段階で、変更理由、変更対象、コード変更、得られた効果、残る問題または次の判断を説明する。
- [ ] 生の迷いや試行錯誤ではなく、整理された思考順として提示する。
- [ ] いきなり完成コードだけが現れない。

## E. 完成コード・運用・結果

### RH-15：完成コードの読みやすさ

- [ ] クラス・責任ごとに見出しとコードブロックを分ける。
- [ ] `main()` / Applicationは組み立てとシナリオ呼び出しへ限定する。
- [ ] 長いシナリオは目的別の名前付き関数へ分ける。
- [ ] 分割したコードを順に連結するとコンパイルできる。

### RH-16：ケース別の結果証明

- [ ] 「実行コード→結果→読み取ること」の順でケース別に置く。
- [ ] 入力値が結果のどこへ反映されたか説明する。
- [ ] 内部数値や状態が変わる場合、変更前→変更後と後続判定をログへ出す。
- [ ] 成功、存在、一致という語だけで完了判定していない。
- [ ] エラー時に状態が変わらないなら、状態遷移図へエラー遷移を足さず、結果で状態不変を確認する。

### RH-17：システムが自動で行う後続処理

- [ ] キャンセル後の待機昇格、在庫更新後の通知など、システムが運用すべき後続処理が起点操作から自動で呼ばれる。
- [ ] `main()` から別操作として手動呼び出しして、システム化したように見せていない。
- [ ] 自動処理の起点、対象データ、状態変化、結果がコードとログで追える。

### RH-18：外部境界と失敗

- [ ] DB、API、通知、ファイル、描画処理を境界クラスまたは契約の先でスタブ化する。
- [ ] 失敗、保留、再試行、非同期が題材の論点なら結果型・状態・キューで表す。
- [ ] 論点外なら、本番での扱いと、この章で省略しても設計判断が変わらない理由を書く。
- [ ] 通知失敗などが状態保存や他の処理を巻き戻すかどうかを明示する。

## F. 著者・出版品質

### RH-19：著者の事実と文体

- [ ] 実在しない同僚との会話、職歴、成功体験、チーム状況を作っていない。
- [ ] 著者の現状は、自分で設計し、顧客レビューの指摘を受け、見直しているという確認済み事実に沿う。
- [ ] ため口の会話ではなく、本文と同じ丁寧な文体である。

### RH-20：掲載品質と残存指示

- [ ] 本文の `★`、`TODO`、編集指示が0件。
- [ ] Kindleのコード行幅・表列数を満たす。
- [ ] Mermaidを変更した章は実際にレンダリングする。
- [ ] C++コードは警告を有効にしてコンパイルし、掲載結果と実出力が一致する。
- [ ] ユーザーの対象外変更をコミットへ混ぜていない。

## 章別判定の記録形式

各章について、次の形式で `review-tasks.md` に記録します。

```text
対象章:
比較基準:
合格したRH:
修正したRH:
対象外のRHと理由:
確認した節・図・コード・結果:
自動検査:
残件:
章判定: PASS / FAIL
```

「合格したRH: 全て」のような一括記載は禁止です。少なくともRH-01〜RH-20を、合格・修正・対象外のどこで判断したか追えるようにします。

## 自動検査ゲート

リポジトリルートから実行します。

```powershell
rg -n "★|TODO|FIXME" kindle/design-patterns/output --glob "*.md"
python kindle/design-patterns/script/validate_book.py
python kindle/design-patterns/script/check_kindle.py
python kindle/design-patterns/script/check_execution_output.py
git diff --check
git status --short
```

次のすべてを満たしたときだけ自動検査合格です。

- `rg` の結果が0件。
- 3つのPython検査が終了コード0。
- `git diff --check` が終了コード0。
- `git status --short` に対象外変更はあっても、ステージ対象へ混ざっていない。

## 全体PASSの条件

次の三条件をすべて満たした場合だけ、このチェックリストはPASSです。

1. RH-01〜RH-20について、第0〜12章とあとがきの章別判定が完了している。
2. 自動検査ゲートがすべて合格している。
3. `review-tasks.md` に最終判定と証拠が記録されている。

一つでも未完了なら、最終判定は `FAIL（残件あり）` です。

## ユーザーへの合格報告

PASS後は、ユーザーへ次の内容を必ず報告します。

```text
過去指摘の再発防止チェックリストはPASSしました。
・確認範囲: 第0〜12章、あとがき
・目視確認: RH-01〜RH-20
・自動検査: validate / Kindle / C++実行結果 / Mermaid / diff
・修正内容と章別証拠: review-tasks.md
・未対応: 0件
```

FAILの場合は「PASSした」と言わず、失敗項目、対象章、次の作業を報告します。
