## 基本姿勢

テンプレートの項目を箇条書きで埋めるだけでは足りない。
各項目は、読者が「ここまで読んだので次へ進める」と感じる水準まで展開する。

各項目では、次の流れを意識する。

1. なぜ今これを確認するか。
2. 何を材料に見るか。
3. 何が分かったか。
4. 次の項目で何に使うか。

## 目的と達成基準

各標準見出しの直下に、本文へ出さない執筆用コメントとして `目的` と `達成基準` を置く。

- 目的：この項目は読者の理解を何のために進めるのか。
- 達成基準：読み終えた読者は何を自分の言葉で説明・予測・判断できるべきか。

目的を達成しない説明、図、表、コード、実行結果は置かない。
達成基準に関係しない一般論や先取りは削る。

## 短段落で積み重ねる

1段落は1〜3文に収める。
長い段落は分割する。
「この文で何かを伝えたら、次の段落で別のことを伝える」という積み重ね方をする。

## 章の独立性

第0章を読んでいれば、どの章から読んでも理解できる完全自己完結の構成にする。

- 「前章で学んだように」は使わない。
- 「第〇章と同様に」は使わない。
- 次章予告は書かない。

## 図解ルール

文章だけで全体像を説明しきろうとしない。
次の箇所は、できるだけ図または表で示す。

- 仕様の入力→加工→出力。
- クラス責任と依存関係。
- 変更影響の広がり。
- 接続点で流れる値・型・操作・イベント。
- 改善前後の差分。
- 責任移動。

図を置くときは、次を守る。

- 図の前に、読者が図を見る目的を1文で書く。
- 図に出るクラス名・値・状態名は、本文または表で説明済みにする。
- 図の後に、図から読み取るべき結論を1〜3文で回収する。
- 図だけで新しい仕様や判断を初出ししない。

## 仕様説明ルール

現状の仕様を文字だけで箇条書きにしない。
1-1の最初の具体物は代表実行結果とする。出力を先に見せ、その出力から読み取れる一連の動き、対応する入力・`main()`を説明してから、「最初にシステム全体をつかむ」で入力、主要処理、出力、掲載コードでの代替を4項目に要約する。その後に要求、データ、図、クラス、コードの順で詳細を説明する。入力コードを実行結果より先に出さない。
必ず以下のいずれかで構造を見せる。

1. 入力→加工→出力の図。
2. 入力→加工→出力の3列テーブル。
3. 動作例テーブル。

加工は実装詳細ではなく、業務上の変換・判定・保存・通知として書く。

## コード提示ルール

コードブロックの前に、読む目的と注目点を書く。
コードブロックの後に、コードから分かったことを1〜3文で回収する。

コードは責任の固まり（入力データ・計算・組み立て・実行など）ごとに分割して掲載する。
各コードブロックの直後に、そのブロックが仕様のどの部分を担い、何をしているかを箇条書きで補う。
プログラミングに不慣れな読者が、ブロック単位で「どの仕様か・何をするか」を追える水準にする。
長いメソッド（計算・判定）は、処理の固まりにコメントや区切りを入れ、各固まりを仕様のルールへ対応づける。

現状コードの説明では、原因や責任外の判断を先取りしない。
特に1-4の実装コード説明では、構造分析や問題提起をせず、コード上の事実と仕様との対応だけを説明する。
原因分析の後で初めて、どの行にどの判断や前提が漏れているかを説明する。

### 掲載単位（1定義1ブロック）

長いコードを一度に見せない。**掲載の最小単位は「1つの定義」**である。第9章 `output/chapter09_2.md` の1-4・3-1・7-1を基準実装とする。適用範囲は1-4（現状コード）、3-1（変更を試みる）、フェーズ6の断片、7-1（完成コード）で、この4か所は同じ書き方でそろえる。

#### 単位の形

各単位は必ずこの順で置く。

1. 見出し（定義名だけの太字）
2. 1行の導入 ―― このブロックで何を見るか
3. コードブロック
4. 説明
5. `---` の区切り線

区切り線を省くと、説明が上のコードのものか下のコードのものかが読者に分からなくなる。導入を省くと、読者は目的を持たずにコードへ入ることになる。

#### どこで分けるか

**1ブロック＝1定義。** 行数では分けない。「長いから割る」「短いからまとめる」はどちらも誤りである。

次の2つだけをまとめてよい。

- 同じクラスの、同じ役割の定義（列挙型と、その表示用変換関数など）
- 同じ操作を複数クラスが実装したもの（3つの優先度ルールなど）

**ブロックはクラスをまたがない。** 判定に迷ったら次で決める。

> **そのブロックが1つの見出しで説明できないなら、それはまとめすぎである。**

#### 宣言と定義を分ける基準

原則は分けない。分けるのは次の一行で判断する。

> **メンバーを見ないと読めない関数は、メンバーと一緒に置く。**

つまり、**手順を持つ関数（制御フロー・複数ステップの処理）があるクラスだけ**、宣言ブロック（メンバーと公開操作の一覧）と、定義ブロック（関数1つにつき1ブロック）へ分ける。それ以外のクラスは、メンバーと処理を同じブロックへ置く。定義だけを並べると継承関係とメンバーが見えなくなるので、機械的に全クラスを分けてはならない。第9章では19クラス中、分けたのは `TicketService` と `TicketManager` の2つだけである。

#### 見出しに書かないこと

見出しは定義名だけにする。クラス名、または `Class::method()` である。

- 「（継承なし）」「`: public Base`」など、コードを見れば分かる情報は書かない。
- 役割の要約を見出しへ足さない。役割は導入の1行で書く。
- 兄弟クラスの片方だけを分けない。`EscalatedPhase` を単独ブロックにするなら、`ResolvedPhase` と `PendingPhase` も単独にする。

#### 説明の深さ

**1行が下限である。** 名前を言い換えるだけの説明（「`assign()`：担当者を割り当てます」）は、コードを読めば分かるので置かない。消すか、意味のある説明へ変えるかのどちらかにする。

1行を超えて書いてよいのは、次のいずれかがあるときだけである。

1. 判断が2つ以上ある
2. 順序に意味がある（入れ替えると壊れる）
3. 失敗の扱いがある
4. 所有権・生存期間・前提がある

#### `main()` と実行結果

`main()` と実行結果は、全定義を説明した後、最後に置く。`main()` を行のまとまりごとに区切り、**各まとまりの直後に対応する出力を置く**。離れた `main()` と出力を読者に往復させない。

掲載したブロックを上から順に連結すれば、そのまま1つのプログラムとして動くようにする。これは `script/check_execution_output.py` が1-4と7-1について機械で確認する。

### 接続点コードの略記禁止

接続点（変わる側と守る側の境界）に当たるコードは、**絶対に略さない**。「← 他のelse ifブロックがここに続く」「〜も同様に並ぶ」「…が続く」のような省略は、読者から判断材料そのものを奪う。同じ構造の分岐が並ぶこと自体が接続点の重要情報なので、全分岐を記載する。接続点以外の周辺コード（検証・保存など）を省く場合は、コードブロックの外で維持条件として明記する。

### 関数・データの記述スタイル

- クラスのデータメンバと各関数の先頭には、役割を示すコメントを付ける（全章共通）。
- 同型で並列な極小関数（1行のエラー出力など）は、揃えた1行形式で並べてよい。並列関係が縦に見え、Kindleの80字制限内に収まる場合に限る。
- それ以外の関数は、1行に潰さずブロック（複数行）で書く。Kindleでは横幅が狭く、1行に詰めた実装は読みにくい。
- 同じコードを別の節で再掲するときは、行の折り返し・ブロック構造を変えない。「おさらい」と言いながら形が違うと、読者は別のコードだと誤解する。

### クラス図の記述スタイル

- クラス図で他と線がつながらないクラスを置く場合、「誰が使うか」の注記（note）または直後の本文説明を必ず添える。
- 矢印のラベルは依存の目的説明（「商品情報を取得」など）として許容する。時間順のやり取りはシーケンス図で示す（0章「クラス図の読み方」参照）。

#### クラス図の線種（全章共通）

関係の種類ごとに線種をそろえる。実コードの関係と一致させる。

| 関係 | Mermaid記法 | 見た目 | 使う場面 |
|---|---|---|---|
| 実現（インターフェース実装） | `<\|..` / `..\|>` | 破線＋白三角 | 具象がインターフェース契約を満たす |
| 継承（クラス拡張） | `<\|--` / `--\|>` | 実線＋白三角 | 具象が抽象・基底クラスを継承する |
| 依存（生成・一時利用） | `..>` | 破線矢印 | 生成して一時的に使い、メンバに保持しない |
| 関連・集約・合成（保持） | `-->` / `o--` / `*--` | 実線 | メンバとして保持する |

- C++に `interface` キーワードはない。「インターフェース」は、全メンバ関数が純粋仮想（`= 0`）でデータメンバを持たず仮想デストラクタを持つ抽象クラスとして書く。この場合、具象からの線は**実現**（`<|..`／破線白三角）にする。
- 掲載コードではlambdaとスマートポインタ（`unique_ptr`、`shared_ptr`、`make_unique`）を使わない。生ポインタが所有関係なら所有者のデストラクタで破棄し、借用するだけなら生存期間を本文で説明する。
- 抽象クラス（一部を実装し、一部を純粋仮想で残す）を基底に継承する場合は**継承**（`<|--`／実線白三角）にする。
- 生成メソッド（ファクトリー等）で作って一時的に使い、メンバに保持しない関係は**依存**（`..>`／破線矢印）にする。参照・所有としてメンバに保持する関係は実線（関連・集約・合成）にする。
- `classDiagram`は原則として`direction TB`で統一する。横向きが不可欠な例外は、図の目的と例外理由を本文に明記する。各型は保持・生成・引数・戻り値・呼び出しのいずれかで関係線へ接続し、説明のない孤立型を作らない。

### フェーズ6のコード提示

フェーズ5は、原因から直接課題IDへ飛ばず、課題候補を出してシステム全体で必要性・重複・依存・統合／分割／除外・完了状態を検討する。採用候補だけを`課題ID・接続点 / 接続するもの・変わる側 / 守る側 / 完了条件`の一表へまとめ、課題ID1から欠番なく採番する。「接続するもの」と「変わる側」は同じセルでラベルを付けて改行し、意味を落とさずKindle向けの4列に収める。同じ内容を引き渡し表、受け入れ条件表、課題カードへ分けない。

フェーズ6はフェーズ5の一表から直接、次を決める。

1. 分離方法：変わりやすい判断・処理・生成判断を、どの契約で守る骨格から切るか。
2. 配置場所：切り出した責任を、どの既存クラスまたは新しい具体クラスへ置くか。
3. 組み立て方法：誰が具体クラスを生成・所有・登録・選択・注入し、安定側はどの契約だけを呼ぶか。

フェーズ6冒頭の「まず全体像」は、現在の混在→分離判断→課題ID別の着地点→守る範囲を`flowchart TB`で図示する。同じ内容を空白整形した`text`ブロックだけで示さない。

三つの観点は手段を並べるためではなく、システム全体の目標構造を漏れなく決めるために使う。対策検討と対策完成後のクラス図は同じMermaid定義を使い、課題の中心となるクラス・契約・依存を色で強調する。さらに構造判断ごとに、採用全体図と同じクラス名・操作・関係を使った部分クラス図を理由の直後・対応コードの前へ置く。`main()` を仮想的なクラスとして描かず、生成・所有・登録・注入は注記、対応表、コードで示す。

**変更前コードをまとめて再掲する節（「課題箇所のおさらい」）は置かない。** 各段が「その段が触る数行を3-1から抜き出す → 変更後を並べる」形になっていれば、手前でまとめて再掲する意味がない。読者は、問いのない状態で100行超のコードを読まされることになる（著者指摘 2026-08-15）。フェーズ6の入口では「書き換える前のコードは3-1にある。ここで全部を再掲することはしない」と1文だけ書き、各段で必要な数行だけを抜く。抜いた断片の掲載箇所には、どの節から抜いたか（`3-1の switch から受付中のケースだけ`）を書く。

以降は課題ごとに関連部分へ絞り、次の順で示す。

1. 着目するクラス・メソッドと、フェーズ3のどの痛みを解くか。
2. 変更前の関連コード。
3. 最小変更後の関連コード。
4. 減った変更、残った問題、次へ進む理由。

#### 対策検討は、考えた順に語る

課題ID節は「ラベル付きブロックを6個並べた資料」ではなく、**設計を導く過程をそのまま順に語る文章**として書く。読者はまだ答えを知らない。答えを知っている側の整理順で並べると、読者には根拠のない結論が並んでいるようにしか見えない（著者指摘 2026-08-15）。

**目指す形は、フェーズ6の最初に掲げる。答えを先に置くこととは違う。** 大枠が見えていない状態で契約の形だけ考えても、良し悪しを判定する基準がない。**大枠が無いと検討が進まない。** フェーズ6の冒頭に「この時点で決まっていること／これから決めること」を表で置き、線を引く。

| 掲げてよい（大枠） | 掲げてはならない（決める対象） |
|---|---|
| 目指す構造の形（「状態ごとの振る舞いを共通契約の裏へ揃えて現在状態へ委譲する」） | 契約・具体・まとめ役のクラス名 |
| 守る範囲 | 契約のメソッド構成、戻り値の型 |
| 課題ごとの完了条件 | 誰が具体を持つか、どう持つか（値か参照か） |
| 変更前クラス図 | 骨格のコード、`main()` の形 |

左は前工程（1-5・5-2・5-3）の出力で、フェーズ6の**入力**である。右はフェーズ6の**出力**である。入力を掲げるのは当然で、出力を掲げると導出が解説に変わる。

**出発点は「課題がもう決めていること」。** 課題IDの文（「公開操作は状態を判定せず、状態ごとの許可操作と遷移先だけを差し替えられるようにする」など）は、すでに**何を分けるか**を言っている。出発点では、決まっていること（分ける対象＝出て行くもの／残るもの、完了条件）と、まだ決まっていないこと（**分けた後にどう繋ぐか**）を分けて示す。この節で解くのは後者だけである。次にフェーズ3までの古い1行を掲載する。読者がその時点で知っているのはここまでである。

**本文は6段を1周する。課題別に節を切らない。** 課題が複数あっても、6段を2周・3周させない。**前半3段（契約・安定骨格・具体）は段の中で課題ごとに分け、後半3段（生成・注入・利用開始）は課題をまたいで1回だけ決める。**

| 段 | 考えること | ラベル | 単位 |
|---|---|---|---|
| 1 | 分けて、境界に何が渡るかを決める | 【契約】 | 課題ごと |
| 2 | 呼ぶのは、残った側。出て行った側どうしを呼ばせない | 【安定骨格】 | 課題ごと |
| 3 | 契約の裏を埋める | 【具体】 | 課題ごと |
| 4 | 実体を作る人がいる。生成・所有・寿命を決める | 【生成】 | **共通** |
| 5 | 作ったものを渡す。3択から消していく | 【注入】 | **共通** |
| 6 | 結果として、呼び方はこうなった | 【利用開始】 | **共通** |

**課題別に節を切らない理由は3つある。**

1. **後半3段は共同決定である。** 複数の契約は同じ箱が持ち、同じコンストラクタで注入される。片方の課題節で先に決めると、もう片方の節は「同じ1行です」というエコーになり、しかも先に決めた側が相手を先読みした形になる（第9章では、状態軸しか説明していない段階で箱の名前が `TicketPolicySet`＝両方入る名前になっていた）。
2. **課題別に書くと、比較が離れる。** 「接続するものの数と、そのうち何を引数から消したかが契約の大きさを決める」は課題を並べて初めて言えることなのに、課題別だと比較相手が数百行先になる。
3. **1課題の章と複数課題の章で形が変わらない。** 課題が1つの章はもともと1周なので、複数課題でも1周にすれば全章が同じ形になる。

**ただし条件がある。課題どうしが独立していること。** 片方の契約がもう片方の入力になっている場合、同じ段に並べると依存が見えなくなる。5-2で独立と判断していない章では、依存の順に並べ、依存関係を明記する。

課題IDは節見出しではなく**各段の中のラベル**（`**課題ID1（状態軸）。**`）で示す。どの段落がどの課題の話かを、必ず全部に付ける。段3の各課題の終わりに、その課題の完了条件を回収する。

1段目では、まず**割り方の根拠**を書く。「具体が1つ増えたときに触るかどうか」で線を引き、出て行く側は増え、残る側は1行も増えないことを示す。

**次に決めるのは「接続するものの形」である。新しい用語を発明しない。** 何が境界を行き来するかは、**5-3の接続点定義表がすでに列挙している**（第9章なら課題ID1が「現在状態、操作、次状態、操作結果」の4つ、課題ID2が「顧客区分とHigh／Normalの結果」の2つ）。フェーズ6の1段目が決めるのは**その受け渡しの形だけ**である。数を勝手に数え直したり、「渡すもの／受け取るもの」のような独自の言葉で言い換えたりしない。フェーズ5の出力とフェーズ6の入力が一致しなくなる。

接続するものを1つずつ、次の3列の表で決める。

| 接続するもの（5-3） | 決めた形 | そう決めた理由 |

「引数で渡さない」と決めたものには、**代わりに何が担うか**を書く（クラスであること自体が体現する／メソッド名が担う）。理由の列には、その形にしないとどうなるかを書く（分岐が移動するだけになる／生成後の配線が要る）。接続点に入っていない項目があるなら、**5-3の守る側で除いたから**だと明示する。

**新しいクラス名を、決める前に出さない。** フェーズ6冒頭の全体像・三つの設計決定・材料表は、**何を決めるのかだけ**を書く。`ITicketPhase` や `TicketPolicySet` のような、各段で決まる名前をそこへ書くと、以降の段が「すでに出ている答えの解説」になる。冒頭に書いてよいのは、既存クラス名（変更前クラス図に載っているもの）と、役割の言葉（「状態が満たす共通契約」「具体を生成・所有する場所」）だけである。

**既存クラスの改名も、決定として導く。** 「ここで名前を変えます」と1文で済ませない。元の名前が何を指していたか、責任が出て行った結果それが合わなくなったこと、変えなくても動くが読み手にどう誤読されるか、を書く。1-3のクラス一覧に書いた役割のうちどれが消えたかまで戻せると、改名が編集上の都合ではなく設計の結果になる。

**後の段で決めることを、前の段のコードへ書かない。** これが導出の可否を決める。第9章では【安定骨格】の段が `policies.phaseFor(t.status).assign()` と書いていた。この1行には、**まだ決めていない箱の名前（4で決定）と、注入されたメンバー（5で決定）が両方入っていた。** 骨格が「導かれた」のではなく、完成形を先に置いて後から理由を付けていたことになる。

**穴が空くなら、穴を見せる。** 骨格を書こうとして書けない部分が出たら、それは**次の段が要る理由そのもの**である。埋めずに、名前だけ付けて残す。

1. 手順を段で数える（読む → 尋ねる → 保存する）
2. 書ける段と書けない段を分ける
3. 書けない部分に名前を付け、コードへそのまま置く（`phaseFor(t.status)`）
4. **なぜ書けないかを言う**（`TicketStatus` は値であって契約の実体ではない／自分で持てば具体の名前を知る）
5. 何段目で決めるかを言う

次の段は「その穴を誰が埋めるか」から始める。**埋める者の条件は、穴の性質から出る**（引くには持っていなければならない → 引く関数を置く場所と、具体を所有する場所は同じ）。こうすると、生成の置き場所が独立した思いつきではなく前段の帰結になる。

穴が埋まったら、**骨格のどこが変わったかを1行で見せる**（`phaseFor(...)` → `policies.phaseFor(...)`）。骨格そのものは1行も変わっていないことを確認する。変わるなら、骨格の切り方が間違っている。

**宣言も、決まったところまでで止める。** メンバーが全部決まっていない段階でコンストラクタまで書くと、そこに答えが入る。「この段で分かるのはここまで」と断り、完成した宣言は決まった段で出す。

**「返す情報の使い道を後から考えて大丈夫か」に答える。** 契約の戻り値を1段目で決めるとき、読者は「使い道が決まっていないのに形を決めてよいのか」と思う。**答えは変更前コードにある。**

分けるのは処理の置き場所であって、やり取りする情報ではない。**残る側が変更前に実際に消費していた値を、そのまま戻り値にする。** 第9章では `t.status = TicketStatus::InProgress;`（状態値）と `changed = true;`（真偽）を消費していたので、その2つを返す。将来の使い道を見込んで決めているのではない、と明示する。

そのうえで、**確定は2段目**であることを書く。骨格を実際に書いて足りることを確かめ、足りなければ1段目へ戻る。**戻り先が1段だけで済むのは、確かめようのある根拠（変更前コード）から決めているからである。** この2文が無いと、1段目の決定が思いつきに見える。

**既存クラスの改名は、1-3のクラス一覧の役割と突き合わせる。** 一覧に挙げた役割のうちどれが出て行き、どれが残るかを数える。**「判断が1つも残らない」のような言い切りをしない。** 検証・操作固有の判断は残ることが多い。出て行くのは「具体が増えると変わる判断」だけである。責任が変わっていないのに名前だけ変えるのは、差分を増やすのでしない。

**契約だけを見せて数を数えない。実装を1つ置いて、数えた結果を確かめる。** インターフェース定義だけでは「渡すものが無い」「受け取るのは2つ」が本当かどうか読者には確かめようがない。契約の直後に具体クラスを1つ掲載し、次の2つを実物で回収する。

- **渡すもの0の実態**：引数が無いこと。そして、それでも判断できる理由（そのクラスであること自体が値を体現している／メンバー変数が1つも無い）
- **受け取るものN個の実態**：返している実際の値（`{true, TicketStatus::InProgress}` の `true` が何で、`InProgress` が何か）

このとき、その具体クラスに**書かれていないこと**（変更前にあったのに消えた行）へ触れ、それが誰の仕事になるかは何段目で決まるかを1文で示す。答えを先取りせず、問いだけを立てて次の段へ渡す。

段3（具体）では同じクラスを再掲しない。1で見せたのと**対照的な**もの（許可操作が少なく「書かないこと」で規則を表しているクラスなど）を1つ選び、残りは表で示す。

**【注入】は「実装が骨格へ入る瞬間」を指す。コンストラクタ引数のことではない。** ここを取り違えると、章の中心が組み立ての配線の話にすり替わる。

骨格は契約の型（`const ITicketPhase&`）でしか書いていない。そこへ具体（`OpenPhase`）が入るのは、**引き当て関数が契約への参照を返した瞬間**である（`policies.phaseFor(t.status)`）。この1行が注入であり、骨格はそこに何が入ったかを最後まで知らない。

**この段では次の3つを書く。**

1. **引き当て関数の戻り値の型**を見せる。具体クラスの型ではなく契約への参照であること
2. **受け取る1行**を見せ、「ここで実装が入る」と名指しする
3. **どれが入るかを決める鍵**と、その出どころを書く

**鍵と出どころは、構造の違いをそのまま表す。** 第9章では、状態分離（State）が「保存された状態」を鍵にし、規則差し替え（Strategy）が「入力の属性」を鍵にする。**入れる仕組みは同じで、鍵の出どころだけが違う。** 複数の構造を扱う章では、この対比を表1つで示す。

**組み立て時に1回入るのか、呼び出しごとに入るのかを明示する。** 引き当て関数を通す形では呼び出しごとに決まる。ここを書かないと、読者は起動時に固定されると読む。

**骨格が引き当て役へ届く方法（値メンバか、外から受け取るか）は、別の話として扱う。** どちらでも注入は起きる。混ぜて書くと、注入がコンストラクタ引数の話に見える。

**「代表ケースの実行接続」表では、【注入】が軸の数だけ現れる。** 組み立ての1行としてまとめない。

**「値メンバではだめなのか」に答える。** 注入を扱う段で読者が必ず持つ問いはこれである。答えずに進むと、パターンを理由なく適用したことになる（CLAUDE.md「パターン名から設計を選ばない」）。

選択肢は3つではなく4つある。**具体クラスを直接持つ**／**まとめ役を値メンバとして持つ**／**取りに行く**／**外から受け取る**。このうち消えるのは1番目（具体の名前を知る）と3番目（依存が宣言にも引数にも現れない）だけで、**2番目は多くの場合そのまま成立する。** 「自分で作ると具体の名前を知ることになる」を、まとめ役を値で持つ場合へ当てはめてはならない。まとめ役の名前を知ることと、その中の具体の名前を知ることは別である。

そのうえで、外へ出す**実際の理由**を1つ挙げる。挙げられないなら注入しない。理由になるのは次のいずれかで、**その章で実際に起きていること**に限る。

- `main()` など外側がその部品を直接使う（第9章では `log.printAll()`）
- 複数の利用者が同じ実体を共有する
- 差し替える場面を章の中で実際に見せる

**得るものと払うものを並べる。** 払うもの（組み立ての行数、生存期間を読者が追う必要）を隠さない。**章の中で差し替えを見せていないなら、「差し替えられるから注入した」と書かない。** 「1つを外に出す必要があり、それにそろえた」なら、そう書く。

**【注入】の段は、コード1行で済ませない。** `Service svc(a, b, c);` を1行出して「渡しました」と書いても、読者には**何が渡っているのか、なぜそれが注入なのか**が分からない。この段では次の4つを必ず書く。

1. **変更前の組み立てと並べる。** 変更前は依存を値メンバとして内側に持っていたので `Manager manager;` の1行しか出ていない。その対比が「注入」の説明そのものになる（内側から外へ出た、差し替えられるようになった）
2. **`main()` の組み立てを省略せずに出す。** 引数に出てくる実体がどこで作られたかが本文に無いと、その断片は貼っても動かない。組み立ての行を全部見せる
3. **引数を表で説明する。** 引数名／何を渡しているか／変更前はどこにあったか。**この章の対策で入れ替わったのはどれか**が読者に分かる状態にする
4. **生存期間を回収する。** 参照で借りているなら、貸す側が先に作られ後まで生きていることを、コードの行順で示す

**分離に関係のない依存まで外へ出す場合は、その理由を書く。** 「組み立ての場所を1か所にするため」であって分離のためではない、と書かないと、読者はすべての引数が差し替え対象だと誤解する。

**まとめ節に「束ね直す」節を作らない。** 生成・所有・実行順は各段で決まる。決めた場所で書けば、まとめ節でもう一度コードを再掲する必要はない。まとめ節が持つのは表だけにする（構造ポイントの全貌／代表ケースの実行接続）。同じコードを段とまとめ節の両方へ置いていたら、それは段の説明が足りていない。

**新設・変更したクラスは、必ず中身の構造を示す。** 名前と1行の使用例だけで済ませない。特に、他の段のコードから呼ばれているクラス（`policies.phaseFor()` の `TicketPolicySet` など）は、**初めて呼ばれる段より後ろへ本体を回さない。** 回すなら、その場で「何を返す窓口か」と「中身はどの段で開くか」を1文で断る。

中身の示し方は、そのクラスの役割で決める。

- **契約・安定骨格・組み立て役**：クラス本体を掲載する。掲載した後、メンバー・公開操作・内部の分岐を役割ごとに箇条書きで回収する。「増やすときどこを触るか」を必ず書く
- **同じ契約を実装する兄弟クラス群**：代表1つをコード、残りは**表**で構造を示す（クラス名／上書きする操作／返す値／書かないこと）。5クラスを5ブロック並べない。表の「書かないこと」の列は、許可しない操作を不在で表す構造の要になる
- **既存クラスの改名・責任移動**：変更前のどのメンバーが消え、何に置き換わったかを1行で対応づける

**安定骨格に例外があるなら、そこで書く。** 契約の裏へ寄せた判断のうち、1か所だけ骨格側に残るものがある場合（第9章ではエスカレーション時の優先度引き上げ）、その理由と「なぜ契約側へ持たせないか」を書く。書かないと、読者は後で完成コードを見たときに設計が崩れていると誤解する。

4段目は共通の段なので、**責任配置が異なる完成構造が複数残る場合の比較を、ここへ置く。** 第9章では「箱を1つにするか2つにするか」がそれで、片方の課題だけを見ていては決められない判断である。比較を書く場所が無いなら、その判断を課題節へ埋め込んでしまっている。

**前の段の結論が、次の段が要る理由になっていること。** これが繋がらない並びは間違っている。段の終わりに「線を引いただけでは分けられない。隙間を何が跨ぐか」「では、この契約を誰が呼ぶのか」「呼ぶ以上、実体を持っていなければいけない」のような一文を置いて次へ渡す。

**2と3には検算を書く。** 2では「具体を1つ足したとき、この手順は変わるか。変わるなら1へ戻って線を引き直す」。3では「契約のメソッド以外に書きたくなるものがあるなら、1の割り方か数え方を間違えている」。導出は一直線ではなく、この2か所だけ前へ戻る辺がある。それを隠さない。

**【利用開始】を先頭に置いてはならない。** 対策後は呼び方そのものが変わることがある（例：`manager.updateStatus(id, "assign", agent)` → `svc.assign(id, agent)`）。新しい呼び方は設計の結果であって前提ではないので、先頭に置くと根拠のない結論を先に見せることになる。呼び方が変わらない課題では、変わらなかったことを6で明示する。同じ章に両方があるなら、6は共通の段なので、その違いを並べて書く。

#### 各段は、図の差分とコードの差分で見せる

完成形のクラス図を1枚出して終わりにしない。**フェーズ6の冒頭に変更前クラス図（基準の図）を置き、各段ではそこへ足した部分だけを `focus` 色にした図を出す。** 読者が追うのは、図が少しずつ変わっていく過程である。

- 図を置くのは、静的構造が実際に変わる段だけにする（契約の新設、依存の追加、所有の追加、実装の追加）。【利用開始】のように呼び方だけが変わる段には置かない。1課題あたり3〜4枚が目安である
- 図の後は「2つの箱の間に矢印がまだありません。契約を置いただけで、誰も呼んでいないからです」のように、その段で何が起きたか・まだ起きていないかを1〜3文で回収する
- 図に描いていないクラスは、その段では変わらないと明記する
- 戻り値の値型（`Transition`、`Priority` など）は図へ描かない。採用全体図にも無いので、部分図だけに現れると照合できなくなる

コードも同じ粒度で並べる。**その段が触る数行を3-1から抜き出し、変更後と並べる。** 変更前と比べて何が消えたかを1文で書く（「状態名で分岐する `case` が1つも無くなりました」「`if (userType == ...)` の連鎖が1つも無くなりました」）。

#### フェーズ6の並び

```
フェーズ6冒頭
  ├ 全体像フローチャート（起点）
  ├ 守る範囲 ―― この章で変えないもの（箇条書き）
  ├ 対策検討のクラス図：変更前クラス図＝基準の図（【残す】【移す】注記つき）
  ├ この時点で決まっていること、これから決めること（3行の表）
  └ 接続点の分離・配置・組み立てを決める（3行の予告。クラス名は出さない）
課題ID1〜課題IDnを6段で解く（1周だけ。課題別に節を切らない）
  ├ 出発点（前工程で決まっていること／まだ決まっていないこと）
  └ 1〜6段。各段＝変更前の数行→決めたこと→変更後→図の差分→次が要る理由
       前半3段（契約・安定骨格・具体）は軸ごと、後半3段（生成・注入・利用開始）は共通
システム全体の最終構造を決める（変更後の全体図。部分図の和と一致すること）
6-1 構造ポイントの全貌（表）／代表ケースの実行接続（全課題を解き終えてから1本の経路で追う）
```

「接続点の分離・配置・組み立てを決める」は表にしない。6-1の全貌表と同じ責任移動を二度書くことになる。`分離方法`／`配置場所`／`組み立て方法` の3語を各1行の結論として書き、根拠は6段の各段へ渡す。

**表は最後にまとめる。** 「構造ポイントの全貌」表は6-1へ置き、課題IDをまたいで責任の移動を一覧する。「代表ケースの実行接続」表は6-1の全貌表の直後に置き、全課題を解き終えた1本の経路として追う。**ここだけが実行順（【生成】→【注入】→【利用開始】→【安定骨格】→【契約】→【具体】）を担う。** 表の導入文で「ここからは実行時に通る順で貫く」ことを1文だけ断る。本文中に「説明順と実行順は違う」という注記を散らさない。

丸数字（①〜⑥）は使わない。段の番号は `1.` から `7.` の素の数字を使う。本文の順序が1つになったので、番号と実行順が食い違う心配はもう無い。

考えた順では【注入】が【生成】より先に来るが、`main()` 上の実際の行順は逆になる。各コードの「掲載箇所」に「組み立ての最後の行」「【注入】の直前の行」のように位置を書き、行の前後関係が分かるようにする。

中間コードの外で省略範囲を説明し、コードブロック内に `...` や「以下省略」を入れない。コード断片の直前には、所属クラス、完全な関数シグネチャ、入力、戻り値または副作用、省略する不変部分、読む着眼点を書く。クラス分離が必要になった段階では、分離先、利用側、生成・所有・注入箇所を、その判断を追うために必要な関連コードとして示す。

全章共通の外部I/O・スタブの説明は1-3直後の簡略化節へ置く。変更要求だけに必要な模擬方法は、「本章での簡易実現モデル」のような著者向け共通名にせず、「取引ID付き認証と補償をどう試すか」のように対象を見出しへ出す。

採用後の全体コードは7-1へ置く。フェーズ6では完成構造をクラス図で先に定めたうえで、関連コードがそこへ到達する変更を段階的に示す。完成コード全体を先出しして、後から理由を説明する順序にしない。

7-1の完成コードは「掲載単位（1定義1ブロック）」に従う。具象クラスの`override`は宣言と実装を分断せず、クラス単位で実装込みにまとめる（手順を持つ関数がないため、分ける理由がない）。宣言と定義を分けるのは、手順を持つ関数を抱えるクラスだけである。相互参照のため型定義順を調整する必要がある場合は、利用されるコンテキスト型を先に定義する。

分離・配置・組み立てから完成構造が一つに定まるなら、案の比較は置かない。全課題を満たし、責任配置や依存関係が異なる完成構造が複数残る場合だけ、システム全体の効果・変更影響・導入コストを比較する。関数化だけ、責任の一部だけを切り出す案など、課題を残す途中状態は採用候補にしない。

コードへの気づきはコード外の散文で説明する。
`// 💭` は使わない。

## 実行結果ルール

実行結果は、最終値だけを並べない。
読者が「何を・いくらで・誰が」入力し、「どう変わって」その値になったかを追えるようにする。

- 入力（対象データ・金額・会員種別など）と結果（小計→支払金額、状態遷移など）をセットで出力する。
- 内部の件数・残高・在庫・予約数を変更するときは、対象IDと「変更前→変更後」（必要なら上限・単位）をログへ出す。結果名だけで数値変化を隠さない。
- 将来リスクにはリスクID1から連番を付ける。2-5で「変わる見込み＝はい」「変えられるようにする部分」「当面安定として守る部分」を確定し、対策検討で同じリスクIDを採用構造へ再適用する。リスクIDを扱うのはフェーズ2と6だけとし、フェーズ3・7には持ち込まない。リスクIDは実装要求ではないため、未確定機能を完成コードや実行結果へ追加しない。
- システムが後続して行う昇格・通知・補償・履歴記録を、`main()` や運用者による別操作として実装しない。起点となるユースケースから自動的に呼ぶ。
- 状態が変わらないエラーは状態遷移図の矢印に含めず、エラー条件表と実行結果で示す。
- 検証・照会メソッドが成否や結果を返す場合は、呼び出し側で判定・保存・返却のいずれかに使う。戻り値を意図的に持たない命令は`void`とし、結果を捨てているように見える呼び出しを残さない。
- 割引・加算・状態変化など、施策や操作の効果が変更前後で読み取れる形にする（例：`小計 10000円 → 支払金額 8000円`）。
- 実行結果の直前に、実行対象コード・対応する動作例ケース・確認したいことを書く。
- 複数ケースを並べるときは、ケースの区切りと、どのコード（現状／変更後／最終）の結果かを示す。
- 実行結果が複数ケースにまたがる場合や1ブロック25行以上になる場合は、呼び出しコードをケース単位へ分け、各コードの直後へ対応する結果を置く。一括`main()`の後に全ケースの長い結果をまとめない。
- 最終値の羅列だけにして、「何が起きたか」を読者の推測に委ねない。

## コードラベルのルール

| ラベル | 用途 |
|:---|:---|
| `// ← 知らなくていい` | 原因分析後に、呼び出し元へ漏れている判断や前提を示す |
| `// ← ここだけ変わる` | 改善後に、変更影響が局所化された行を示す |
| 【深化コード】 | より難しい変化への対応 |
| 【過剰コード】 | 使いすぎた失敗例 |

`// ← 知らなくていい` は、フェーズ4以降の説明根拠があるコードで使う。
フェーズ1の現状コードには入れない。

## パターン名の扱い

パターン名は、対策を決める前の選択肢ラベルとして使わない。
章タイトルでは、読者の検索性と期待値合わせのためにパターン名を出してよい。ただし「得られること」、ステップ名、要約表、本文中の判断理由では、パターン解説前は本文で導いた構造名を使う。
問題を解いた後、その構造をチームで共有する語彙として紹介する。
パターン解説の直前に、題材から導いた構造とパターン名を結ぶ移行文を置く。見出しだけで突然パターン名へ切り替えない。

## この章を読むと得られること

- 「〜できるようになる」または「〜がわかるようになる」形式で3〜4項目にする。
- パターン名を前面に出さない。
- 問題を発見できる目、使う/使わない判断、影響範囲を読む目を含める。

## 禁止表現

| 禁止する表現 | 代替 |
|:---|:---|
| 文頭・段落冒頭の「まず〜」 | 「最初の試みとして〜」 |
| 「ここで答えは出さない」等 | 削除。問いを立てるだけでよい |
| 「次章では〜」等の次章予告 | 書かない |
| 「悪いコード」「スパゲッティ」 | 「この構造では〇〇が難しい」等の事実で書く |
| 「〜すべき」「〜べきです」 | 「〜が合うかもしれません」等 |

## テスト文法説明ルール

スタブ・モック・アサーションマクロが初めて登場する箇所に、1〜2行の日本語コメントを添える。

```cpp
class IPayrollFacade {
public:
    virtual int calculateNetPay(int grossPay) = 0;
    virtual ~IPayrollFacade() = default;
};

// スタブ：本物のAPIを呼ばずに、あらかじめ決めた値を返す差し替えクラス。
class StubPayrollFacade : public IPayrollFacade {
public:
    int calculateNetPay(int grossPay) override {
        return grossPay - 1200;
    }
};

class PayrollCalculator {
    IPayrollFacade& payroll;
public:
    explicit PayrollCalculator(IPayrollFacade& payroll)
        : payroll(payroll) {}

    int calculate(int grossPay) {
        return payroll.calculateNetPay(grossPay);
    }
};

StubPayrollFacade stub;
PayrollCalculator calc(stub); // コンストラクタでスタブを注入する。

// EXPECT_EQ(期待値, 実際の値)：等しければテスト通過。
EXPECT_EQ(8800, calc.calculate(10000));
```

## Kindle品質ルール

- コードブロック：1行80文字以内。
- Mermaid図：テキストでも意味が伝わる説明を必ず添える。
- 仕様図は正常系を先に描き、入力・判定・加工・正常出力を形状または色で区別する。成功側しか描かない入力検証はひし形＋`Yes`にせず、検証済み入力と処理順で表す。ひし形を使うのは正常系にも複数の有効な結果があり、図に全分岐を描く場合だけとする。異常系は同じ図へ混ぜず、エラー条件表で扱う。エラー条件表は正常系の各種仕様表をすべて示したあと、1-1の最後に置く。
- 脚注：使わない。
- 表：列数は最大4列まで。
- 1段落の長さ：5〜7行以内。
- コードブロックの前後：必ず説明文を置く。
