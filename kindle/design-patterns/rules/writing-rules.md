## 基本姿勢

テンプレートの項目を箇条書きで埋めるだけでは足りない。
各項目は、読者が「ここまで読んだので次へ進める」と感じる水準まで展開する。

各項目では、次の流れを意識する。

1. なぜ今これを確認するか。
2. 何を材料に見るか。
3. 何が分かったか。
4. 次の項目で何に使うか。

## 目的と達成基準

各標準見出しの直下に、本文へ出さない執筆用コメントとして `目的` と `達成基準` を置く。

- 目的：この項目は読者の理解を何のために進めるのか。
- 達成基準：読み終えた読者は何を自分の言葉で説明・予測・判断できるべきか。

目的を達成しない説明、図、表、コード、実行結果は置かない。
達成基準に関係しない一般論や先取りは削る。

## 短段落で積み重ねる

1段落は1〜3文に収める。
長い段落は分割する。
「この文で何かを伝えたら、次の段落で別のことを伝える」という積み重ね方をする。

## 章の独立性

第0章を読んでいれば、どの章から読んでも理解できる完全自己完結の構成にする。

- 「前章で学んだように」は使わない。
- 「第〇章と同様に」は使わない。
- 次章予告は書かない。

## 図解ルール

文章だけで全体像を説明しきろうとしない。
次の箇所は、できるだけ図または表で示す。

- 仕様の入力→加工→出力。
- クラス責任と依存関係。
- 変更影響の広がり。
- 接続点で流れる値・型・操作・イベント。
- 改善前後の差分。
- 責任移動。

図を置くときは、次を守る。

- 図の前に、読者が図を見る目的を1文で書く。
- 図に出るクラス名・値・状態名は、本文または表で説明済みにする。
- 図の後に、図から読み取るべき結論を1〜3文で回収する。
- 図だけで新しい仕様や判断を初出ししない。

## 仕様説明ルール

現状の仕様を文字だけで箇条書きにしない。
1-1の最初の具体物は代表実行結果とする。出力を先に見せ、その出力から読み取れる一連の動き、対応する入力・`main()`を説明してから、「最初にシステム全体をつかむ」で入力、主要処理、出力、掲載コードでの代替を4項目に要約する。その後に要求、データ、図、クラス、コードの順で詳細を説明する。入力コードを実行結果より先に出さない。
必ず以下のいずれかで構造を見せる。

1. 入力→加工→出力の図。
2. 入力→加工→出力の3列テーブル。
3. 動作例テーブル。

加工は実装詳細ではなく、業務上の変換・判定・保存・通知として書く。

## コード提示ルール

コードブロックの前に、読む目的と注目点を書く。
コードブロックの後に、コードから分かったことを1〜3文で回収する。

コードは責任の固まり（入力データ・計算・組み立て・実行など）ごとに分割して掲載する。
各コードブロックの直後に、そのブロックが仕様のどの部分を担い、何をしているかを箇条書きで補う。
プログラミングに不慣れな読者が、ブロック単位で「どの仕様か・何をするか」を追える水準にする。
長いメソッド（計算・判定）は、処理の固まりにコメントや区切りを入れ、各固まりを仕様のルールへ対応づける。

コード内の空行は、行数を増やす装飾ではなく**処理の段階を示す境界**として使う。関数内では、次の段階が切り替わる場所に1行だけ空ける。

1. 入力・依存先の取得
2. 妥当性判定と早期return（連続するガード条件は一群にする）
3. 実行対象の選択・計算
4. 状態変更・保存
5. 通知・表示・結果返却

同じ段階の代入や連続するガード条件の間には空行を入れない。閉じ波括弧の直後に別の判定・実行・返却が続く場合、または準備した値を使って新しい判定へ入る場合は空行を入れる。短い関数でも「判定」と「正常時の実行」が切り替わるなら省略しない。

現状コードの説明では、原因や責任外の判断を先取りしない。
特に1-4の実装コード説明では、構造分析や問題提起をせず、コード上の事実と仕様との対応だけを説明する。
原因分析の後で初めて、どの行にどの判断や前提が漏れているかを説明する。

### 掲載単位（1定義1ブロック）

長いコードを一度に見せない。**掲載の最小単位は「1つの定義」**である。第9章 `output/chapter09_2.md` の1-4・3-1・7-1を基準実装とする。適用範囲は1-4（現状コード）、3-1（変更を試みる）、フェーズ6の断片、7-1（完成コード）で、この4か所は同じ書き方でそろえる。

#### 単位の形

各単位は必ずこの順で置く。

1. 見出し（定義名だけの太字）
2. 1行の導入 ―― このブロックで何を見るか
3. コードブロック
4. 説明
5. `---` の区切り線

区切り線を省くと、説明が上のコードのものか下のコードのものかが読者に分からなくなる。導入を省くと、読者は目的を持たずにコードへ入ることになる。

#### どこで分けるか

**1ブロック＝トップレベルの1定義。** 行数では分けない。「長いから割る」「短いからまとめる」はどちらも誤りである。`class`、`struct`、`enum class`は、それぞれ1つずつ別のコードブロックへ置く。同じ契約を実装する短い兄弟クラスも同居させず、共通の導入の下へ1クラスずつ隣接して置いて比較する。共通ヘッダー、自由関数、`main()`も、型定義へ詰め込まず役割ごとに分ける。

クラス内に短いメソッドを実装込みで置くことは、そのクラス1つの定義なので分割違反ではない。宣言と定義を分ける基準は次項に従う。

**ブロックはトップレベルの型をまたがない。** 判定に迷ったら次で決める。

> **そのブロックが1つの見出しで説明できないなら、それはまとめすぎである。**

#### 宣言と定義を分ける基準

原則は分けない。分けるのは次の一行で判断する。

> **メンバーを見ないと読めない関数は、メンバーと一緒に置く。**

つまり、**手順を持つ関数（制御フロー・複数ステップの処理）があるクラスだけ**、宣言ブロック（メンバーと公開操作の一覧）と、定義ブロック（関数1つにつき1ブロック）へ分ける。それ以外のクラスは、メンバーと処理を同じブロックへ置く。定義だけを並べると継承関係とメンバーが見えなくなるので、機械的に全クラスを分けてはならない。第9章では19クラス中、分けたのは `TicketService` と `TicketManager` の2つだけである。

#### 掲載ブロックと実ファイルを混同しない

コードブロックは読解単位、`.h`／`.cpp`は依存・変更・ビルドの単位であり、同じ判断ではない。本書は動作確認のため、各章のブロックを上から連結すると1つの`.cpp`になる形を正本とする。一方、実務の配置は次を基本にする。

- `.h`：利用側へ公開する契約、クラス宣言、引数・戻り値に必要な型
- `.cpp`：メソッドの処理本体と外へ公開しない補助処理
- `main.cpp`：実体の生成・所有・登録・注入と公開入口の呼び出し

インターフェースのように処理本体を持たない型は、宣言と短い定義をヘッダーへ置き、対応する`.cpp`を作らない構成もある。小さな値の型は、同じ機能境界で一緒に変更される場合だけ`OrderTypes.h`のような共有ヘッダーへまとめてよい。行数や「同じ画面に収まるか」でファイルを決めない。第0章「掲載ブロックと実ファイルの分け方」で、掲載用1ファイルと実務配置の違いを読者へ説明する。

#### 見出しに書かないこと

見出しは定義名だけにする。クラス名、または `Class::method()` である。

- 「（継承なし）」「`: public Base`」など、コードを見れば分かる情報は書かない。
- 役割の要約を見出しへ足さない。役割は導入の1行で書く。
- 兄弟クラスの片方だけを分けない。`EscalatedPhase` を単独ブロックにするなら、`ResolvedPhase` と `PendingPhase` も単独にする。

#### 説明の深さ

**1行が下限である。** 名前を言い換えるだけの説明（「`assign()`：担当者を割り当てます」）は、コードを読めば分かるので置かない。消すか、意味のある説明へ変えるかのどちらかにする。

1行を超えて書いてよいのは、次のいずれかがあるときだけである。

1. 判断が2つ以上ある
2. 順序に意味がある（入れ替えると壊れる）
3. 失敗の扱いがある
4. 所有権・生存期間・前提がある

#### `main()` と実行結果

`main()` と実行結果は、全定義を説明した後、最後に置く。`main()` を行のまとまりごとに区切り、**各まとまりの直後に対応する出力を置く**。離れた `main()` と出力を読者に往復させない。

掲載したブロックを上から順に連結すれば、そのまま1つのプログラムとして動くようにする。これは `script/check_execution_output.py` が1-4と7-1について機械で確認する。

### 接続点コードの略記禁止

接続点（変わる側と守る側の境界）に当たるコードは、**絶対に略さない**。「← 他のelse ifブロックがここに続く」「〜も同様に並ぶ」「…が続く」のような省略は、読者から判断材料そのものを奪う。同じ構造の分岐が並ぶこと自体が接続点の重要情報なので、全分岐を記載する。接続点以外の周辺コード（検証・保存など）を省く場合は、コードブロックの外で維持条件として明記する。

### 関数・データの記述スタイル

- クラスのデータメンバと各関数の先頭には、役割を示すコメントを付ける（全章共通）。
- 同型で並列な極小関数（1行のエラー出力など）は、揃えた1行形式で並べてよい。並列関係が縦に見え、Kindleの80字制限内に収まる場合に限る。
- それ以外の関数は、1行に潰さずブロック（複数行）で書く。Kindleでは横幅が狭く、1行に詰めた実装は読みにくい。
- 同じコードを別の節で再掲するときは、行の折り返し・ブロック構造を変えない。「おさらい」と言いながら形が違うと、読者は別のコードだと誤解する。

### クラス図の記述スタイル

- クラス図で他と線がつながらないクラスを置く場合、「誰が使うか」の注記（note）または直後の本文説明を必ず添える。
- 矢印のラベルは依存の目的説明（「商品情報を取得」など）として許容する。時間順のやり取りはシーケンス図で示す（0章「クラス図の読み方」参照）。

#### クラス図の線種（全章共通）

関係の種類ごとに線種をそろえる。実コードの関係と一致させる。

| 関係 | Mermaid記法 | 見た目 | 使う場面 |
|---|---|---|---|
| 実現（インターフェース実装） | `<\|..` / `..\|>` | 破線＋白三角 | 具象がインターフェース契約を満たす |
| 継承（クラス拡張） | `<\|--` / `--\|>` | 実線＋白三角 | 具象が抽象・基底クラスを継承する |
| 依存（生成・一時利用） | `..>` | 破線矢印 | 生成して一時的に使い、メンバに保持しない |
| 関連・集約・合成（保持） | `-->` / `o--` / `*--` | 実線 | メンバとして保持する |

- C++に`interface`キーワードも`abstract`キーワードもない。純粋仮想関数を1つ以上持つクラスはC++の型として抽象クラスになる。そのうち、データメンバや業務上の共通実装を持たず、公開する業務操作を純粋仮想（`= 0`）で示す型だけを、本書では`<<interface>>`と書く。仮想デストラクタの既定実装は持てる。この場合、具象からの線は**実現**（`<|..`／破線白三角）にする。
- 掲載コードではlambdaとスマートポインタ（`unique_ptr`、`shared_ptr`、`make_unique`）を使わない。生ポインタが所有関係なら所有者のデストラクタで破棄し、借用するだけなら生存期間を本文で説明する。
- 抽象クラス（一部を実装し、一部を純粋仮想で残す）には`<<abstract>>`を書き、基底に継承する線は**継承**（`<|--`／実線白三角）にする。純粋仮想関数がなく直接生成できる通常の基底クラスにはステレオタイプを付けず、同じ実線白三角を使う。
- 派生側のC++構文は、契約の実装でも実装継承でも`: public 基底型`になる。型名の`I`や派生宣言だけで線種を決めず、基底型にデータ・共通実装・純粋仮想関数があるかを確認する。
- 生成メソッド（ファクトリー等）で作って一時的に使い、メンバに保持しない関係は**依存**（`..>`／破線矢印）にする。参照・所有としてメンバに保持する関係は実線（関連・集約・合成）にする。
- `classDiagram`は原則として`direction TB`で統一する。横向きが不可欠な例外は、図の目的と例外理由を本文に明記する。各型は保持・生成・引数・戻り値・呼び出しのいずれかで関係線へ接続し、説明のない孤立型を作らない。

### フェーズ6のコード提示

フェーズ6は、フェーズ5の全課題から**一つの実行可能な構想**を作る場所である。契約だけ、生成だけ、実行だけを別々に完成させない。選択方法、所有者、生存期間、受け渡し、実行順は相互依存するため、主要クラスと接続順を最初に一望へまとめる。

#### 構想を決める

冒頭に次を一表と一経路で示す。

- 契約と代表具体
- 具体の生成者・所有者・生存期間
- 必要な登録・選択と、その判断材料
- 利用側へ渡す実際の操作
- 公開入口から契約・具体・結果までの呼び出し順

この構想では`main()`、`Class::method()`、生成場所を示してよい。これらは完成コードの先出しではなく、全点が同時に成立する案かを検算するための設計名である。コードで成立しなければ構想へ戻る。

登録は候補を預けること、選択は候補から使う実体を決めること、注入は外で用意した実体を利用側が契約として使う場所へ渡すことである。同じ語でまとめず、章で実際に行う操作名を書く。

#### 構想をコードでつなぐ

本文は次の順に連続させる。

1. `#### 契約：境界の形と受け渡しを決める`
2. `#### 具体：契約の裏へ変わる判断を置く`
3. `#### 生成・選択・受け渡しを決める`
4. `#### 実行骨格：組み立てた実体を契約から呼ぶ`
5. `#### 公開入口から具体の実行まで追う`

変更前コードは境界を引く根拠になる数行だけをフェーズ3「変更を試みる」から抜く。変更後は契約、代表具体、生成・受け渡し、実行の要点だけを示す。同型の全具体、完成コード、実行結果を再掲しない。

フェーズ6のC++断片には、既存コードなら`**変更前から抜き出す箇所：**`、構想のコードなら`**ここで確認するコード：**`を直前へ置く。所属する定義・メソッドを`Class::method()`または`main()`で示す。

一つのC++ブロックにはトップレベルの型を一つだけ置く。入力・取得、判定、選択・計算、保存、通知・返却の意味が切り替わる箇所は空行で区切る。

#### 構想を採用する

最後は、課題ID→採用構想→完了条件の表と、リスクID→備え→変更先→残る弱点の表だけを置く。分離、配置、実行を別の要約表で繰り返さない。完成可能な構想が一つなら比較せず、責任配置や依存関係が異なる複数構想が残る場合だけ、変更影響・導入コスト・運用規則で比較する。

フェーズ6には`classDiagram`を置かない。完成後のクラス図、完成クラス一覧、実行シーケンス、全コード、実行結果はフェーズ7「対策実施」で一度だけ示す。

問題から導いた構造名を使い、デザインパターン名を対策理由にしない。実装と効果を確認した後で、得られた構造を共有語彙としてパターン名へ結び付ける。

## 実行結果ルール

実行結果は、最終値だけを並べない。
読者が「何を・いくらで・誰が」入力し、「どう変わって」その値になったかを追えるようにする。

- 入力（対象データ・金額・会員種別など）と結果（小計→支払金額、状態遷移など）をセットで出力する。
- 内部の件数・残高・在庫・予約数を変更するときは、対象IDと「変更前→変更後」（必要なら上限・単位）をログへ出す。結果名だけで数値変化を隠さない。
- 将来リスクにはリスクID1から連番を付ける。2-5で「変わる見込み＝はい」「変えられるようにする部分」「今回維持する部分」を確定し、対策検討で同じリスクIDを採用構造へ再適用する。リスクIDを扱うのはフェーズ2と6だけとし、フェーズ3・7には持ち込まない。リスクIDは実装要求ではないため、未確定機能を完成コードや実行結果へ追加しない。
- システムが後続して行う昇格・通知・補償・履歴記録を、`main()` や運用者による別操作として実装しない。起点となるユースケースから自動的に呼ぶ。
- 状態が変わらないエラーは状態遷移図の矢印に含めず、エラー条件表と実行結果で示す。
- 検証・照会メソッドが成否や結果を返す場合は、呼び出し側で判定・保存・返却のいずれかに使う。戻り値を意図的に持たない命令は`void`とし、結果を捨てているように見える呼び出しを残さない。
- 割引・加算・状態変化など、施策や操作の効果が変更前後で読み取れる形にする（例：`小計 10000円 → 支払金額 8000円`）。
- 実行結果の直前に、実行対象コード・対応する動作例ケース・確認したいことを書く。
- 複数ケースを並べるときは、ケースの区切りと、どのコード（現状／変更後／最終）の結果かを示す。
- 実行結果が複数ケースにまたがる場合や1ブロック25行以上になる場合は、呼び出しコードをケース単位へ分け、各コードの直後へ対応する結果を置く。一括`main()`の後に全ケースの長い結果をまとめない。
- 最終値の羅列だけにして、「何が起きたか」を読者の推測に委ねない。

## フェーズ4の比較表

- 全パターン章の4-2は、列見出しを `今回変える責任` / `ほかの変更から守る責任` の2列へ統一する。恒久的な変わりやすさではなく、今回観測した変更理由と保護範囲を比較する。
- 題材固有の語、原因の詳細、赤丸・緑丸などの色付き記号は行の内容で表し、列見出しには加えない。

## コードラベルのルール

| ラベル | 用途 |
|:---|:---|
| `// ← 知らなくていい` | 原因分析後に、呼び出し元へ漏れている判断や前提を示す |
| `// ← ここだけ変わる` | 改善後に、変更影響が局所化された行を示す |
| 【深化コード】 | より難しい変化への対応 |
| 【過剰コード】 | 使いすぎた失敗例 |

`// ← 知らなくていい` は、フェーズ4以降の説明根拠があるコードで使う。
フェーズ1の現状コードには入れない。

## パターン名の扱い

パターン名は、対策を決める前の選択肢ラベルや、対策を指示する動詞の目的語として使わない。「Strategyを適用する」「Stateを使う」のように名前から設計行為を表す文は避け、必要な責任移動・境界・組み立てを述べる。
章タイトルでは、読者の検索性と期待値合わせのためにパターン名を出してよい。ただし「得られること」、ステップ名、要約表、本文中の判断理由では、パターン解説前は本文で導いた構造名を使う。
問題を解いた後、その構造をチームで共有する語彙として紹介する。「ここまで導いた構造は、一般に【パターン名】と呼ばれる」と接続する。
パターン解説の直前に、題材から導いた構造とパターン名を結ぶ移行文を置く。見出しだけで突然パターン名へ切り替えない。

## 章内参照の書き方

本文から別の項目へ読者を移動させるときは、番号だけで参照しない。初回は`フェーズ3「変更を試みる（3-1）」`のようにフェーズ名・項目名・番号を併記し、同じ段落や近接箇所で繰り返すときだけ`変更試行（3-1）`と短縮する。表の列名、要求IDの対応欄、コードの出典ラベルは番号だけでも対象が明らかなため、この規則の対象外とする。

## テスト文法説明ルール

スタブ・モック・アサーションマクロが初めて登場する箇所に、1〜2行の日本語コメントを添える。

```cpp
class IPayrollFacade {
public:
    virtual int calculateNetPay(int grossPay) = 0;
    virtual ~IPayrollFacade() = default;
};

// スタブ：本物のAPIを呼ばずに、あらかじめ決めた値を返す差し替えクラス。
class StubPayrollFacade : public IPayrollFacade {
public:
    int calculateNetPay(int grossPay) override {
        return grossPay - 1200;
    }
};

class PayrollCalculator {
    IPayrollFacade& payroll;
public:
    explicit PayrollCalculator(IPayrollFacade& payroll)
        : payroll(payroll) {}

    int calculate(int grossPay) {
        return payroll.calculateNetPay(grossPay);
    }
};

StubPayrollFacade stub;
PayrollCalculator calc(stub); // コンストラクタでスタブを注入する。

// EXPECT_EQ(期待値, 実際の値)：等しければテスト通過。
EXPECT_EQ(8800, calc.calculate(10000));
```

## Kindle品質ルール

- コードブロック：1行80文字以内。
- Mermaid図：テキストでも意味が伝わる説明を必ず添える。
- 仕様図は正常系を先に描き、入力・判定・加工・正常出力を形状または色で区別する。成功側しか描かない入力検証はひし形＋`Yes`にせず、検証済み入力と処理順で表す。ひし形を使うのは正常系にも複数の有効な結果があり、図に全分岐を描く場合だけとする。異常系は同じ図へ混ぜず、エラー条件表で扱う。エラー条件表は正常系の各種仕様表をすべて示したあと、1-1の最後に置く。
- 脚注：使わない。
- 表：列数は最大4列まで。
- 1段落の長さ：5〜7行以内。
- コードブロックの前後：必ず説明文を置く。

#### 節番号は、フェーズごとの初出で節名を併記する

`5-3で決まっています` のような裸の番号は、読者が何の話か思い出せず、節を行き来することになる（著者指摘 2026-08-30）。**各章・各フェーズの中で最初に現れた参照へ、`5-3（課題IDと接続点を確定する）` の形で節名を足す。** 同じフェーズの2回目以降は、直前に名前を見ているので番号だけでよい。フェーズが変わったら数え直す。

節名は各章の見出し `### 5-3：…` から取る。`実装コード（現状）` のように末尾へ補足の括弧が付く節は、`1-4（実装コード）` と補足を落として入れ子を避ける。直後に節名と同じ語が続く場合（`1-2bの状態遷移表`）は、重複するので足さない。

反映は `script/annotate_section_refs.py` で機械的に行う。見出し・表・引用・コードブロックは書き換えない。**本文の定型文を文字列一致で検査している箇所があるので、走らせた後は `validate_book.py` を必ず回す。**
