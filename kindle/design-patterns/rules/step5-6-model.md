# フェーズ5〜7 接続点レビュー・モデル

このファイルは `design-decision-guide.md` の短縮版である。

## フェーズ5：原因から課題を検討して確定する

- 5-1：フェーズ4の各原因から、痛みを減らすために変えるべき構造を課題候補として導く。まだ課題IDを付けない
- 5-1：各候補の直前または表内で、フェーズ3・4のどのクラス、メソッド、分岐、データ操作を根拠にしたかを示す。要求IDを課題IDへ変換しない
- 5-2：候補の必要性、重複、依存、独立性、網羅性、完了状態をシステム全体で評価し、統合／分割／除外を判断する
- 5-3：採用候補だけに課題ID1から欠番なくIDを付け、`課題ID・接続点 / 接続するもの・変わる側 / 守る側 / 完了条件` の一表へまとめる。接続するものと変わる側は同じセル内でラベルを付けて改行する
- 要求IDと課題IDを直接対応させない。課題は`変更ID→変更試行→痛み→原因`から導く。要求を局所変更で満たせ、設計上の痛みがなければ課題IDを作らない

## フェーズ6：構想を一つのコード経路へ変える

- 構想：主要クラス、契約・具体、生成者・所有者、登録・選択、受け渡し、公開入口から結果までを一表と一経路へまとめる
- 要点コード：契約→代表具体→生成・選択・受け渡し→実行骨格→公開入口の順に続ける
- 採用判断：課題IDとの対応と将来リスクだけを確認し、別の要約表を重ねない
- 完成物：完成クラス図、全コード、実行シーケンス、実行結果はフェーズ7だけに置く

固定的な分類から案を選ばない。完成構造が一つなら比較せず、全課題を満たす完成構造が複数残る場合だけ比較する。

## フェーズ7：要求・課題・変更影響を別々に検証する

- 全有効要求IDが最終コードと受入結果に対応し、既存要求も維持できたか（既存動作の消失は要求ID別の回帰で確認する。機能IDは設けない）
- 課題IDごとに構造差分と減った変更影響を確認できるか
- 変更IDごとに今回の変更でどこを修正するか
- どこを再テストするか
- 組み立て・登録・設定に残る変更は何か
- 導入コストに見合うか

最後に、採用した構造の共有語彙としてパターン名を紹介する。
