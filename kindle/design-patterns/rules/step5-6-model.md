# フェーズ5〜7 接続点レビュー・モデル

このファイルは `design-decision-guide.md` の短縮版である。

## フェーズ5：原因から課題を検討して確定する

- 5-1：各原因について、どの責任をどの責任から分けるかと、境界で渡す入力・受け取る結果を決める。まだ課題IDを付けない
- 5-1：変更要求を現状構造へ当てた責任配置と目標配置を、同じ抽象的な責任名の部分クラス図で対比する。着目箇所を色と番号で示し、最終クラス名・操作名・生成方法は先取りしない
- 5-1：一部だけ切り出して具体名や判断が残る配置は、原因が残るため途中案として文章で退ける。独立した節や一般的な比較表は作らない
- 5-2：目標責任配置図の番号へ課題ID1から欠番なくIDを付け、各課題を`解く原因 / 構造の変更 / 接続 / 完了条件`の短いカードへまとめる。変更後構造を別の表や長文で定義し直さず、接続では送信元・送信先と入力・結果／反映を一文で示す。原因を反転した完了条件はコードで真偽判定できる短い箇条書きにする
- 責任をメソッドやデータ項目の数へ合わせない。同じ業務上の理由で一緒に変わる処理は一つの責任へまとめる
- 要求IDと課題IDを直接対応させない。課題は`変更ID→変更試行→痛み→原因`から導く。要求を局所変更で満たせ、設計上の痛みがなければ課題IDを作らない

## フェーズ6：構想を一つのコード経路へ変える

- 導入：フェーズ5で決めた責任配置を再確認し、契約→具体→生成・所有→受け渡し→実行の順でコード構造へ変えると示す。最終判断の表や完成図を先出ししない
- 契約：フェーズ5の課題カードにある業務上の入力・結果／反映を再検討せず、C++のクラス／インターフェース、メソッド、引数型、戻り値型へ翻訳する。共通型を置く根拠がなければ具体クラスまたは関数にする
- 要点コード：契約→代表具体→生成・選択・受け渡し→実行骨格→公開入口の順に続ける
- 構造判断：責任・継承・実現・保持・注入を決める箇所では、対象外を明記した部分クラス図と対応コードを組にする
- 構想確定：採用する責任配置と原因が残る形を短文で確定する。責任→クラス対応図を表へ書き直さず、完了条件の合否はフェーズ7へ送る
- 完成物：部分図を統合した完成クラス図、全コード、実行シーケンス、実行結果はフェーズ7だけに置く

固定的な分類から案を選ばない。完成構造が一つなら比較せず、全課題を満たす完成構造が複数残る場合だけ比較する。

## フェーズ7：要求・課題・変更影響を別々に検証する

- 全有効要求IDが最終コードと受入結果に対応し、既存要求も維持できたか（既存動作の消失は要求ID別の回帰で確認する。機能IDは設けない）
- 課題IDごとに、フェーズ5の全完了条件を一つずつコードまたは実行結果の証拠へ照合し、合否を確認できるか
- 変更IDごとに今回の変更でどこを修正するか
- どこを再テストするか
- 組み立て・登録・設定に残る変更は何か
- 導入コストに見合うか

最後に、採用した構造の共有語彙としてパターン名を紹介する。
