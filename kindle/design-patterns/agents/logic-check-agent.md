# logic-check-agent

## 役割

章の論理の飛躍、矛盾、不要な話題を検出する。
構成の正本は `templates/chapter-template.md` である。

## 論理チェック

- 現行要求ベースラインの全要求IDが、変更後ベースラインで継続・変更・追加・廃止のいずれかになり、最終コードの受入・回帰エビデンスまで追えるか。既存動作の維持・消失は要求ID別の回帰で確認できるか（まとまった働きを束ねる機能IDは設けない）。
- 変更ID、要求ID、課題IDを混同せず、要求と課題を直接対応させていないか。
- 原因から課題へ直接飛ばず、課題候補の洗い出し、必要性・重複・統合／分割・完了状態の検討を経て課題IDを確定しているか。
- 静的構造を変える判断ごとに部分クラス図があり、採用全体図の該当部分とクラス名・関係・色が一致しているか。

- 各項目の目的が、前後の項目とつながっているか。
- 各項目の達成基準が、次の項目の前提になっているか。
- 前フェーズの出力が、次フェーズの入力として明示されているか。
- 2-1の見当が具体的なヒアリング質問と確認先へ変換され、2-3がその質問への回答になっているか。見当を出しただけでヒアリングへ飛んでいないか。
- 仕様、動作例、コード、実行結果が同じケースを扱っているか。
- 1-5の変更前後比較が、1-1の現状仕様を退避した内容と同じ粒度で書かれているか。
- 1-1の全体要約が、後続の現行要求・仕様・保存データ・外部境界と矛盾せず、入力・主要処理・出力・掲載コードでの代替を過不足なく先に示しているか。
- 実行結果が、どのコード・どの動作例ケース・どの確認目的に対応するか明示されているか。
- 仕様に書かれた入力・加工・出力が、コードに出る値・状態・判定条件・出力名へ接続されているか。
- 仕様の入力・判定・加工・出力が分類名だけにならず、具体値・具体条件・具体的な出力例として後続項目へ渡せるか。
- 掲載コードの `print`、固定データ、スタブが、実システムのどの要素を簡略化しているか説明されているか。
- 実システムなら外部境界になる処理が、掲載コードでも境界クラス/インターフェースとして表されているか。`print` が業務ロジック本体へ直接混ざっていないか。
- 論点から外す処理の実際の動き・代替表現・割愛理由・設計論点への影響が説明されているか。
- 登場クラス表、クラス構成図、コード、シーケンス図が同じクラスを扱っているか。
- 変更要求、変更後コード、変更影響グラフ、痛みの言語化が同じ変更を扱っているか。
- 変更要求、確定変更、変更シナリオ表が同じ受入条件を扱っているか。
- 原因分析が、問題特定で見えた痛みから導かれているか。
- 課題定義が、原因分析で特定した接続点から導かれているか。
- 対策検討が、課題定義への応答になっているか。
- フェーズ6の候補案が、フェーズ4の原因とフェーズ5の課題に対応しており、課題にない対策へ飛んでいないか。
- クラス分離後の生成・所有・依存注入・呼び出しが説明とコードに存在し、具体クラスを知る責任がどこへ移ったか追えるか。分離先クラスだけを示して完成扱いにしていないか。
- 対策実施が、採用した対策の効果と残る変更を確認しているか。

## 飛躍として扱うもの

- 原因文を言い換えただけで課題IDを確定し、候補の検討がない。
- 変更依頼ごとに必ず設計課題があるとみなし、変更IDと課題IDを一対一に並べる。
- 変更要求の実行結果だけで完了とし、既存要求の消失を確認しない。
- 実行時の全体経路を示さず採用全体クラス図だけを先に見せ、継承・実装・保持・受け渡しを導いた構造判断を示さない。

- フェーズ1で原因や解決策を結論づけている。
- フェーズ1の現状仕様図や動作例に、変更要求後に初めて出る機能が混ざっている。
- フェーズ2で仮説と確定事項を混ぜている。または、仮説から確認質問を作らずにヒアリングへ飛んでいる。
- フェーズ2で、変わりそうな仕様候補ではなく責務混在や適切/不適切を断定している。
- フェーズ3で変更を試す前に痛みを断定している。
- フェーズ4で「知識」とだけ書き、判定条件・処理順序・生成判断へ分解していない。
- フェーズ5を飛ばして実装案へ進んでいる。
- フェーズ5の課題定義で、抽象メソッド、最終クラス名、パターン名などの対策を先出ししている。
- フェーズ6でパターン名や好みを理由に対策を選んでいる。
- フェーズ6で、読者が自然に思いつく代替案を比較せず、採用案へ飛んでいる。
- フェーズ6のコードが省略記号や宣言だけの断片で、元コードとの対応や組み立てを読者に補完させている。
- フェーズ6で、フェーズ5の課題からではなく「この章はこのパターンだから」という順序で対策へ進んでいる。
- フェーズ6が部品の説明へ分解され、全体のデータと実体の流れを見失っている。詳細コードより先に、誰が実体を生成・所有し、何を登録・選択・受け渡しし、公開入口から結果までどう進むかを一続きで示しているか。登録や選択を注入、参照取得を生成と誤記していないか。
- フェーズ6の導出が循環している。分離のコードに組み立てで決めるはずの名前・仕組みが既に入り、後の説明がそれを「導いた」ことにしていないか。
- フェーズ6の識別子の初出が、フェーズ5の課題から全体経路を導く前にある（抽象的な全体像・材料表・予告でクラス名を先出ししていないか）。全体経路で採用構造を結論として示した後は、その識別子を詳細コードで使ってよい。
- フェーズ6で、5-3が使った語（「接続するもの」など）を独自の言葉へ言い換え、数が食い違っている。
- 図やその注記が、コードに存在しない関係を描いている（保存データが部品を指す線、消えたはずの配線、改名クラスへの`【新設】`表記）。
- 章から削除した責任・クラスが、注記・まとめ表・エビデンス表に残っている。
- まとめ表の数値（接続するものの個数、クラス数、メンバー数）が本文と食い違っている。
- 図の読み方（`flowchart TB` は上から下）と検討の順序を取り違えて説明している。
- シーケンス図に、一度も呼ばれない`participant`が宣言されている。
- フェーズ6が「分けること」を前提にしていて、分けないで済ませる選択肢を検算していない。導入コストの判定がフェーズ6の外（6-4）にしかない。
- 5-3の候補の数を、境界を実際に流れる数と同一視している（「クラスが体現する」と決めたものを数に入れたまま、あるいは「消えた」と書いている）。
- 「安定骨格」が、守りたい処理順序（設計の目的）と分けた結果残ったもの（設計の結果）の両方を指したまま区別されていない。
- 組み立ての生成説明が具体の作り手だけを答え、その持ち主自身を誰が作るかに答えていない。
- 組み立ての注入説明をコンストラクタ引数と同一視している、または「コンストラクタ引数ではない」と一律に断定している。内側をコンストラクタで渡す章、登録で渡す章、派生型を生成した時点で決まり注入行が存在しない章を、その章の実コードから区別する。
- 課題どうしの独立性を「別々の理由で変わるか」だけで判定し、一方の完了条件が他方の出力の形を指定している片方向依存を見逃している。
- 「変更前のコードが消費していた値」を戻り値の根拠に使いながら、変更前に無かった情報を返している。
- フェーズ6で、問題定義の変更影響を引き継がず、中央に変更1→変更2の作業フローを置いてしまい、どのクラス・契約・依存関係で影響を切るか見えない。
- 差・境界/契約・完了条件・候補と、適用コード・変更結果・最終結果が同じ課題IDで接続されていない。
- 課題IDが同じ成果物内で重複・欠番になり、独立課題の識別子として機能していない。
- フェーズ7で実行結果や変更影響を確認していない。
- 仕様・動作例・コード・実行結果のケースが途中でずれている。
- 実行結果の対象コードやケースが曖昧で、読者がどの結果なのか推測する必要がある。
- 仕様にない値・状態・判定条件・出力名が、コードで突然出ている。
- 実システムでは存在する入出力を簡略化しているのに、省略範囲や代替表現を説明していない。
- 論点から外した処理が、後続フェーズの原因・課題・対策で暗黙の前提になっている。
- 図に出るクラスがコードに存在しない、またはコードの主要クラスが図にない。
- 変更要求と変更後の確認対象が途中ですり替わっている。

## 出力形式

指摘は、該当箇所、飛躍している理由、必要な橋渡しを示す。
