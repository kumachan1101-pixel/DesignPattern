# AIコンテキスト - 設計思考を鍛える本

## このファイルの位置づけ

このファイルは、章を生成・修正するAIが読む入口である。
別のAIへ作業を渡す場合は、最初に `AI_HANDOFF.md` を読む。
詳細ルールを重複して収録せず、次の正本を順に読む。

1. `AI_HANDOFF.md`
2. `CLAUDE.md`
3. `design-philosophy.md`
4. `shared/skills/author-voice.md`
5. `rules/writing-rules.md`
6. `rules/connection-point-review.md`
7. `rules/design-decision-guide.md`
8. `rules/phase-consistency-check.md`
9. `templates/chapter-template.md`
10. `agents/chapter-agent.md`

## 本の目的

デザインパターン名を暗記することではなく、変更要求を受けたときに次を説明できるようにする。

1. 何が変わるのか。
2. 何を変えたくないのか。
3. 変更を試すとどこが痛むのか。
4. 変わる理由が異なる判断・条件・処理順序・生成判断がどこに混在しているのか。
5. 接続点で何を受け渡しているのか。
6. 呼び出し元へどの判断や前提が漏れているのか。
7. どの判断・条件・処理・生成責任をどの責任へ移すのか。
8. 導入コストに見合うか。
9. 変更要求を再度当てたとき、修正・再テスト範囲がどう変わるか。

## 7つのフェーズ

| フェーズ | 目的 |
|---|---|
| 1：現状把握 | 1-1冒頭で入力・主要処理・出力・掲載コードの代替をつかみ、現行要求IDの要求ベースライン、仕様、動作例、登場クラス、現状コード、変更ID、変更後要求ベースラインを事実として読む |
| 2：仮説立案 | 見当を具体的な質問と確認先へ変換してからヒアリングし、今回確実に変わることと将来リスクを分ける |
| 3：問題特定 | 変更IDを試し、修正・確認・再テスト範囲として痛みを確認する |
| 4：原因分析 | 混在する判断・条件・処理・生成判断と、接続点へ漏れている前提を言語化する |
| 5：課題定義 | 原因から課題候補を導き、システム全体で統合／分割／除外してから、接続点と完了条件へ課題IDを付ける |
| 6：対策検討 | 全課題を解く分離・配置・組み立てを決め、判断ごとの部分クラス図と段階コードで示す |
| 7：対策実施 | 実装・実行し、要求IDの受入、課題IDの構造結果、変更IDの変更影響を別々に確認する |

各フェーズは、前フェーズの出力を次フェーズの入力として使う。
入力、加工、出力の流れが見えにくい箇所は、文章だけで説明せず図または表で示す。ただし分類図で終わらせず、図に置いた各要素が後でどの動作例・コード・変更要求・接続点で使われるかまで対応づける。

## 接続点レビュー

接続点を固定的な種類へ分類しない。次の問いを使う。

- 境界を越える値・型・操作・イベントは何か。
- その仕様は、どの機能・仕様変更で変わるか。担当者や関係者が分かる場合は補助情報として使う。
- 呼び出し元が相手のクラス名を知る必要はあるか。
- 呼び出し元が生成方法や処理順序を知る必要はあるか。
- 条件分岐や生成判断はどちらの責任か。
- 変更要求を当てると、どのファイルを修正・再テストするか。
- 呼び出し元へ残す最小限の約束は何か。

## 対策検討

課題候補をシステム全体で評価した後、確定した全課題IDを同時に満たす分離方法・配置場所・組み立て方法を決める。完成構造が一つなら比較しない。責任配置や依存関係が異なる完成構造が複数成立する場合だけ比較する。

静的構造の判断ごとに、最終採用クラス図から関係部分を抜き出した着色済みの部分クラス図を理由の直後・コードの前へ置く。部分図は迷いや未採用案ではなく、完成構造を段階的に理解するための抜粋である。

## パターン名の扱い

パターン名から設計を選ばない。
問題を解いた後、その構造をチームで共有する語彙として紹介する。

Strategy、Facade、Stateなどを一つの分類体系へ無理に当てはめない。
各パターンが解く問題と意図を、その章の変更要求から説明する。

## 執筆上の注意

- 既存コードを否定しない。
- 一つの正解を押しつけない。
- 架空の著者体験を書かない。
- 「変更がゼロ」「絶対に壊れない」と断定しない。
- 組み立て、登録、設定、テストに残る変更を隠さない。
- コードは実行可能にし、掲載した出力と照合する。
- AIへの指示文や引用マーカーを本文へ混入させない。
- `templates/chapter-template.md` の目的・達成基準・図解基準を章本文の起点にする。
