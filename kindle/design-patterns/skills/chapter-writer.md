# 章を執筆する手順

## 正本

章構成は `templates/chapter-template.md` を正本とする。
第1章や過去章の見出しがテンプレートと食い違う場合は、テンプレートを優先する。
別のステップ番号や独自のフェーズ構成を作らない。

執筆前に次を読む。

1. `CLAUDE.md`
2. `design-philosophy.md`
3. `rules/writing-rules.md`
4. `rules/connection-point-review.md`
5. `rules/design-decision-guide.md`
6. `rules/phase-consistency-check.md`
7. `templates/chapter-template.md`

## 章作成の基本

- 各標準見出しの直下に、本文へ出さない執筆用コメントとして `目的` と `達成基準` を置く。
- 目的には「なぜこの項目を置くのか」を書く。
- 達成基準には「この項目を読み終えた読者が何を説明・予測・判断できる状態になっているか」を書く。
- 本文、図、表、コード、実行結果は、その目的と達成基準を満たすために置く。
- 図だけで新しい仕様や判断を初出ししない。図に出る名前・値・状態は、本文または表で説明してから使う。
- 各フェーズ単体の達成基準だけで合格にしない。仕様、動作例、クラス、コード、実行結果、変更要求、変更影響、最終コードが章全体で同じ対象を追っているか確認する。
- フェーズ間整合は `rules/phase-consistency-check.md` を正本とする。
- 仕様は、コードに出る値・状態・判定条件・出力名へ紐づく粒度まで定義する。
- 掲載コードで `print`、固定データ、スタブ、簡略化した `main()` を使う場合、実システムでは何に相当するかを図または表で示す。仕様変更で新たに加わる外部API、タイマー、永続化、非同期受信、画面などは、現状の簡略化と分けて1-5へ置き、実システムの変更対象・掲載コードの代替・省略範囲・省略しても実行する処理を示す。
- C++の型定義は、`class`、`struct`、通常の`enum`、`enum class`、`namespace`を含め、トップレベルの1定義ごとにコードブロックを分ける。見出しには直下で定義する1つの名前だけを書き、複数クラスのまとめ見出しを置かない。
- 登録順や組み合わせが業務上の優先関係を表す場合、専用の組み立てクラスが具体を所有・登録し、`main()`は完成した部品の生成と注入だけを担う形にする。
- 論点から外す処理は、実際はどう動くか、掲載コードでは何で代替するか、なぜ割愛するか、設計論点への影響がないかを補足する。

## 7つのフェーズ

### フェーズ1：現状把握

標準見出し：

1. `1-1：このシステムの仕様`
2. `1-2：動作例テーブル`
3. `1-3：登場クラスとクラス構成図`
4. `1-4：実装コード（現状）`
5. `1-5：変更要求`

事実だけを確認する。原因分析、設計上の痛み、解決策を先取りしない。
第0章の確認観点に沿い、「何を受け取り、何をして、何を返すか」「どのクラスが何を担うか」「今回何を変えるか」を、題材の仕様・構造・コードで順に答える。
1-1の最初に「最初にシステム全体をつかむ」を置き、要求表より前に入力、主要処理、出力、掲載コードでの代替を示す。大筋を先に渡してから、要求・データ・図・クラス・コードを体系的に説明する。
変更前システムの要求には要求ID1からIDを付け、現行要求ベースラインを作る。今回の変更依頼には変更ID1からIDを付け、1-5で各要求IDの継続・変更・廃止と追加要求IDを示した変更後要求ベースラインを確定する。変更IDを要求IDとして扱わない。
仕様は、入力、加工、出力の構造図または表で示す。
実システムの入出力を簡略化する場合は、省略範囲と代替表現を示す。変更要求で初めて加わる簡略化は1-5へ分ける。
クラス構成図の前に、登場クラスの責任説明を置く。

### フェーズ2：仮説立案

フェーズ1の事実から、変わりそうな部分を仮説として挙げる。
第0章の確認観点に沿い、「どの仕様が、どんな理由・きっかけ・頻度で変わりそうか」「今回何を維持するか」を題材固有に答える。
今回確実に変わること、将来リスク、当面安定していることを混ぜない。
関係者ヒアリングは、仮説を確認するために置く。2-1の最後で見当を具体的な質問と確認先へ変換し、2-3はその質問へ答える順で書く。

### フェーズ3：問題特定

変更IDを現状コードへ当てる。
第0章と同じ「この場所は、今回の変更の理由と関係があるか」を明示し、要求を満たすために直接必要な追加・修正と、現在の構造に巻き込まれた修正・解読・再テストを題材固有に分ける。
痛みを感想で語らず、修正箇所、確認範囲、再テスト範囲として示す。
変更影響はグラフで可視化し、直接変更と巻き込まれた変更を区別する。

### フェーズ4：原因分析

各問題IDについて、何を変えたくて既存のどこまで直したかを、短いコード上の目印とともに文章で示す。全処理は再列挙しない。責任はフィールドやメソッドではなく、同じ業務上の理由で一緒に変わる仕事のまとまりとし、実務で通じる短い名前を付ける。責任ごとに変更前後の具体的なルールを並べた後、コードへ戻って変更理由の異なる責任の同居や直接依存を確認し、原因IDを付ける。
「知識」は曖昧に使わず、判定条件、計算式、処理順序、生成判断、クラス名、型、操作名などに分解して書く。
呼び出し元が相手の何を知りすぎているかを明示する。
原因分析では、境界、クラス、インターフェース、型・操作名、生成場所、対策候補を決めない。

### フェーズ5：課題定義

原因から課題IDへ直接変換しない。5-1で、変更要求を現状構造へ当てた責任配置と目標配置を、同じ抽象的な責任名の部分クラス図で対比する。着目箇所へ番号を付け、一部だけを切り出して原因が残る案は同節で短く退ける。5-2で、その番号へ課題IDを付けて完了条件を確定する。フェーズ5では最終クラス名・操作名・生成方法を使わない。
確定表は `課題（解く原因） / 分ける責任 / 分けた後のつなぎ方` の3列とする。表の直前で1行と列の読み方、入力・結果／反映の送信元と送信先を説明し、セルは入力・結果の名前だけに絞る。型名・操作名・生成場所・パターン名はフェーズ6で決める。完了条件はコードで真偽判定できる短い箇条書きにする。
変更IDと課題IDは一対一とは限らない。要求を満たすために不要な課題を作らず、複数要求が同じ構造問題を露呈する場合は同じ課題として扱う。

### フェーズ6：対策検討

見出しはテンプレートに合わせる。フェーズ5の全課題IDを同時に解く一つのシステムとして、分離方法・配置場所・組み立て方法を決める。冒頭に完成答案の表や完成図を置かず、フェーズ5の責任配置を契約・具体・生成・所有・受け渡し・実行へ順に具体化する。判断後に`課題 / 決定した構造 / コード上の実現`の表で構想を確定し、完了条件の合否はフェーズ7へ送る。
フェーズ3から再掲するのは確定課題に関係するコードだけとし、全コードをおさらいしない。中間コードは試行錯誤ではなく、採用した完成構造を理解できる実装順として示す。
責任・継承・実装・保持・注入などの静的構造を変える判断ごとに、理由の直後、対応コードの直前へ部分クラス図を置く。部分図は最終採用クラス図の抜粋であり、同じクラス名・操作・関係を使って着目箇所を色で強調する。
flowchart / graph の`［変更］`ノードには`変更前→変更後`を具体的に書く。出版本文では、図を置く編集上の理由ではなく、システムの変更事実と読者が確認する箇所を説明する。
責任配置や依存関係が異なる完成システムが複数成立する場合だけ、目的・構造差・変更影響・コストで比較する。関数化だけ、部分的な責任移動だけなど、課題を残す途中状態は比較案にしない。読者が思いつきそうなら、なぜ完了条件を満たさないかを短く補足する。
コードでは、分離先だけでなく生成場所・所有者・登録・選択・依存の受け渡し・安定側の実行まで示す。採用後の全体コードはフェーズ7へ置く。

### フェーズ7：対策実施

最終コードでは、内部数値の変更を対象ID・変更前→変更後・上限/単位付きでログへ出す。システムが続けるべき昇格・通知・補償・履歴記録は、起点ユースケースから自動で呼び、`main()` の手動操作で成立させない。状態不変のエラーは状態遷移図へ描かず、エラー条件表と実行結果で扱う。要求IDによる受入・回帰確認と、課題IDの完了条件および同じ変更IDによる影響縮小の確認は分けて示す。`設計課題の完了確認`では、フェーズ5の完了条件を省略せず、一つずつコードまたは実行結果の証拠と判定へ対応づける。

標準見出しは`7-1：解決後のコード（全体）`と`7-3：変更影響グラフ（改善後）`である。完成後の実行シーケンス、要求の受入・回帰、設計課題の完了確認は7-1の中へ置く。7-2や7-4を作って同じ結論を繰り返さない。

掲載コードを実行し、動作例と照合する。
組み立て、登録、設定に残る変更も記載する。
改善前後の変更影響を図または表で比較する。
変更後要求ベースラインの全有効要求IDを最終コードと受入結果へ照合する。課題IDは構造改善、変更IDは変更影響の比較に使い、三つを同じ表へ強制的に結び付けない。

## 後段

順序は次のとおり。

1. 整理
2. 振り返り
3. あなたのコードで考える
4. パターン解説

パターン名は、問題を解いた構造の共有語彙として説明する。
